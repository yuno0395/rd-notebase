## 前提と設計方針

知見は「目的・ノード・イシュー・タスク・ナレッジ」の5種類などの Markdown ファイルに分けて Box に置き、ウィキリンク `[[id_名前|名前]]` でつなぐ。各自が個人 vault で書き、知見同期プログラムが条件を満たしたものを共有 vault へ集めて、関係する人の個人 vault へ配り直す。共有 vault にあるものがチームの正本になる。

対象は BtoB のものづくり(製品開発)で得た知見。設計・材料・加工・試験・調達・顧客対応のノウハウ、失敗と対策を残し、次の案件ですぐ使えるようにする。

- 当面は2人(1人2役)なので、仕組みはフォルダとルールだけにして道具を増やさない。
- 100人規模になったときにGitや検索ツールへそのまま移せるよう、形式はテキスト(Markdown)に揃える。
- クラウドは Box を使い、各自の Windows PC で Box Drive を通して同期する。個人・共有・機密の3種類のフォルダと開発データはすべて Box 上に置き、PC の中だけには置かない(PC が壊れても消えないため)。

**この仕様書の正本**: 仕様書3点・テンプレート・設定・同期プログラムは、GitHub のリポジトリ rd-notebase を正本にする(「仕組みの正本と配布」)。共有 vault の `00_仕様書.md` などは、版を出すたびに置く写し。10年後の担当者も、知見と同じ場所でルールを読めるようにするため、写しは必ず置く。

## Obsidian の使い方(ツール非依存のルール)

Obsidian は編集と閲覧の道具として使い、知見ファイルはメモ帳や GitHub で開いても読める普通の Markdown に保つ。

- 個人 vault と共有 vault を、どちらも Box 上のフォルダとして Obsidian で開く(場所は「フォルダ構成」)。
- 同期は Box Drive で行い、Obsidian Sync は使わない。

**書き方のルール**

| 項目 | 使う | 使わない |
| --- | --- | --- |
| ノート同士のリンク | `[[ファイル名]]` の形だけ | `[[水#性質]]`(見出し)、`^id`(ブロック参照) |
| 外部リンク | `[説明](https://...)` | ― |
| 画像 | `![図1](_仕組み/attachments/0RDGPG4XGV/成形品.jpg)`(vault の一番上からのパス) | `![[埋め込み]]`(Excalidraw のフレームの引用だけは例外。「図とパワーポイント」) |
| 属性・タグ | 先頭の YAML 属性欄 | 本文中の #タグ だけに頼ること |
| 図・ボード | Excalidraw(SVG を自動で書き出す)、PNG / SVG / PDF を添付 | Canvas(.canvas) |
| 注記 | 普通の引用 `>` | コールアウト `> [!note]` |

**ウィキリンクとツール非依存の両立**: ノートのファイル名は `id_名前.md`(例: `0RAYFN4XGV_水.md`)にし、リンクは `[[0RAYFN4XGV_水|水]]` と書く。| の左はファイル名そのものなので、Obsidian がなくても同じ名前のファイルを開けばたどれる。id がファイル名の先頭にあるので、名前の部分を後で変えても id で探せる。VS Code(Foam)や Logseq なども同じ書き方を読める。

- ファイル名は vault 全体で一意にする。これは id で保証する(「ノートの id」の節)。
- 名前の部分に `# | [ ] ^ : \ /` を使わない。
- まだないノードへのリンクは `[[水]]` と名前だけで書いてよい。同期プログラムがノートに id を振るときに、id 付きのリンクに直す。
- この仕様書の例では、読みやすさのため id を省いて `[[水]]` と書いている。実際のノートでは `[[0RAYFN4XGV_水|水]]` の形になる。

**Obsidian の設定**: 「ファイルとリンク」で、Wikiリンクを使うをオン、新しいリンクの形式を「最短パス」にする。「ファイル名変更時にリンクを更新」はオンにする。添付ファイルの置き場所は Custom Attachment Location で決める(下の「添付ファイルの置き場所」)。

**添付ファイルの置き場所**(Yu 2026-10-23)

画像・PDF・軽い動画は、vault の一番上の `_仕組み/attachments/<ノートの id>/` に、元のファイル名のまま入れる。

```
_仕組み/attachments/
├── 0RDGPG4XGV/            ← 「保圧を変えて試作する」の添付
│   ├── 成形品.jpg
│   └── Pasted image 20261024103512.png
└── 0RBDMG4XGV/
    └── ヒケ断面.pdf
```

- ファイル名は変えない。ノートの id は全員で一意なので、別の人が同じ名前のファイルを貼っても、共有 vault でフォルダが分かれて名前がぶつからない。
- 個人 vault と共有 vault で同じパスになるので、共有へ集めるときも配るときもリンクを書き換えない。ノートと一緒に `_仕組み/attachments/<id>/` ごとコピーする。
- フォルダ名を id にするのは、ノートの名前の部分を後で変えても、添付のフォルダとリンクが変わらないようにするため。
- 同じノートに同じ名前のファイルを2回貼ったときだけ、Obsidian が末尾に番号をつける。
- 設定(Custom Attachment Location): 「Follow Obsidian attachment location」をオフにし、添付フォルダを `_仕組み/attachments/{{frontmatter:{key:'id'}}}`、ファイル名を `{{originalAttachmentFileName}}` にする(今の版は `${…}` ではなく `{{…}}` の書き方)。名前のない貼り付け画像(スクリーンショット)は Obsidian の既定の名前(`Pasted image <日時>`)のままにする。リンクは vault の一番上からのパスで入れる。設定で選べない書き方は同期プログラムが直す。
- このために、ノートの id は作るときにテンプレート(Templater)が入れる(「ノートの id」)。まだ id のないノートに貼った添付は、同期プログラムが id を振るときに `_仕組み/attachments/<id>/` へ移し、リンクを直す。
- 重い添付は vault の外の `開発データ/<プロジェクト>/<id>/` へ移す(「重い添付ファイルの置き場所」)。ここでも元のファイル名のままにする。

**コアプラグイン**: テンプレート、デイリーノート、Canvas など、ファイルに独自の書式や別形式を残すものは知見作りに使わない。検索・バックリンク・グラフなど見るだけでファイルに痕跡が残らないものは使ってよい。Bases は例外として使ってよい(Dataview の上位互換として一覧表に使う。Yu 2026-10-23)。Dataview は使わない。.base ファイルは索引ノートと同じく vault 直下に 00_タスク一覧.base のような名前で置き(イシュー・タスク・ソリューション・ノードの4つ。個人 vault にも同じものを配る)、知見ノートには埋め込まない。例外はプロジェクトのノート(台帳)だけで、テンプレートに `![[00_イシュー一覧.base#台帳用]]` を入れ、そのプロジェクトのイシューを priority 順に出す(台帳は知見ノートではないため。Yu 2026-10-24)。一覧は属性欄の type(例: type == "タスク")や project・priority で絞る。そのため id と type は属性欄に残す(id は同期プログラム、type はテンプレートが自動で入れる)。Bases がなくても属性欄はただの文字なので、検索で同じものを探せる。テンプレートは _仕組み/templates/ のファイルを QuickAdd と Templater で挿入する(「標準テンプレート」)。

**使いながらプラグインを足すとき**(Yu 2026-10-25)

足してよい。ただし次の順で、まず自分の個人 vault で試し、よければ全員に配る。

1. 個人 vault でだけ試す。共有 vault と機密 vault では、配ったプラグインだけを使う(ほかの人のノートを書き換えないため)。
2. 入れる前に3つ確かめる。商用利用できるライセンスか(AGPL・GPL も可)。外してもノートがそのまま読めるか(独自のコードブロックや書き方をノートに残さない)。ノートを自動で書き換えないか(書き換えるものは、共有に集まったノートにも広がるので特に慎重に)。
3. ショートカットが配ったキー(Ctrl+K・D・I・T・H・U・S など)とぶつからないようにする。
4. よかったものは金曜の定例で出す。まとめ役がこの表に足し、正本に設定を入れ、版で全員に配る。
- 各自が足したプラグインは、版を当てても外れない。同期プログラムは有効にするプラグインの一覧(`community-plugins.json`)を「配るもの＋各自が足したもの」で合わせる(要件書 F-46)。
- 配ったプラグインの設定(`.obsidian/plugins/<名前>/data.json`)とキー(`hotkeys.json`)は版ごとに上書きされる。変えたいときは自分で直さず定例で出す。
- プラグインの自動更新は切る。新しい版はまとめ役が試験用の vault で確かめてから、使う版を変更履歴に書く。

## リーン開発との関係

開発はトヨタ式の製品開発、特に「セットベース開発」を軸にする。目標性能が決まる前は設計案を1つに絞らず、複数の候補を並べたまま、目標の物理現象から必要な構造・理想的な構造と設計空間を調べておく。目標の仮性能や販売戦略が決まったら、その瞬間に調べた範囲から一気に絞り、量産まで進める。目指すのは、他の顧客でも使え、利益率が高く、簡単に速く作れ、競合が真似できないもの。目標性能や販売戦略のように市場に聞かないとわからない部分だけは、リーンスタートアップのように小さく試して確かめる。この仕組み自体も小さく始めて直していく。

- 知見ノートには「仮説」と「検証結果」を残す。うまくいかなかった試作も残し、同じ試作を繰り返すムダをなくす。
- 知見に成熟度をつける: 仮説 → 検証済み → 標準。標準になったものは設計基準や DR のチェックリストに反映する。
- 仕組みの改善: 月末の金曜の定例で15分、書いた本数・再利用された例・困ったことを振り返り、この仕様書の版を上げる。「記録に時間を取られたか」を必ず聞き、重いと感じた入力は削る。

**セットベース開発の進め方**

| 時期 | やること | 使うノート |
| --- | --- | --- |
| 目標が決まる前(広げる) | 候補の構造を複数並べ、それぞれの物理現象と設計空間を調べる。候補どうしの終わり方ではなく、どの条件ならどの案が勝つかを知る | ソリューション(status: 候補)、実験・試作記録、ナレッジ(トレードオフ曲線) |
| 少しずつ絞る | 物理的に無理な案、他の顧客で使えない案、利益率が低い案を根拠つきで外す。外した案も消さずに残す | ソリューション(status: 不採用、外した理由) |
| 目標が決まった(一気に絞る) | DR で、決まった仮性能と販売戦略をトレードオフ曲線に当て、候補を1つにする。そこから量産までのタスクを一度に立てる | 議事録、ソリューション(status: 採用)、プロジェクトの節目の表 |

- 候補はソリューションのノートで書き、parent に実現したい価値の仮説(仮説を置くまでもなければ目的)をつける。同じ parent の候補が「一組」になり、K-Plex では並んで見える(Yu 2026-10-25)。
- 絞り込む準備ができた合図は、関係する impact 大のイシューが解像度「設計空間」以上になったとき(出荷準備度)。ここまで来ていれば、目標が決まった日に絞れる。
- ナレッジの標準の形は「トレードオフ曲線」にする。縦軸に性能、横軸にコストや寸法などをとり、候補ごとに線を引く。目標が変わっても曲線は使い回せるので、他の顧客・次の開発でもそのまま役に立つ。描き方は「トレードオフ曲線の描き方」。
- 不採用の案も知見として共有する。目標が変われば最善の案になることがあるため。

## フォルダ構成

Box の中に、個人・共有・機密の3種類のフォルダを、それぞれ好きな場所に置く(Yu 2026-10-24)。3つは入れ子にせず、完全に分ける。場所は各自の PC の同期プログラムの設定ファイルに書く。

| フォルダ | 見られる人 | 置くもの | Obsidian |
| --- | --- | --- | --- |
| 個人 | 本人だけ | 自分のノート、デイリーノート、書きかけ | 個人 vault |
| 共有 | チーム | みんなのノート(正本)、仕様書、テンプレート | 共有 vault |
| 機密(いくつでも) | 権限のある人だけ。権限がなければフォルダがあることも見えない | 事実だけ。顧客の図面・仕様書・契約・NDA 対象、測定の生データ、顧客名。知見は置かない | 機密 vault |

```
    ├── 同期設定.yaml             チーム設定
    ├── tools/同期プログラム/      保守手順書・ソースの控え・テスト用 vault・メンバー.csv(人の記号)
    ├── tools/配布/<版>/           版ごとの配布物(「仕組みの正本と配布」)
    ├── 設定/                     配る Obsidian の設定(.obsidian)と導入手順
    ├── 記録/ノート履歴/<名前>.csv  期限・状態の変わった日・古い id(同期プログラムが人ごとに書く)
    ├── templates/
    └── attachments/<id>/

<機密フォルダ>/                   例: Box\機密\顧客A\(名前は自由。共同作業者: その案件の担当者だけ。いくつでも作る)
├── 00_README.md                  この機密フォルダに何があるか、誰が見てよいか
├── 06_事実/                      事実ノート(id つき)。顧客の要求値、受け取った図面の要点、測定の生データの要約

<管理者向け報告>/                  例: Box\チーム\開発ノート_報告\(週報の HTML と 週報の一覧.html)
```

- 一番上のフォルダは、毎日開くものだけにする(Yu 2026-10-24)。デイリーと週報は 00_日誌/ に、添付・記録・テンプレート・設定・同期レポートのようにあまり開かないものは _仕組み/ にまとめる。価値の仮説は新しいフォルダを作らず、目的と同じ 01_目的/ に置く。
- 「結果」という言葉は使わず「ナレッジ」と呼ぶ(Yu 2026-10-24)。大事なのは結果そのものではなく、結果をもとにイシューのリスクが減ったかどうかの知見だから。
- 3つを別々の場所に置くので、Box の権限は各フォルダに直接つける。上のフォルダの権限が下へ引き継がれて、下だけを絞れない問題が起きない。
- 機密フォルダの名前は自由に決めてよい(Yu 2026-10-24)。共有のノートには機密フォルダの名前を書かず、事実ノートの id だけで指すので、名前に顧客名を使っても共有側には出ない。
- 機密フォルダには知見(ナレッジ・イシュー・タスク)を置かない。事実と原本だけを置く。知見は個人・共有のノートに書く。共有側には、顧客名を伏せた数値は書いてよい(例:「ある顧客の設備は月2回止まる」「要求荷重 500N」)。誰の何か(顧客名・図番・設備名)は、機密の事実ノートだけに残す。
- 個人・共有のノートから機密を指すときは、属性欄に `secret_refs: ["[[0RX00A4XGV_案件A|案件A]]"]` と、共有の「機密の窓口」ノートへのリンクを書く(Yu 2026-10-24)。機密はそれほど見返さないので、事実ノートを開くキー(Ctrl+Shift+S)は作らず、中身を知りたい人は窓口に書いてある人に聞く。窓口ノートは機密フォルダごとに1つ、共有 vault の `共通/機密の窓口/` に置く(type: 窓口)。書くのは、顧客名を使わない呼び名(例: 案件A)、readers(機密フォルダを見てよい人。Box の共同作業者と同じ)、owner(社内の当事者)だけ。顧客名・図番・設備名・相手の担当者の名前・事実の id は書かない。事実ノートの数も共有側には出さない。新しいノートのメニューの「機密の窓口」で作る(個人 vault ではいったん 02_ノード/ にでき、同期プログラムが 共通/機密の窓口/ へ集める)。機密フォルダの 00_README.md に、そのフォルダの窓口ノートの名前を書いておく。
- 機密フォルダも Obsidian の vault として開ける。事実ノートのテンプレート(type: 事実)を置く。ファイルを置くだけの使い方でもよい。id の形は同じなので、ほかのノートとぶつからない。
- 社内の正式な原本(CAD データ・正式図面・試験成績書)は既存の保管場所に置き、ノートには図番・文書番号だけを書く。
- 設計・加工などの分野はフォルダでは分けず、ノード同士のリンクで表す。フォルダが増えると振り分け先に迷うため。
- 個人と共有で同じファイル名(同じ id)のファイルは「同じもの」と扱う。

**各自の設定ファイル**(同期プログラムが読む。場所は PC ごとに違ってよい)

```yaml
member: Yu
personal: C:\Users\yunos\Box\個人\開発ノート_Yu
shared: C:\Users\yunos\Box\チーム\開発ノート_共有
shared_data: C:\Users\yunos\Box\チーム\開発データ
report: C:\Users\yunos\Box\チーム\開発ノート_報告

  - C:\Users\yunos\Box\機密\顧客A
```

**複数の PC で使う**(Yu 2026-10-25)

1人が自宅と職場など2台以上の PC で、Box Drive 上の同じ個人 vault を開いてよい。どの PC でも同じように動くよう、次のように決める。

| 起きやすいこと | 決まり |
| --- | --- |
| 前回同期の記録が PC ごとだと、別の PC で変えていないノートを「競合」と見誤る | 記録は個人 vault の `_仕組み/記録/同期の記録.json` に置き、どの PC からも同じものを使う。v0.45 までの `%APPDATA%\知見同期\state_<名前>.json` は、新しい方がまだなければ1回だけ読む |
| 2台で同時に同期すると、同じノートの改名やコピーがぶつかる | 同期の間だけ個人 vault に札 `_仕組み/記録/同期中.lock`(PC の名前と時刻)を置く。別の PC の札が15分より新しければ、その回は見送る。15分より古い札は止まった PC のものとみなして取り直す |
| 重い添付のリンクに、Windows のユーザー名入りの場所(`file:///C:/Users/<名前>/Box/...`)が入る | 開発データは Box Drive の中に置くので、ユーザー名が同じ PC どうしなら同じ場所になる。ユーザー名が違っても、`C:/Users/だれでも/Box/...` の形なら同じ開発データとして読む(共有へは `開発データ/...` の形で集まる) |
| Obsidian の画面配置(`.obsidian/workspace.json`)の Box の複製ができる | 中身は画面の並びだけなので、同期プログラムが backup に移して片付ける |
| Templater の「Trigger Templater on new file creation」は PC ごとの設定 | 2台目の PC でも手でオンにする(マニュアル「初期設定」)。忘れても、同期プログラムがあとから id をつける |

- 同期プログラムの設定ファイル(`config.yaml`)は PC ごとに置く。中身の場所は PC ごとに違ってよい。
- スマートフォンは Box Drive の外なので対象にしない。

**vault の名前を変える**(Yu 2026-10-25)

個人・共有・機密の vault のフォルダ名は、あとから変えてよい。フォルダ名はノートにも同期の記録にも残らず、書いてあるのは各 PC の `config.yaml` の場所だけだからである。システム管理者が名前を変えても、各 PC の `config.yaml` を1台ずつ直さなくて済むようにする。

| 起きやすいこと | 決まり |
| --- | --- |
| 名前を変えたあと、PC の `config.yaml` が古い場所のまま | 同期プログラムが新しい場所を探し、見つかれば `config.yaml` のその行だけを書き直す(コメントは残し、直す前の控えを同じ場所に置く)。探すのは、元の場所の上で残っているいちばん近いフォルダと、その1つ上のフォルダから、それぞれ下へ3段まで(ホームフォルダとドライブの一番上は探さない。要件書 F-50) |
| 新しい場所が本当に同じ vault か | 各 vault の `_仕組み/記録/vault_id.txt` に、その vault だけの印を置く(同期プログラムが最初の同期で作る)。印は `config.yaml` の隣の `vault_ids_config.json` に覚える。印を覚える前の PC でも、個人は `個人設定.md` の name、共有は メンバー.csv に自分の名前があることで見分ける |
| 候補が2つ以上ある(vault を丸ごとコピーしたなど) | 選ばずにレポートに出し、人に直してもらう |
| 個人 vault が見つからない | 何も書かずに止める。古い名前の空のフォルダを作り直すと、そこへ共有のノートが配られてしまうため |
| 機密フォルダが見つからない | 機密の言葉が混ざっていないかを確かめられないので、同期を止める(v0.46 までは警告だけで続けていた) |

- Obsidian の保管庫の登録は名前を変えると外れる。各自が開き直し、Templater の「Trigger Templater on new file creation」をもう一度オンにする(マニュアル「システム管理者 普段の仕事」)。
- 開発データ・報告フォルダの名前は変えない。重い添付のリンク(`file:///…/開発データ/…`)がノートに書いてあるためである。

## 5種類のノートとつながり方

目的を頭に、「目的を価値の仮説に分け、仮説を実現するソリューションの候補を出し、イシューが候補の実現を脅かし、タスクがイシューを減らし、ナレッジがイシューのリスクがどう変わったかを示す」という一本の流れでつなぐ。ノードはそのどれからも参照される辞書になる。仕事の中心は、ソリューションの候補を磨くこと(Yu 2026-10-25)。

```
  [目的] ← [価値の仮説] ← 実現する ─ [ソリューション候補] ← 脅かす ─ [イシュー] ← 減らす ─ [タスク] ← リスクの変化を示す ─ [ナレッジ]
     ↑                                    │                              │                 │
     └──── 目的に直接つく候補もある ──────┘                              │                 │
                                          └─────────── 関係する ─────────┴─────────────────┘
                                                                         ▼
                                                                      [ノード]  ── ノード同士もリンクし合う
```

| 種類 | 中身 | リンクする先 |
| --- | --- | --- |
| 目的 | 開発の根幹目的。何のために、誰に何を届けるか | 関係するノード |
| 価値の仮説 | 目的を、確かめられる形に分けたもの。1つの目的に3〜5個(例: 電池3年、後付け10分、1週間前の予兆検知) | 目的 |
| ソリューション | 価値の仮説(または目的)を実現する案の候補。1つの仮説に複数並べ、磨いて絞る。図番・採用の理由もここに残す(v0.37 までの設計記録) | 実現する価値の仮説か目的、細かい候補なら上のソリューション |
| ノード | ものや値の名前と、何から決まるか(parts)、どう変化するか | 他のノード |
| イシュー | ソリューションの候補が本当に仮説を実現できるかを脅かすリスク、関係する単語、何をすれば減らせるか。候補がまだないうちは仮説に直接つけてもよい | 脅かされる候補(なければ価値の仮説)、関係ノード |
| タスク | リスクを減らすための仕事。担当・期限・状態 | 減らすイシュー、関係ノード |
| ナレッジ | タスクを実行してイシューのリスクがどう変わったか(結果そのものより、リスクが減ったかどうかの知見が大事。Yu 2026-10-24)。impact 大はナレッジのノートと Excalidraw のナレッジ図(画面1枚)、中・小はタスクの「リスクはどう変わったか」欄に数行 | 対象のタスクとイシュー |

- **価値の仮説**(Yu 2026-10-24): 「顧客価値を最大にする」のような目的は広すぎて、イシューが目的に沿っているかを判定できない。そこで目的の下に価値の仮説を3〜5個置き、その下にソリューションの候補、候補の下にイシューをつなぐ。仮説は 01_目的/ に置き、parent に目的を書く。知見が増えると、目的と仮説の間の筋道(なぜその仮説で目的に近づくか)や、仮説を覆す事実が見えてくる。これを書くのも仮説を進めるのと同じくらい大事なので(Yu 2026-10-24)、仮説の下に仮説を置いて筋道を木にし、覆す事実は challenger でつなぐ。週報の「目的に沿わない開発」は、仮説につながらないもので判定する(ソリューションを通ってつながればよい)。
- **ソリューション**(Yu 2026-10-25): 仮説を置いたら、最初にやるのは仮説を実現する案の候補を出すこと(例: 目的「顧客満足度を最大にする」→ 仮説「当日出荷」→ 候補「近くに倉庫」「受注生産をやめて在庫」)。候補ごとに「本当に仮説を実現できるか」を問い、それを脅かすリスクをイシューにする。目的に直接つく候補も置ける。ソリューションは 01_目的/ に置き、Ctrl+U で作る。案を分けて考えるときは、ソリューションの下にソリューションを置く。
- 上流へのリンクは属性欄の parent に、関係するノードは friend に書く(仮説が目的を、ソリューションが仮説を、イシューがソリューションを、タスクがイシューを、ナレッジがタスクを指す)。K-Plex がこれを読んで全体像を描く。逆向きは書かず、Obsidian のバックリンク表示で見る。二重管理を避けるため。
- ナレッジでわかったこと(例: 保圧を上げるとヒケが減る)は、関係するノードにも書き戻す。これが次の開発で使える知見になる。

**例: ノード「水」**

```markdown
---
type: ノード
parts: ["[[水素]]", "[[酸素]]"]
---
# 水
0℃以下で [[氷]]、100℃以上(1気圧)で [[水蒸気]] になる。
```

**例: 値のノード「ヒケ量」**

```markdown
---
type: ノード
value_kind: 組み立て
parts: ["[[肉厚]]", "[[保圧]]", "[[PA66の収縮率]]"]
---
# ヒケ量
肉厚が厚いほど、保圧が低いほど大きくなる。関係式がわかれば本文に書く。
```

**例: 電子デバイスの値のノード「電池寿命」**

```markdown
---
type: ノード
value_kind: 組み立て
parts: ["[[電池容量]]", "[[スリープ電流]]", "[[送信間隔]]", "[[送信1回の消費電荷]]"]
---
# 電池寿命
送信間隔が短いほど、スリープ電流が大きいほど短くなる。電池寿命 ≒ 電池容量 ÷ 平均消費電流。
```

**例: ものづくりでの流れ**

| 種類 | ファイル名 | 本文に書くこと |
| --- | --- | --- |
| 目的 | 外観不良ゼロで樹脂カバーを量産する.md | 顧客に届ける価値、判定基準 |
| イシュー | 肉厚部のヒケで外観不良になるおそれ.md | 阻害: \[\[外観不良ゼロで樹脂カバーを量産する\]\]、関係: \[\[PA66\]\] \[\[ヒケ\]\] \[\[保圧\]\]、減らし方: 肉厚を均一にする、保圧を上げる |
| タスク | 保圧を変えて試作する.md | 減らす: \[\[肉厚部のヒケで外観不良になるおそれ\]\]、担当、期限 |
| ナレッジ図 | 保圧を変えて試作する_ナレッジ図.excalidraw.md | 実施前後のリスクの変化を画面1枚で |

## 全体像の把握(K-Plex)

開発の全体像は K-Plex で見る。目的(目標)を中心に、イシューと事実がどうつながっているかをたどり、目標の解像度がどれだけ上がったかを確かめる。[K-Plex](https://github.com/zsviczian/kplex) は Excalidraw と同じ作者のプラグインで、中心のノートの上に親、下に子、左に友(関係)、右に反論(challenger)を並べて表示する。独自のデータは持たず、属性欄とリンクを読むだけなので、外しても知見はそのまま残る。

| 属性名 | K-Plex での位置 | 書くもの |
| --- | --- | --- |
| `parent` | 上 | 上流。仮説は目的か上の仮説、ソリューションは実現する仮説か目的(または上のソリューション)、イシューは脅かすソリューション候補(なければ価値の仮説)、タスクは減らすイシュー、ナレッジは元のタスク |
| `friend` | 左 | 関係するノード |
| `challenger` | 右 | 前提を覆す事実。方針が180度変わるような結果を、その目的・仮説・イシューにつなぐ |
| (子) | 下 | 書かない。parent の逆向きとして K-Plex が自動で表示する |
| previous | 左 | イシューを生んだ対策(タスク・実験・試作記録)。対策で新しい機能や構造ができ、そこから生まれたイシューに書く |

- K-Plex を開くのは Ctrl+G(Obsidian 標準のグラフ表示の代わり)か、本文の右クリックのメニューの「K-Plex で見る」。開いているノートが中心になる(Yu 2026-10-24)。
- `parent`・`friend`・`challenger`・`previous` は K-Plex の既定の属性名に入っていて、大文字小文字を区別しない。既定から1つだけ変え、子の属性名に `parts` を足して配る(`.obsidian/plugins/k-plex/data.json`。Yu 2026-10-24)。ノードを中心にすると、parts に書いた部品や決める値が下に並び、末端が独立値かを目で追える。個人 vault では 90_共有/ に配られた他の人のノートもつながるので、プロジェクト全体の中で自分の仕事の位置が見える。
- friend と challenger は、本文の `[[ ]]` の上で右クリックし、「関係としてつなぐ」「反論としてつなぐ」で属性欄に足す(Yu 2026-10-24)。属性欄を手で書かなくてよい。本文のリンクはそのまま残る。
- カードの名前は aliases の最初の値を使う。すべての種類のテンプレートが aliases に名前を入れるので、id は出ない(Yu 2026-10-24)。テンプレートを使わずに作った古いノートは id つきで出るので、気になれば aliases に名前を書く。
- カードの色は priority で変える(1 赤、2 橙、3 黄、4 灰。Yu 2026-10-24)。status が解消・中止・不採用・外れたのものは、Graph Lens「終わったものを薄く」で灰色の点線にする。どちらも K-Plex のテーマ「開発ノート」に入れて配る(既定のテーマは K-Plex が読み込むたびに元の色に戻すため)。priority は同期プログラムが書くので、動く前は色がつかない。
- K-Plex の中でもノートを作れる(Ctrl+矢印)が、テンプレートと id の決まりを通らないので、いまは使わない。K-Plex の中心のノートを開く編集欄(Editor node)でも書かない。試したところ、編集欄を開いたまま中心を別のノートに移すと、前のノートの中身を移った先のノートに上書きした(K-Plex 0.2.3)。K-Plex は見るのに使い、作るのは Ctrl+I / T / H と Ctrl+N にする。
- K-Plex を見ながら作るときは Ctrl+Shift+N(「K-Plex の中心から作る」、Yu 2026-10-25)。K-Plex の中心のノートから、種類(イシュー・タスク・仮説・ソリューション)を選び、名前を打つと、Ctrl+I / T / H / U と同じ決まりで作る(parent・project・previous が入る)。中心の種類に合う種類が先頭に出る。K-Plex を開いていなければ、今開いているノートから作る。作ったノートは K-Plex の中心の下に出る。
- 値は `parent: ["[[外観不良ゼロで樹脂カバーを量産する]]"]` のように引用符で囲む。これで K-Plex がなくても普通の YAML として読める。
- 「事実」はノードを指す。イシューの friend につなぐノードが、そのリスクの背景にある事実になる。maturity(仮説 / 検証済み / 標準)で、その事実がどこまで確かかを示す。

**対策から新しいイシューが生まれるとき**

1. イシューの対策としてタスクを作る。わかった新しい機能や構造は、元のソリューションの「わかったこと」に書き足して案を磨く(大きく分かれるなら、その行で Ctrl+U を押して下のソリューションにする)。
2. 新しい部品や構造はノードにし、ソリューションの friend につなぐ。
3. タスクの「リスクはどう変わったか」から新しいイシューを作る。parent は元のイシューと同じソリューション候補、previous はそのタスクにする(Ctrl+I で作れば自動で入る)。
4. 新しいイシューも impact と speed で優先順位をつけ、他のイシューと同じように進める。

K-Plex では「イシュー → 対策 → 磨いた案 → 新しいイシュー」の連鎖を previous でたどれる。対策ごとに生まれたイシューの数も数えられる。

**たどれるようにする仕掛け**

- タスク・実験・試作記録の中で Ctrl+I を押すと、previous に今のノート、parent に元のイシューのソリューション候補(なければ価値の仮説)、project に元のイシューの値が入ったイシューができ、押した行が新しいイシューへのリンクに変わる(Yu 2026-10-24。以前の案の QuickAdd「このノートから新しいイシュー」を Ctrl+I にまとめた)。
- 同期プログラムは、タスク・実験・試作記録の「リスクはどう変わったか」「判定」にあるイシューの previous が空なら、そのノートを previous に入れてレポートで知らせる。手で作って書き忘れてもつながる。
- イシューに `generation`(元のイシューが 1、そこから生まれたものが 2…)を持たせる。Ctrl+I が元のイシューの値＋1 を入れ(元に generation がなければ 1 とみなす)、同期プログラムが previous をたどって合っているか確かめる。同期プログラムが共有 vault 直下の `00_イシュー世代ツリー.md` に、世代ごとに字下げしたツリーを普通の Markdown で書き出す。世代が深くなり続けている箇所(対策が次々にリスクを生んでいる箇所)を金曜の定例で見直す。

**目標の解像度**

解像度は「目的を阻害するイシューを、現象・性質まで因果でたどれているか、その因果をモデルにできているか」で測る。ただし一番大事なのは、装置として出荷できるだけリスクを管理しきれているかどうか。設計空間がわかれば物は作れる。原理までわかっていればなお良い。

各イシューの属性欄に resolution(段階)を書く。段階は DR で決める(下の「段階の判定」)。書かなければ「未把握」と扱う。

| 段階 | resolution | 状態 | 判断の目安 |
| --- | --- | --- | --- |
| 0 | 未把握 | リスクの名前だけで、原因はわかっていない | friend に検証済みのノードがない |
| 1 | 現象 | 何が起きるかを事実で確かめた | 現象・性質のノード(maturity: 検証済み)に因果がたどり着いている |
| 2 | 設計空間 | どの寸法・条件をどの範囲にすれば起きないかがわかっている。物は作れる | ナレッジに許容範囲が数値で書かれ、確認済み(例: 肉厚 2.0〜2.5mm、保圧 60〜80MPa。電子なら スリープ電流 5µA 以下、送信間隔 10〜30分) |
| 3 | 原理 | なぜ起きるかを因果モデル(式・シミュレーション)で説明でき、範囲の外も予測できる | parts をたどった末端がすべて独立値で、関係式と適用範囲がノードに書かれ、maturity が 標準 |

**出荷できるかの判定**(一番大事な指標): その目的につながる impact 大のイシューがすべて段階2以上で、status が 低減済み か 解消 になっていること。段階3は「なお良い」もので、出荷の条件にはしない。

```latex
\text{出荷準備度} = \frac{\text{impact 大で段階2以上のイシュー数}}{\text{その目的の impact 大のイシュー数}}
```

- 因果の距離: イシューの friend から、ノードの parts を下へたどる。末端がすべて独立値なら、原因を「これ以上分けられない値」まで分解できている。末端が組み立て値のまま(parts が空)なら、まだ本質に届いていない。同期プログラムがイシューごとに数え、届いていないイシューを次の検証の候補として同期レポートに出す。K-Plex でも目で確かめられる。

**独立値と組み立て値**(Yu の提案 2026-10-23)

値を表すノードには `value_kind` を書き、原因をどこまで分解できたかを数えられるようにする。

| 区分 | 意味 | 例(樹脂成形) | 書くこと |
| --- | --- | --- | --- |
| 独立値 | このプロジェクトで直接決めるか、与えられる値 | 肉厚、保圧、金型温度、PA66 の収縮率 | 単位、設計空間(効く範囲) |
| 組み立て値 | 他の値の組み合わせで決まる値 | ヒケ量、外観品質、成形サイクル、コスト | `parts:` に決める値のノード。わかれば関係式を本文に |

電子デバイスでは、送信間隔・電池容量・マイコンのスリープ電流(部品の仕様で与えられる)が独立値、電池寿命・平均消費電流が組み立て値になる。

- 独立かどうかは立場で変わる(材料の物性は設計者には与えられた値、材料メーカーには組み立て値)。そのプロジェクトで直接決めるか与えられる値を独立とする。
- セットベース開発では、独立値が候補ごとに振って試すもの、組み立て値が比べる性能になる。トレードオフ曲線の軸はここから選ぶ。
- `parts` は物の構成(水 ← 水素・酸素)にも値の構成(ヒケ量 ← 肉厚・保圧)にも使う。本文に「何からできているか」の章は作らない。
- 現場の負担を増やさないよう、value_kind が空なら「未分類」と扱う。分類はまとめ役が金曜の定例でつけてもよい。
- 週報には、目的ごとに出荷準備度と、段階0〜3のイシュー数を並べて書く。
- イシューが増えると分母が増えて数字は一時的に下がる。これは「見えていなかったリスクが見えた」という前進として扱う。

**段階の判定**: resolution の段階は、DR(デザインレビュー)で複数人が判断して決める。独立値・組み立て値の数え方は判断の材料にするが、それだけで段階を決めない。作成者は案を書いておき、DR で決まったら DR 議事録(Ctrl+N の「DR 議事録」。属性に `kind: DR`)の「解像度の判定」に「- [[イシュー]]: 現象 → 設計空間(根拠)」のように残し、イシューの resolution を更新する。DR の場では `00_イシュー一覧.base` の「DR 用」ビューで、impact 大(方針・絞込・出荷)のイシューを段階ごとに並べて見る(Yu 2026-10-24)。候補の絞り込みは `00_ソリューション一覧.base` の「候補の一組(仮説・目的ごと)」ビューで、同じ parent のソリューションを並べて比べ、結果を「絞り込み」の欄に残す。このビューには候補ごとに「残りのイシュー」(この候補にリンクしているイシューのうち status が未対応・対策中の数)と「うち impact 大」が出る。少ないほど磨けている候補(Yu 2026-10-25)。絞り込みの根拠にしたトレードオフ曲線は、議事録の「使ったトレードオフ曲線」に [[ ]] で残す。線が目標に届かない案は不採用の根拠になる。出荷準備度も DR で決まった段階だけで数える。

## イシューの優先順位

イシューは「目的達成へのインパクトが大きい」かつ「すぐできる」ものから着手する。各イシューに impact と speed をつけ、その組み合わせで priority(1〜4)を決める。

**impact(目的達成へのインパクト)は5段階**(Yu 2026-10-24)

開発の初期は、どのイシューも「解けないと出荷できない」に当たる。そこで「大」を、セットベース開発での意味で3つに分ける。答えが出ると候補が減る問いほど先に解く。

| impact | 意味 | 例 |
| --- | --- | --- |
| 方針 | 答えによって開発の方向が変わる。構造候補の大半が消える、または狙う顧客・市場が変わる | 樹脂化そのものが成り立つか。無線方式で電池3年が成り立つか |
| 絞込 | 答えによって候補のいくつかが消える | 肉厚4mm案でヒケが出るか |
| 出荷 | どの候補を選んでも解く必要がある。解けないと出荷できない | 量産での寸法ばらつき |
| 中 | 遅れやコスト増になるが、出荷はできる | 金型修正の回数 |
| 小 | 改善になる程度 | 梱包の手間 |

- この仕様書で「impact 大」と書くときは、方針・絞込・出荷の3つをまとめて指す。記録の重さ・確認・出荷準備度の決まりは、3つとも同じに扱う。
- 現場の質問は「答えによって開発の方向が変わる？」「候補が減る？」「解けないと出荷できない？」を順に聞き、はい / いいえで答える。
- 迷ったら「出荷・すぐ」にする。作るときに直感で1回選び、金曜の定例で直す。

**speed(すぐできるか)**

- すぐ: 約1週間以内に、今ある人・設備・予算で試せる。
- 時間がかかる: 試作発注、設備導入、顧客・仕入先の回答待ちなどが必要。

**priority の決め方**

| priority | impact と speed の組み合わせ | 扱い |
| --- | --- | --- |
| 1 | 方針・すぐ、絞込・すぐ | 最優先で着手 |
| 2 | 方針・時間がかかる、絞込・時間がかかる、出荷・すぐ、未判定 | 時間がかかるものは、分解してすぐできるタスクを探す |
| 3 | 出荷・時間がかかる、中・すぐ | 手が空いたら |
| 4 | 中・時間がかかる、小 | 保留(見直しのたびに確認) |

- 時間がかかる絞込は priority 2 に置く。早く始めないと、目標が決まった日に絞れず、セットベース開発が回らないため。
- 出荷のイシューは、候補が絞られてから解く方が無駄がない。消える候補のために解かずに済むため。
- **期限から逆算する**: 認証・金型・長納期部品のように、始めてから終わるまで何週もかかるイシューには `lead_weeks`(かかる週数)を書く。マイルストーン(イシューの milestone、なければプロジェクトの次のマイルストーン)の見込み日までの残り週数が lead_weeks 以下になったら、同期プログラムが priority 1 に上げる。
- **未判定**: ショートカット(Ctrl+I)で作ったイシューは impact を「未判定」にし、priority 2 として扱う。金曜の定例では「未判定」だけを見直せばよい(Bases の一覧で impact == "未判定" で絞る)。
- priority は同期プログラムが impact と speed から計算して書く(人は書かない)。`00_イシュー一覧.base` も同じ表を Bases の式で計算した列(priority)で並べるので、同期プログラムが動く前や止まっている間も priority 順に見られる(Yu 2026-10-24)。同期プログラムが lead_weeks で priority 1 に上げたものは、一覧でも 1 になる。

**運用**

- 金曜の定例で priority 1・2 のイシューだけを見直し、impact・speed・status を更新する。リスクの変化がわかったイシューは必ず評価し直す。
- priority 2 は大きいまま扱わず、「すぐできる小さな検証」のタスクに切り出す。リーン開発の「安く速く確かめる」に合わせるため。
- 一覧は `00_イシュー一覧.base`(Bases)で priority 順に表示する。Bases がなくても「priority: 1」で検索すれば同じものが探せる。

**タスクに溺れないための歯止め**

| 歯止め | 中身 |
| --- | --- |
| 同時に進めるのは1人3件まで | 進行中が3件あるときは新しく着手しない。回答待ち・納品待ちのタスクは status を「待ち」にし、3件には数えない。待ちが2週を超えたら同期レポートに出す。priority 1 が動いている間は priority 3・4 に手を出さない |
| タスクのノートにする基準 | 半日以上かかり、イシューのリスクを下げる仕事だけ。それ以外はチェックボックスの備忘録(「日々の備忘録とデイリーノート」) |
| 記録の重さを impact で変える | 大: ナレッジ図＋ナレッジ＋確認。中: 写真と数値をタスクの「リスクはどう変わったか」欄に3行。小: 「リスクはどう変わったか」欄に1行で完了 |
| 議事録からイシューにするのは中以上 | 小は議事録に残すだけ |
| やめる手段を持つ | タスクとイシューの status に「中止」がある。priority 4 で4週動かないもの、期限切れのまま4週たったものは、同期レポートに「やめますか」と出す |

小さなタスクの後処理は、「リスクはどう変わったか」欄に1行書いてイシューを見直すだけ(5分程度)になる。丁寧に残すのは、出荷を左右する impact 大だけ。

**今の仕事を確かめる**(Yu 2026-10-24)

一番大事なのは、「目的に対して最も貢献度が高く、自分で実行でき、少しチャレンジングな仕事を今しているか」。これを Ctrl+J ですぐ確かめられるようにする。新しい属性は足さず、今ある属性だけで判定する。

| 問い | 何で判定するか |
| --- | --- |
| 目的への貢献が一番大きいか | 今のタスク(デイリーノートのタイムラインで今の時刻のもの、なければ開いているタスク)がつながるイシューの priority。自分が手をつけられるイシューの中に、もっと上のものがないか |
| 自分で実行できるか | owner が自分(空なら author)で、speed が「すぐ」、status が「待ち」「確認待ち」でないこと |
| 少しチャレンジングか | つながるイシューの resolution が「未把握」か「現象」であること(答えがまだわかっていない) |

- (まだ作っていない。案を Yu に確認中)Ctrl+J を押すと、3つの問いに ○ か × で答える。× があれば、代わりに取りかかれる上位の候補を3つ出す。毎朝、デイリーノートの先頭にも同じものを出す(同期プログラム)。
- やらなければいけない雑務はチェックボックスで書く決まりなので、判定に入れない。判定するのはタスクのノートだけ。
- 自分のタスクがすべて resolution「設計空間」以上のイシューのものなら、「答えのわかった仕事だけになっています」と知らせる。
- 本人が自分の向きを確かめる道具なので、管理者向けの週報には載せない。

**プロジェクトでの分類**

開発案件はプロジェクトでまとめ、イシューの属性欄 `project` で分類する。個人 vault のフォルダはプロジェクトごとに分けない(共有 vault では同期プログラムが <プロジェクト名>/ に集める)。

| イシューの種類 | project の書き方 |
| --- | --- |
| 1つのプロジェクトだけ | `project: [樹脂カバー量産]` |
| 複数のプロジェクトにまたがる | `project: [樹脂カバー量産, 新型ブラケット]` |
| すべてに関係する(横断) | `project: [共通]` |

- プロジェクト名はプロジェクトのノート(台帳)で決め、表記をそろえる。メンバーもここを正とし、同期プログラムの設定には書かない。
- タスクとナレッジには project を書かない。リンク先のイシューでプロジェクトがわかるため(二重管理を避ける)。
- イシュー一覧はプロジェクトごとに絞り込んで priority 順に見る。台帳を開くと、埋め込んだ一覧(「台帳用」ビュー)にそのプロジェクトのイシューが出る。「共通」はどのプロジェクトの一覧にも出す。
- ノードはプロジェクトを問わず使い回すため、project をつけない。

## ファイル形式と命名規則

すべて Markdown(.md)で書き、ファイル名は `id_名前.md` にする。id のつけ方と、種類ごとの名前の付け方は次のとおり。

## ノートの id

すべてのノートに10文字の id をつけ、ファイル名の先頭に置く(Yu 2026-10-24、人の部分を4文字に Yu 2026-10-25)。同じ名前のノートが複数できてもファイル名が衝突せず、名前順に並べると作成順になる。

**id の形**: `時刻6文字＋人4文字`。例: 番号 229999 の人が 2026-10-24 09:35:12 に作ると `0RDGPG4XGV`、1秒後は `0RDGPH4XGV`。

| 部分 | 文字数 | 中身 |
| --- | --- | --- |
| 時刻 | 6 | 2026-01-01 00:00(日本時間)からの秒数を、数字と大文字の32種類(見間違えやすい I・L・O・U を除く Crockford Base32)で表す。約34年分(2060年まで) |
| 人 | 4 | 一人ずつ決めた6桁の数字(社員番号など。例: 229999)を36進数(0〜9と A〜Z の36種類)にしたもの(例: 4XGV)。6桁の数字は必ず4文字に収まる(999999 → LFLR)。辞めた人の番号は欠番にし、使い回さない |

- 名前順(昇順)で作成順、逆順で新しい順になる。文字の並びが「数字→大文字」なので、どのツールで並べても同じ順になる。ハイフンは入れない。
- 大文字と小文字は区別しない。Windows と Box は大文字・小文字を同じ名前と扱うので、区別するとファイル名がぶつかり、並び順も崩れるため。
- 人の記号が入るので、2人が同じ秒に作ってもぶつからない。同じ人が同じ秒にまとめて作るとき(同期プログラムがまとめて id をつけるときなど)は、スクリプトが1秒ずつずらす。
- 番号は共有の `_仕組み/tools/同期プログラム/メンバー.csv`(名前・番号・使い始めた日)に並べる。各自は個人 vault の `_仕組み/個人設定.md` の属性欄に、自分の名前(name)と6桁の番号(number)を書く(Yu 2026-10-25)。テンプレートとスクリプトは番号を36進数にして id に使う。番号は `"012345"` のように引用符で囲む(先頭の0が消えないように)。同期プログラムは個人設定.md とメンバー.csv が合っているか確かめる。共有・機密の vault では、設定フォルダの名前(`.obsidian-<名前>`)からメンバー.csv の番号を引く。
- 人の部分には I・L・O・U も入る(時刻の部分とは違う)。id は人が打たず、ファイル名とリンクで使うだけなので、見間違えは問題にならない。
- **画面には id を出さない**(Yu 2026-10-25): ファイル名には id が入るが、見出し・タブ・左の一覧・検索・グラフ・リンクの候補には Front Matter Title で aliases の最初の名前(= 名前の部分)を出す。リンクは `[[id_名前|名前]]` なので本文でも名前だけが見える。aliases のない古いノートは id つきのまま出るので、気になれば aliases に名前を書く。左の一覧の並びはファイル名(= 作成順)のまま。
- id を見ても日付は読めない。作成日時を知りたいときは、Bases の一覧にファイルの作成日を出す。同期レポートでは id の横に作成日時を書く。
- **v0.38 までの id**: 人3文字(例: `0RDGPG001`)で作った id はそのまま使い、ファイル名もリンクも直さない。長さが違うので新しい id とぶつからず、先頭6文字が時刻なので並び順も保てる。プログラムとスクリプトは id を「先頭6文字が時刻、`_` までが人」と読み、長さを決め打ちしない。メンバー.csv に古い3文字の記号が残っていれば、その記号をそのまま使う。古い `_仕組み/記録/私.yaml` も、個人設定.md がなければ読む。時刻の6文字は2060年までに見直す。

**id のつけ方**

- QuickAdd・ショートカット・テンプレートで作るノートは、作るときに Templater が id を作り、属性欄に入れ、ファイル名を `id_名前.md` にする。添付のフォルダ(`_仕組み/attachments/<id>/`)をすぐ決められるようにするため。
- テンプレートを使わずに作ったノート(まだない `[[水]]` をクリックしたときなど)には、同期プログラムが次の手順で id をつける。

1. Obsidian でいつもどおり「水」という名前でノートを作る。
2. 同期プログラムが id のないノートを見つけ、ファイルの作成日時と作った人の記号から id を作る。
3. ファイル名を `0RAYFN4XGV_水.md` に変え、属性欄に `id` と `author` を書き、vault 内の `[[水]]` を `[[0RAYFN4XGV_水|水]]` に置き換える。
4. 同じ名前(ファイル名の名前の部分や aliases)のノートがすでにあれば、同期レポートで知らせる。同じものなら統合する。共有に初めて集めるノードなら、レポートの「同じもの」にチェックを入れるだけで同期プログラムがまとめる(下の「同じものに2つのノートができたら」)。

**衝突の確認**: 形の上では衝突しない。同期プログラムは念のため、共有 vault に同じ id で別のノートがないかを確かめ、あれば集めずに同期レポートで知らせる(同じ番号を2人が使ったなど、設定の誤りの印)。統合などで使わなくなった id は、共有の `_仕組み/記録/ノート履歴/<名前>.csv` に old_ids として残す。v0.22 までの形(`261023-k7q2`)で作った試しのノートは、同期プログラムが新しい形に振り直し、古い id を old_ids に残す。

**id をつけないもの**: デイリーノート(日付が名前)、テンプレート、README、同期レポート。

## 種類ごとの名前の付け方

| 種類 | 名前の付け方 | ファイル名の例 |
| --- | --- | --- |
| 目的 | 「〜する」で終わる文 | 0RAT8G4XGV_外観不良ゼロで樹脂カバーを量産する.md |
| ノード | ものの名前(名詞) | 0RAYFN4XGV_水.md |
| イシュー | 「〜のおそれ」で終わる文 | 0RBDMG4XGV_肉厚部のヒケで外観不良になるおそれ.md |
| タスク | 「〜する」で終わる動作 | 0RDGPG4XGV_保圧を変えて試作する.md |
| ナレッジ図 | タスク名＋ `_ナレッジ図` | 0RY1TD4XGV_保圧を変えて試作する_ナレッジ図.excalidraw.md |

**ノードの粒度**: 自由。「ヒケ」でも「肉厚部のヒケ」でもよい。その粒度で複数の人が同じものとして理解できれば問題ない。細かいノードを作ったら、大きい方のノードとリンクでつなぐ(例: 「肉厚部のヒケ」に \[\[ヒケ\]\] の一種と書く)。

- 正式名はファイル名の名前の部分(`0RAYFN4XGV_米.md` なら「米」)。title は書かない。
- ノードのテンプレートには最初から `aliases` の欄があり、正式名が1つ入っている(別名をよく使うため。Yu 2026-10-24)。別名があれば `aliases: [米, お米]` のように、正式名に続けて並べる。正式名も入れるのは、Obsidian で「米」「お米」と打ったときに候補に出し、選ぶと `[[0RAYFN4XGV_米|お米]]` の形でリンクが入るようにするため。id を覚えて打つ必要はない。本文に別名の章は作らない(二重管理を避ける)。
- 同じものに2つのノートができたら、古い方に中身をまとめ、新しい方の名前を aliases に移して、不要な方は 99_archive へ移す。自分のノードを共有に集めるときに、名前か別名が共有のノードと重なれば、同期プログラムが集めずに同期レポートで「同じもの」「別もの」を聞く(Yu 2026-10-24)。「同じもの」にチェックすると、次の同期で次のことをする。
  - 共有のノードの aliases に自分のノードの名前と別名を、author に自分を足す(`author: [佐藤, Yu]`。先頭が最初に書いた人)。
  - 自分のノードの本文を、共有のノードの末尾の「## まとめたメモ(名前、人、日付)」に入れ、`- [ ] Yu: 「H2O」のメモを上の本文に書き直して、この章を消す 📅 1週間後` のタスクを置く。書き直すのは人。
  - 自分の vault の中のリンクを共有のノードへ付け替え(表示名はそのまま)、自分のノードは 99_archive へ移す(消さない)。
  - 「別もの」なら両方を共有し、同じ組は二度と聞かない。
- 添付は `_仕組み/attachments/<id>/` に元のファイル名のまま入れる(「添付ファイルの置き場所」)。

## ナレッジの必須項目

ナレッジ(タスクでイシューのリスクがどう変わったかをまとめたノート)には、次の5項目がそろっている必要がある。そろっていないものは同期プログラムが共有 vault に出さない。人が書くのは risk_reduction と usefulness だけで、author は同期プログラムが書き、reviewed_by は確認した人が書き、visibility は書かなければ「チーム」と扱う。ノードは辞書なので、特定のイシューのリスク低下とは結びつけない。ノードの author は自動、visibility はチーム以外のときだけ、maturity(仮説 / 検証済み / 標準)は仮説以外になったときだけ書く。

| 項目 | 属性名 | 書き方 |
| --- | --- | --- |
| 作成者 | author | 同期プログラムが id を振るときに設定の member を書く |
| 確認者 | reviewed_by | 確認した人の名前。impact 大は作成者以外に1人以上、中・小は作成者本人でよい |
| 公開範囲 | visibility | 個人 / チーム / 社内。書かなければチーム。顧客の情報そのものは機密フォルダに置き、ナレッジには書かない(「フォルダ構成」) |
| リスクの低下 | risk_reduction | どのイシューのリスクが、どれだけ下がったか。impact の変化で書く |
| 有用性レベル | usefulness | A / B / C(下の定義) |

```yaml
author: Yu
reviewed_by: [佐藤]
visibility: 社内
risk_reduction:
  - "[[肉厚部のヒケで外観不良になるおそれ]] 出荷→小"
usefulness: A
```

- リスクを下げなかった知見(試したが効果がなかったなど)も、`"[[イシュー名]] 出荷→出荷"` と書いて残す。同じ試しを繰り返さないため。
- 1つの知見が複数のイシューに効くときは行を足す。
- `[[ ]]` は引用符 " " で囲む。囲むと Obsidian でもリンクとして扱われ、YAML としても壊れない。

| 有用性レベル | 意味 |
| --- | --- |
| A | 他のプロジェクトでもそのまま使える。設計基準やチェックリストに入れる候補 |
| B | 同じ種類の製品・工程なら使える |
| C | この案件限りの記録。振り返り用 |

## 標準テンプレート

標準テンプレートは次の14種類。共有 vault の _仕組み/templates/ を正本にし、同期プログラムで各自の個人 vault に配る。プロジェクト・議事録・実験・試作記録・設計記録は v0.13 で追加し、設計記録は v0.38 でソリューションに改めた。

| テンプレート | 作られる場所 | 作り方 |
| --- | --- | --- |
| 目標(目的) | 01_目的/ | QuickAdd |
| 価値の仮説 | 01_目的/ | QuickAdd、または行を選んで Ctrl+H(目的のノートでなくてもよい) |
| ソリューション | 01_目的/ | QuickAdd、または行を選んで Ctrl+U(仮説・目的のノートで押すと、その下の候補になる) |
| ノード | 02_ノード/ | QuickAdd |
| イシュー | 03_イシュー/ | QuickAdd |
| タスク | 04_タスク/ | QuickAdd |
| ナレッジ | 05_ナレッジ/ | QuickAdd |
| ナレッジ図(キャンバスの代わり) | 05_ナレッジ/ | Excalidraw のテンプレート設定 |
| デイリー | 00_日誌/デイリー/ | Periodic Notes が毎日自動で作る |
| 週報 | 00_日誌/週報/ | Periodic Notes が毎週自動で作る。共有 vault では 00_週報/<名前>/ に集まる |
| プロジェクト | 共有 vault の <プロジェクト名>/ | QuickAdd |
| 議事録(打ち合わせ) | 04_タスク/ | QuickAdd |
| DR 議事録 | 04_タスク/ | QuickAdd の「DR 議事録」。属性に kind: DR、本文に「解像度の判定」「絞り込み」の欄 |
| 実験・試作記録 | 04_タスク/ | QuickAdd |
| 事実 | 機密フォルダの 06_事実/ | QuickAdd(機密 vault の中だけ) |
| 機密の窓口 | 02_ノード/(共有では 共通/機密の窓口/) | QuickAdd。機密フォルダを作った人が1つ作る |
| 図(ひな形) | 各ノートの _仕組み/attachments/<id>/ | Ctrl+D(「図とパワーポイント」) |

- **ナレッジとナレッジ図は impact 大のときだけ作る**。中・小はタスクの「リスクはどう変わったか」欄に書いて終える。
- **図は説明の途中に入れる**。書いている途中で Ctrl+D を押すと、そのノートの図ができて横に開き、カーソルの位置に1枚目の引用が入る(「図とパワーポイント」)。
- **キャンバス**: コアの Canvas は使わず、Excalidraw の「ナレッジ図」テンプレートで代わりにする。実施前・やったこと・実施後の3つの枠を画面1枚分に配置しておき、Excalidraw の設定「テンプレートファイル」に指定する。
- **挿入の方法**: コアの「テンプレート」は使わず、QuickAdd と Templater を併用する。Templater は「フォルダテンプレート」を担い、03_イシュー/ などでノートを作るだけでその種類のテンプレートが入るようにする。日付や条件分岐などの処理も Templater の書き方で書き、QuickAdd から作ったときも同じテンプレートが動く。テンプレート内のスクリプトは属性欄の値を入れる程度にとどめ、できあがったノートには残らないようにする。QuickAdd(MIT)のコマンドで種類を選ぶと、決まったフォルダにテンプレート入りのノートができる。日付はテンプレート内の `{{DATE:YYYY-MM-DD}}` を QuickAdd が置き換える。
- **プラグインがないとき**: _仕組み/templates/ のファイルをコピーして使い、`{{DATE...}}` は手で書き換える。id と author はどちらの場合も同期プログラムが後から書くので、書かなくてよい。

**QuickAdd を押し間違えたときの取り消し**

> まだ作っていない(v0.41 時点)。いまは「名前を入れる前に Esc」だけが使える。作ったあとは、ノートを手で 99_archive へ移すか、作ってから10分以内ならゴミ箱へ消してよい(同期プログラムは10分以内でテンプレートのままのノートを集めない)。いまの 作成履歴.csv は make_id.js が書く「日時,id,テンプレート」の1行だけで、元のノートは残していない。

| いつ | やり方 | 仕組み |
| --- | --- | --- |
| 名前を入れる前 | Esc を押す | QuickAdd は入力を閉じると何も作らずに終わる |
| 作る直前 | 確認で「いいえ」を選ぶ | 元のノートも書き換える QuickAdd のコマンドだけ、「03_イシュー に『○○』を作り、元のノートにリンクを足します」と確認を出す |
| 作ったあと | QuickAdd の「直前の作成を取り消す」を実行 | 作ったノートを Obsidian のゴミ箱(.trash)へ移し、元のノートに足したリンクも消す |

- 取り消せるのは、作ってから中身を書いていないノートだけ。書き始めていたら「書かれた内容があります。それでも取り消しますか」と聞く。
- そのために QuickAdd は、作ったノートと書き換えた元のノートを個人 vault の `_仕組み/記録/作成履歴.csv` に1行残す。ノートの属性欄には書かない。
- ゴミ箱は Obsidian の設定「削除したファイル」を「Obsidian のゴミ箱(.trash)」にして使う。間違えて取り消しても、ここから戻せる。
- 同期プログラムは、作ってから 10 分以内で中身がテンプレートのままのノートには id を振らず、共有にも出さない。取り消しの前に名前が変わったり他の人に配られたりしないようにするため。

**追加した4つの役割**

- プロジェクト: プロジェクト名・メンバー・関係する目的を書く台帳。`project` の表記をそろえるためと、同期プログラムが「誰に何を配るか」を決めるために使う。
- 議事録: デザインレビューや顧客との打ち合わせは、イシューが生まれる一番の場になる。「出た指摘 → イシュー」「決まったこと → タスク」にすぐつなげられる形にする。イシューにするのは impact 中以上の指摘だけで、小は議事録に残すだけにする。
- 議事録・実験・試作記録は 04_タスク/ に置き、振り分け・確認・共有のルールはタスクと同じに扱う。
- 実験・試作記録: 条件・測定値・写真を毎回同じ形で残す。ものづくりのリーン開発ではこの記録が「事実」の元になる。
- ソリューション(v0.37 までの設計記録): 価値の仮説を実現する案の候補。候補を並べ、「本当に仮説を実現できるか」を問い、わかったことで磨き、採用・不採用の理由を残す。図面の原本は置かず、図番と版数を書く。あとから「なぜこの形にしたのか」をたどれるようにする。01_目的/ に置く(Yu 2026-10-25)。古い 設計記録 のノートは、そのままソリューションとして扱う。

**属性は使うときだけ書く**(Yu 2026-10-23)

| 扱い | 属性 | 理由 |
| --- | --- | --- |
| 残す(自動) | type(テンプレートが入れる)、id(同期プログラムが入れる) | id はファイル名が変わっても消えないように。type は Bases で種類ごとに一覧するため |

## ショートカットキー(質問なしで作る)

文字を書く速さ・因果を考える速さを邪魔しないよう、質問に答えずにノートを作れるキーを用意する(Yu 2026-10-24)。足りない属性は既定の値で入り、金曜の定例で見直す。QuickAdd の質問つきのボタンも残し、ゆっくり考えて作るときに使う。

| --- | --- | --- |
| Ctrl+L | 行を `- [ ]` にする。もう一度押すと完了になる | Obsidian 標準のコマンド「Toggle checkbox status」。Windows では最初から Ctrl+L に割り当て済み |
| Ctrl+K | 選んだ語を `[[ ]]` でつなぎ、ノードがなければその場で作る。`[[ ]]` の中で押すと、まだファイルのないリンクをノードにする。何も選ばずに押すと検索窓が出て、名前と別名でノードを探せる(候補にない名前ならそのまま作る) | Templater のスクリプト(`link_node.js`)。同じ名前か別名(aliases)のノードがあれば、新しく作らずにそれにつなぐ(90_共有 の他の人のノードも探す)。候補が2つ以上のときだけ選ぶ。表示名は選んだ文字のまま。作ったノートは開かない |
| Ctrl+S | ふつうに保存し、このノートにまだファイルのない `[[ ]]` があれば、その名前を右上に出す。ファイルは作らない | Templater のスクリプト(`save_check.js`)。標準の保存コマンドを呼ぶので、Linter の保存時の整形も動く |

- `[[ ]]` を打つだけでも構わない。ただし、ファイルは自動では作らない。`[[ ]]` はノードとは限らず、イシュー・タスク・目的・ただのメモのこともあるため(Yu 2026-10-24)。作るときは `[[ ]]` の中にカーソルを置き、種類に合わせて Ctrl+K(ノード)・Ctrl+I(イシュー)・Ctrl+T(タスク)・Ctrl+H(仮説)・Ctrl+U(ソリューション)を押す。作り忘れは Ctrl+S で保存したときに右上に出る。
- キーは押しやすい Ctrl にそろえる(Yu 2026-10-24)。Obsidian 標準の Ctrl+K(Markdown リンク)・Ctrl+I(斜体)・Ctrl+T(新しいタブ)・Ctrl+H(検索と置換)は外して使う。斜体は `*文字*`、タブは Ctrl+クリック、置換はコマンドパレットで代わりができる。Ctrl+G(グラフ表示)は K-Plex に置き換える。グラフはコマンドパレットや左のリボンから開ける。
- キーを覚えなくても使えるよう、同じ動きを本文の右クリックのメニューにも入れる(Commander、Yu 2026-10-24)。`[[ ]]` の上で右クリックするとカーソルがそこに移るので、そのリンクが対象になる。新しいキーを作ったら、メニューにも足す。
- キーは配布する設定(`_仕組み/設定/` の .obsidian)のホットキーに入れておく。Ctrl+L を何もない行で押したときに `- [ ]` ができるかは導入時に確かめ、できなければ同じ動きを Templater で作る。
- スクリプトは `_仕組み/templates/_scripts/` に置き、書く前に Yu が確認する。

## 図とパワーポイント

検討には図をたくさん使う。図を作る手間を最小にし、パワーポイント(パワポ)より便利にして、このシステムでまとめてもらう(Yu 2026-10-24)。

**どのノートにも図をつける**

- Ctrl+D を押すと、そのノートの図(`_仕組み/attachments/<id>/図.excalidraw.md`)を作って横に開き、カーソルの位置に1枚目のフレームの引用 `![[_仕組み/attachments/<id>/図.excalidraw#^clippedframe=frame1]]` を入れる(Yu 2026-10-24)。`#^frame=` は編集中の表示で絵にならず中身の文字が出るので、枠の中だけを切り出す `#^clippedframe=` を使う(Yu が PC で確かめた)。2回目からは同じ図を開くだけ。空の図ファイルが増えないよう、図は初めて押したときに作る。2枚目からは、Excalidraw でフレームを選んで「フレームへのリンクをコピー」で、説明の好きな位置に貼る。貼ったリンクの `#^frame=` は `#^clippedframe=` に書き換える。
- 図のひな形(`_仕組み/templates/図.excalidraw.md`)には 16:9 の枠(Excalidraw のフレーム)を1つ置く。枠1つを「1枚」とし、足りなければ枠を足す。
- ナレッジとソリューションでは、Ctrl+D が種類に合ったひな形を使う(Yu 2026-10-25)。ナレッジは `ナレッジ図.excalidraw.md`(1枚目に実施前・やったこと・実施後、2枚目にトレードオフ曲線)、ソリューションは `トレードオフ曲線.excalidraw.md`。枠の名前と同じ見出し(「ナレッジ図」「トレードオフ曲線」、ソリューションでは「どの条件ならこの案が勝つか」)がノートにあれば、引用はその見出しの説明の行の下に入る。見出しがなければ1枚目だけカーソルの位置に入れ、2枚目は入れない。ひな形がない vault(機密)では、ふつうの図のひな形を使う。キーは増えない。
- フレームの引用は Obsidian の中だけで図として見え、拡大やリンクもその場で使える。そのため `![[ ]]` の埋め込みを図にだけ例外として使う。メモ帳や GitHub では引用の行が文字で見える。フレームごとの SVG を `_仕組み/attachments/<id>/図_<フレーム名>.svg` に書き出す仕組みは後で作る(GitHub の issue に記録)。形が決まっているので、道具を移るときは引用の行を SVG への普通の画像リンクに一括で置き換えられる。

**パワポの良さを、どう置き換えるか**

| パワポの良さ | このシステムでのやり方 |
| --- | --- |
| 1枚という区切りがあり、理解に合わせた粒度にできる | フレーム1つが1枚。1ノートに1テーマ、図は1〜数枚 |
| 画像・グラフ・動画を見た目どおりに貼れる | Excalidraw に Ctrl+V で貼る。Excel のグラフはコピーして貼れば画像になる。動画は vault に置いてリンクし、図には代表の1コマを置く |
| 文字の見栄えを変えられる | Excalidraw でフォント・大きさ・色を変える。図の中の名前も `[[ ]]` でノードにつなげられる |
| 人に配りやすい | フレームを1枚ずつ PDF か PNG に書き出す(Excalidraw の書き出し機能。導入時に確かめる)。パワポで配りたいときは、同期プログラムがフレームを1枚1スライドにした pptx を作る(配布用。直すのは図の側) |

**パワポより便利になる点**

- 図の中の名前がノードにつながるので、「ヒケ」で探すと過去の図がすべて出る。
- 同じ図を週報・DR 資料・ナレッジで使い回せる。図を直せば全部に反映される。
- 「最新版_改2.pptx」のような版の混乱がない。最新は常に1つ。
- 過去の図も「類似・参考ナレッジ」に出るので、着手前に目に入る。

**今あるパワポを取り込む**

- pptx を `00_inbox/` に置くか、ノートにドラッグすると、同期プログラムが取り込む(PowerPoint の入った PC で動かす)。
    - 1スライドずつ PNG にして、スライドの文字と一緒に1つのノートにする(1スライドが1つの見出し)。
    - 元の pptx は重いデータの置き場所へ移し、ノートからリンクする。
- 取り込むと、スライドの文字で検索でき、画像を Excalidraw に貼って書き込める。
- パワポで作り続けたい人は、pptx をそのまま添付してもよい。取り込めば検索にかかる。

## ナレッジ図の描き方(Excalidraw)

impact 大のイシューに関わるタスクを実行したら、リスクがどう変わったかを Excalidraw で画面1枚に描く。スクロールせずに全体が見える大きさに収める。中・小は描かず、タスクの「リスクはどう変わったか」欄に書く(中は写真と数値を3行、小は1行)。

```
┌─ 実施前 ─────────┐   ┌─ やったこと ────────┐   ┌─ 実施後 ─────────┐
│ イシュー名          │   │ タスク名              │   │ リスク: 出荷 → 小   │
│ リスク: 出荷        │ → │ 条件・試したこと    │ → │ 数値・写真          │
│ 現象の写真・数値    │   │ (例: 保圧 60→80MPa) │   │ わかったこと・次の手 │
└────────────────────┘   └──────────────────────┘   └────────────────────┘
```

- 左に実施前のリスク、真ん中にやったこと、右に実施後のリスクとわかったことを置く。リスクの大きさはイシューの impact(方針 / 絞込 / 出荷 / 中 / 小)で書く。
- 描いたらイシューの status・impact・priority を更新し、わかったことをノードに書き戻す。
- ツール非依存のため、Excalidraw の設定で「SVG を自動書き出し」をオンにし、「図のデータを圧縮しない」設定にする。プラグインがなくても SVG で見られ、図のデータは excalidraw.com で開ける。
- タスクの「リスクはどう変わったか」欄には SVG を通常の画像リンクで貼る。

## トレードオフ曲線の描き方

セットベース開発で候補を比べ、DR で絞るための図(Targeted Convergence 社のトレードオフ曲線の考え方を取り入れた。Yu 2026-10-25)。ナレッジの図の2枚目と、ソリューションの図(Ctrl+D)に、最初から次の6つが置いてある。描く人は軸の名前を書き換え、点と線を動かすだけ。

| 置いてあるもの | 意味 |
| --- | --- |
| 縦軸 | 比べる性能(組み立て値)と単位 |
| 横軸 | 振って試す値(独立値)と単位 |
| 目標の線(赤の破線) | 仮性能。目標が変わったらこの線だけ動かす |
| 案ごとの線と点 | 点は試した結果、線はそのつながり。案ごとに色を変える |
| 灰色の範囲 | まだ試していない範囲。ここを試すのが次のタスク |
| 読み方・描き方 | 図の右に書いてある。条件(材料・温度など)もここに書く |

- 線が目標を満たす範囲が、その案の勝つ条件。どの点も目標に届かない案は、DR で不採用の根拠になる。
- 1枚の図に一組の候補の線を並べる。案ごとに別の図にしない。
- 不採用になった案の線も消さない。目標が変われば勝つことがある。

## 知見の確認と完了

重要度の高い知見は複数人で内容を確認してから完了にし、すぐ次の優先順位の高いイシューに移る。重要度は、そのタスクが減らすイシューの impact で決める。

| イシューの impact | 確認する人 | 完了の条件 |
| --- | --- | --- |
| 大 | 書いた人＋ほか1人以上 | 全員が確認し、`reviewed_by` に名前を残す |
| 中・小 | 書いた人 | 本人が読み返して完了 |

1. イシューのリスクがどう変わったかを残し(impact 大はナレッジ図とナレッジ、中・小は「リスクはどう変わったか」欄)、わかったことをノードに書き戻す。
2. タスクの status を「確認待ち」にし、`review_request` に確認を頼む人を書いて(例: `review_request: [佐藤]`)、確認者に知らせる。確認者は `00_タスク一覧.base` の「確認待ち(確認する人ごと)」ビューで自分宛てを見る(Yu 2026-10-24)。
3. 確認者はナレッジ図・数値・ノードへの書き戻しを見て、問題がなければ `reviewed_by` に名前を足す。直しが必要なら本文に書かず本人に伝える。
4. 確認がそろったら、タスクを「完了」、イシューの status・impact・priority を更新し、ノードの maturity を「検証済み」にする。
5. 共有 vault へ反映し、イシュー一覧で次に priority の高いイシューへ移る。

- 当面は2人なので、impact 大はもう一人が必ず見る。1人2役のときは一晩おいて読み返し、もう一人が次に来たときに確認する。
- 確認待ちで手を止めない。確認を依頼したら、確認を待たず次のイシューに着手してよい。

## 日々の備忘録とデイリーノート

「5分後にやる」ような細かい仕事は、どのノートにでもチェックボックスで書き、Tasks で今日のデイリーノートに集める。デイリーノートは Day Planner でタイムライン表示し、今やっている仕事と次の仕事をすぐ見られるようにする。

| 使い分け | 書く場所 | 例 |
| --- | --- | --- |
| 思いついたこと・メモ | 今日のデイリーノートの「メモ」、または今やっている仕事のノート | `- 肉厚の角に [[ヒケ]] が出やすい?` |
| 備忘録・雑多な仕事 | どこでも(チェックボックス、Ctrl+L) | `- [ ] 仕入先に納期を電話で確認 📅 2026-10-24` |
| 半日以上かかり、リスクを減らす仕事 | 04_タスク(ノート) | 保圧を変えて試作する.md |
| 1日の時間割 | 今日のデイリーノート | `- [ ] 10:00 - 12:00 [[保圧を変えて試作する]]` |

**デイリーノートの形(00_日誌/デイリー/2026-10-24.md、個人 vault のみ)**

````markdown
# 2026-10-24

## タイムライン
- [x] 09:00 - 09:30 朝会
- [ ] 09:30 - 12:00 [[保圧を変えて試作する]]
- [ ] 13:00 - 14:00 仕入先に納期を電話で確認

## 今日までの備忘録
Tasks が自動で集める
```tasks
not done
due before tomorrow
```

## メモ
やることは行で Ctrl+L を押して - [ ] に。📅 期日をつけるとその日のデイリーに出る
````

- Day Planner のタイムラインでブロックの端をドラッグすると、時刻(例: 12:00 → 13:00)がその場で書き換わる。今の仕事が延びそうなら、これですぐ延長し、後ろの予定もずらす。
- メモは inbox にファイルを作らず、今日のデイリーノートの「メモ」に書く。ファイルは1日1つなので、仕事を並列で進めても増えない。デイリーノートが日付つきの inbox になる。あとで Ctrl+K / I / T を押せば、その行がその場でノード・イシュー・タスクになる。
- 仕事中のメモは、その仕事のノートに直接書く。ショートカットで作ったノートには parent が自動で入るので、inbox を通らない。
- 5分後にやるようなことは、今開いているノートに `- [ ] 内容` とだけ書けばよい(Ctrl+L)。期日(📅)をつければその日のデイリーノートに出てくる。
- デイリーノートは個人の作業用で、知見ではない。共有 vault には出さず、必要な内容だけノードやタスクに移す。

**コアプラグイン非依存との両立**

- デイリーノートの作成はコアの「デイリーノート」ではなく Periodic Notes(MIT)で行う。中身は日付名の普通の Markdown なので、手で作っても同じになる。
- 時間割は `- [ ] 09:30 - 12:00 内容` という普通のチェックリストなので、Day Planner がなくても読める。
- Tasks の期日(📅 2026-10-24)もただの文字。`tasks` の集計ブロックだけはプラグインがないと動かないため、デイリーノートだけで使い、知見ノートには書かない。
- Day Planner がデイリーノートの場所を読めるように、Periodic Notes 側で保存先(00_日誌/デイリー)と日付形式(YYYY-MM-DD)を設定する。導入時にコアをオフにした状態で動くか確かめる。

## インポートと共有の手順

知見は「個人 vault で書く → 知見同期プログラムが共有 vault へ集める → 関係する人の個人 vault へ配る」の一方向で流す。手でのコピーは、プログラムが止まっているときの予備の手順にする。

**A. 個人 vault で書く**

- メモは今日のデイリーノートか、今やっている仕事のノートに書く。00_inbox/ は行き先のわからないファイル(写真・pptx など)だけに使う。ノートの上にドラッグすれば、そのノートの添付になる。
- ショートカット(Ctrl+K / I / T)か QuickAdd で、目的・ノード・イシュー・タスク・ナレッジなどを作る。出てきた単語には \[\[ \]\] をつける。
- visibility は書かなければチームとして共有される。共有したくないものだけ `visibility: 個人` と書く。ナレッジ(impact 大だけ)は必須5項目を埋め、確認を頼む。

**B. 共有へ出す(同期プログラムが行う)**

- 条件を満たすノートを、数分以内に共有 vault のプロジェクトごとの場所へコピーする(「共有の自動化」)。
- 機密フォルダのものは、どこへも出さない。
- 出せなかったノートと理由は _仕組み/同期レポート.md に出るので、金曜の定例で直す。

**C. 他の人の知見を受け取る(同期プログラムが行う)**

- 参加しているプロジェクトと「共通」のノートが、個人 vault の 90_共有/ に配られる。ファイル名が同じなので、自分のノートの \[\[ \]\] がそのままつながる。
- 90_共有/ のノートは編集しない。書き足したいときは自分のフォルダへ移して編集すると、次の同期で共有へ戻る。
- 配られていないプロジェクトのノートを読むだけなら、共有 vault を Obsidian で直接開く。

**D. プログラムが止まっているとき(手の予備手順)**

- 共有 vault に同じ id のファイルがないか検索し、なければ同じ種類のフォルダへコピーする。添付もコピーする。
- あれば上書きせず、「競合の扱い」の手順で統合する。
- id のないノートは手では出さない。機密フォルダのものは、手でもコピーしない。

当面(2人・1人2役)の役割: 書く人と確認する人を分ける。一人で兼ねるときは、翌日に自分で読み返してから共有する。

**E. 同期プログラムができるまでの仮運用**

同期プログラムを各 PC で動かすまでは(いまは手で起動する bat。常駐と exe はまだ)、次のやり方で始める。待たずに使い始められるようにするため。

- 2人とも共有 vault(開発ノート_共有/)を Obsidian で直接開いて書く。個人 vault はデイリーノートと書きかけだけに使う。
- 新しいノートは QuickAdd で共有 vault の <プロジェクト名>/ の種類ごとのフォルダ(ノードは 共通/02_ノード/)に作る。id はテンプレートが入れる。テンプレートを使わずに作ったノートは名前だけでよく、同期プログラムが動き始めたらあとから id をつける。
- 同じノートを2人が同時に開いて書かない。Box が競合した複製を作ったら、金曜の定例でまとめる。
- 顧客から受け取った資料と事実は、最初から機密フォルダに置く。
- 週報(管理者向け)は手で作らず、プロジェクトのノートの見込み3行を管理者に渡す。

## 競合の扱い

競合は同期プログラムが見つけて、上書きせずに残す。人がその都度、共有側を正として統合する。

| 競合の種類 | 起き方 | 対応 |
| --- | --- | --- |
| 両側で更新 | 前回の同期のあと、個人側と共有側の両方が変わった | プログラムが共有側の隣に <名前>*競合*<名前>_<日付>.md を置き、レポートに出す。見比べて元のファイルにまとめ、競合ファイルは 99_archive へ |
| Box の同時編集 | Box Drive が競合した複製を作る | 同上。プログラムが見つけてレポートに出す |
| 内容が食い違う | 別の人が違う条件・数値を書いた | 両方を条件つきで並べて書く(例: 材料ロット、設備の違い)。決着しなければ本文先頭に「要確認」 |
| 重複テーマ | 違う id・違う名前で同じもの | 古い方に統合し、別名を aliases に足す。もう一方は 99_archive へ移して統合先を書く |
| id の衝突 | 別のノートに同じ id がついた | プログラムが自動で振り直す(「ノートの id」)。レポートを見るだけ |

- 共有側は削除しない。消す代わりに 99_archive へ移す。
- 金曜の定例で、同期レポートの「対応が必要」を片付ける。

## 共有の自動化(常駐プログラム)

共有への出し入れは、Obsidian の外で動く常駐プログラム(仮称: 知見同期プログラム)が行う。各自のノートをプロジェクトごとに共有 vault へ集め、そのプロジェクトのメンバーの個人 vault へ配り直す。詳しい要件は「知見同期プログラム 要件書」(https://claude.ai/artifact/3XvGmb5RSbsfqb6c5XqWgg)にまとめ、正本は `docs/00_同期プログラム要件.md`。id 付け・リンク直し・集約・配布・競合・重い添付・自動入力(priority・previous・generation)・類似・参考ナレッジ・週報はできている。exe 化・常駐(タスクトレイ)・pptx の取り込みと書き出し(F-41・42)・仕組みの更新(F-46)はまだ。

**動き方**

各メンバーの PC で1つずつ動かし、自分の個人 vault と共有フォルダ(クラウド同期済みのローカルフォルダ)の間だけを扱う。他人の個人フォルダには触らない。

- 集約: 個人 vault の更新を検知し、条件を満たすファイルを共有 vault のプロジェクトごとの場所へコピーする。
- 再配布: 共有側の更新を検知し、自分が参加しているプロジェクトと「共通」のファイルを、個人 vault の 90_共有/ へコピーする。
- 今すぐ共有へ: ふだんは数分ごとに同期するが、急ぐときは Obsidian で Ctrl+Shift+S(ノートの上の帯のボタン、右クリックのメニューでもよい)を押すと、すぐ1回同期する(Yu 2026-10-25)。
- 機密フォルダ: 中身をどこへもコピーしない。機密 vault の中で id をつけるだけ。
- 報告: 集めなかったファイルと競合を、個人 vault の _仕組み/同期レポート.md に理由つきで書く。

**共有フォルダでの振り分け**

| ファイル | 置き場所 | 決め方 |
| --- | --- | --- |
| ノード | 共通/02_ノード/ | プロジェクトを問わず使い回すため常に共通 |
| 機密の窓口 | 共通/機密の窓口/ | 常に共通 |
| イシュー | <プロジェクト>/03_イシュー/ | project が1つならそのプロジェクト、複数または「共通」なら 共通/03_イシュー/ |
| 目的 | <プロジェクト>/01_目的/ | 目的にも project を書く |
| 価値の仮説・ソリューション | 目的と同じ <プロジェクト>/01_目的/ | parent をたどった先の目的の project を使う |
| タスク・議事録・実験・試作記録・ナレッジ・ナレッジ図 | 親と同じプロジェクト | parent をたどり、イシューならその project、目的なら目的の project を使う |
| 週報 | 00_週報/<名前>/ | visibility が チーム 以上のもの |
| 添付 | 共有 vault の一番上の _仕組み/attachments/<id>/ | ノートと同じ id のフォルダごとコピーする。名前は変えない |

**集める条件**

- visibility が「個人」のものは集めない。
- 機密フォルダの中のファイルへのリンクや画像があるノートは集めず、レポートで知らせる。窓口ノートの本文・属性欄と、ほかのノートの secret_refs に、機密フォルダの名前か事実ノートの名前が入っていれば集めず、レポートで知らせる。secret_refs が窓口へのリンクでなければ(前の書き方の id など)、集めたうえでレポートで直すよう知らせる。
- 機密フォルダの中に type が ナレッジ・イシュー・タスクのノートがあれば、レポートで知らせる(知見は機密に置かない決まりのため)。
- ナレッジで必須5項目がそろっていないもの、ノードで author が空のもの、impact 大で確認が済んでいないものは集めず、レポートに出す。visibility が空のものはチームとして扱う。
- 00_inbox と 00_日誌/デイリー は対象外。inbox に1週間以上残っているファイルは、件数と名前を同期レポートに出す(金曜の定例で片付ける)。

**競合の扱い**

- プログラムは前回同期したときの内容(ハッシュ)を覚えておき、個人側だけが変わったら集約、共有側だけが変わったら再配布する。
- 両方が変わっていたら上書きしない。共有側の隣に `<名前>_競合_<名前>_<日付>.md` を置き、レポートに出す。人が「競合の扱い」の手順で統合する。
- 削除はしない。99_archive への移動だけを共有へ反映する。

**個人 vault への配布のルール**

- 配布先は 90_共有/ だけ。ここはプログラムが上書きするので、人は編集しない。
- 自分のフォルダ(01〜05)に同じ名前のファイルがあれば、そのファイルは配布しない(ファイル名は vault 内で一意の規則を守るため)。内容が違えばレポートに出す。
- 他人のノートに書き足したいときは、90_共有/ から自分のフォルダへ移して編集する。次の同期で集約される。

**前提と作り**

- Obsidian に依存しない。ファイルと属性欄(YAML)だけを読む。
- 設定は YAML ファイル(個人・共有・機密フォルダ・開発データ・報告の場所、同期間隔。「フォルダ構成」の例)。参加プロジェクトは設定に書かず、プロジェクトのノートの members から読む(人が増えても1か所直せば済む)。機密フォルダは、その PC で開ける(Box の権限がある)ものだけを書く。
- 数分おきに確認する。PC 起動時に自動で立ち上がる(Windows のタスクスケジューラでサインイン時に起動)。
- 実際には書き込まず結果だけ表示する「試し運転」モードを持つ。
- プログラムが動かなくても、「インポートと共有の手順」D の手の予備手順で運用できる。

**同期プログラムが止まっても回るようにする**

同期プログラムは便利にするための道具で、知見そのものはプログラムなしで読み書きできる。作った人がいなくなっても、プログラムが何か月止まっても、知見が消えたり読めなくなったりしないことを条件にする。

| 止まったとき | どうなるか | 人がやること |
| --- | --- | --- |
| id 付け | 新しいノートに id がつかない。\[\[水\]\] のような名前だけのリンクのままになる | そのまま書き続けてよい。再開したらプログラムがあとから id をつける |
| 集約・再配布 | 共有 vault と 90_共有/ が更新されない | 他の人の知見は共有 vault を直接開いて読む。急ぎで共有したいものだけ「インポートと共有の手順」D で手で出す |
| 重い添付の移動 | 重い添付が _仕組み/attachments/<id>/ にたまる | 何もしなくてよい。再開後に移る。Box の容量が心配なら手で 開発データ/ へ移してリンクを直す |
| 管理者向け週報 | 作られない | プロジェクトのノート(見込みの3行)をそのまま管理者に渡す |
| priority・generation などの自動入力 | 空のままになる | 空でよい。必要なら表を見て手で書く |

- プログラムの仕事を「核」と「おまけ」に分ける。核は id 付け・集約・再配布・競合の検出・添付の移動・同期レポート。previous と generation の補完、priority の計算、管理者向け週報などはおまけで、壊れても核は止まらない。
- プログラムだけが持つデータを作らない。前回同期の記録は個人 vault の `_仕組み/記録/` にあるが、消えても個人 vault と共有 vault を見比べて作り直せる。作り直すときは上書きせず、違うものは競合として扱う。
- 保守者がいなくなっても直せるように、共有 vault の `_仕組み/tools/同期プログラム/` に次を置く: 保守手順書(作り方・配り方・よくある障害)、ソースコードの控え(Git のバンドル)、テスト用 vault。テストが通れば直してよい、と言える状態にする。
- 年1回、同期プログラムを止めたまま1週間運用する「停止訓練」をする。手の予備手順で回らないところがあれば仕様書を直す。

## 重い添付ファイルの置き場所

Obsidian を軽く保つため、vault の中には画像と軽い動画だけを置き、それ以外の添付は vault の外の「開発データ」フォルダへ移して、ノートにはリンクだけを残す。人がやるのは、いつもどおりノートにドラッグ&ドロップするだけ。移動とリンクの書き換えは知見同期プログラムが行う。

| ファイル | 置き場所 |
| --- | --- |
| 画像(png / jpg / gif / webp / svg) | vault 内の _仕組み/attachments/<id>/ |
| PDF(サイズに関係なく) | vault 内の _仕組み/attachments/<id>/ |
| 動画(mp4 / webm / mov)20MB 未満 | vault 内の _仕組み/attachments/<id>/ |
| 動画 20MB 以上と、それ以外のすべて(Excel、CAD、測定データ、zip など) | vault 外の 開発データ/ |

**流れ**

1. ノートにファイルをドロップするか貼り付ける。Custom Attachment Location が `_仕組み/attachments/<id>/` に元の名前でコピーしてリンクを入れる。
2. 同期プログラムが数秒以内にこれを見つけ、画像・PDF・20MB 未満の動画以外なら 開発データ/ へ移す。
3. ノートのリンクを、移した先を開く `file:///` リンクに書き換える。クリックすると Excel や CAD など、そのファイルに合うアプリで開く。

**開発データフォルダの構成(クラウド上、vault の外)**

```
開発データ/
├── 共通/<id>/
├── <プロジェクト名>/<id>/       例: 樹脂カバー量産/0RDGPG001/成形条件.xlsx
└── _個人/<名前>/<id>/          まだ共有していないノートの添付
```

- プロジェクトはノートの project(タスク・ナレッジなどは parent をたどったイシューや目的)から決める。ノートが共有されたら、添付も _個人/ からプロジェクトのフォルダへ移す。
- 機密フォルダの添付は、重いものもその機密フォルダの `_仕組み/attachments/<id>/` に置き、vault の外へ移さない。権限の違う場所へ出さないため。
- フォルダがノートの id ごとなので、別のノートの添付と名前がぶつからない。同じノートで同じ名前のファイルがあるときだけ、上書きせず末尾に _2 などをつける。

**リンクの書き方(人によって PC 上の場所が違う問題)**

`file:///` は PC ごとの絶対パスなので、そのまま共有すると他の人の PC では開けない。そこで共有 vault では「開発データ/ からの相対パス」で保存し、個人 vault に配るときだけその人の PC の `file:///` に直す。

| 場所 | 書き方 |
| --- | --- |
| 共有 vault | `[成形条件.xlsx](開発データ/樹脂カバー量産/0RDGPG001/成形条件.xlsx)` |
| 個人 vault | `[成形条件.xlsx](file:///C:/Users/yu/Box/開発データ/樹脂カバー量産/0RDGPG001/成形条件.xlsx)` |

- 開発データ/ が自分の PC のどこにあるかは、同期プログラムの設定ファイルに各自が書く。
- どちらも普通の Markdown リンクなので、プラグインには依存しない。

**安全のための決まり**

- ノートが数秒間編集されていないことを確かめてから、リンクの行だけを書き換える(入力中の文字を消さないため)。
- 移動と書き換えはすべて同期レポートに記録し、元に戻せるようにする。

**検討したほかの方法**

- Obsidian 標準: Ctrl(Mac は Option)を押しながらドロップすると、コピーせず `file:///` リンクを入れられる([公式ヘルプ](https://obsidian.md/help/drag-and-drop))。ただしファイルは元の場所(ダウンロードフォルダなど)に残り、パスもその人の PC 専用になる。そのため採用しない。
- [External File Embed and Link](https://github.com/oylbin/obsidian-external-file-embed-and-link): vault 外へのリンクを作れるが、独自の書式になるためツール非依存の方針に合わない。ライセンスも未確認。
- ドロップしたファイルを種類ごとに vault 外へ移してくれる MIT のプラグインは、今回の調査では見つからなかった。

## 管理者向けの週報

管理者は Obsidian を使わない。知見同期プログラムが毎週月曜の朝に、プロジェクトごとの週報を HTML 1つで作り、Box 直下の `開発ノート_報告/<プロジェクト名>/<年-週>.html` に置く。Markdown と Excel に分けるのをやめ、ブラウザで開く1ファイルにまとめた(Yu 2026-10-25)。報告フォルダの直下の `週報の一覧.html` から、全プロジェクトの最新の週報と前の週を開ける。中身はノートの属性欄から自動で集めるので、現場が書き足すのは3行だけ。

**管理者が見たい4点と、その出し方**

| 見たいこと | 週報に出すもの | 元にする属性 |
| --- | --- | --- |
| 目的に沿わない開発をしていないか | 価値の仮説につながっていないタスク・イシュー・実験の一覧(parent をたどっても仮説に着かないもの)と、その件数。外れた仮説につながったまま動いているものも出す(上の仮説が外れたものも含む)。反論(challenger)がついたのに検証中のままの仮説と、そのすぐ下の仮説・イシューの数 | parent、仮説の status、challenger |
| 他のプロジェクトと似たことをしていないか | 同じノードを friend に持つイシューやタスクが、別のプロジェクトにもある組み合わせ。似た名前(aliases)の重複候補も出す | friend、aliases、project |
| 開発に行き詰まりがないか | 前回の DR から resolution が上がらず、その間に対策タスクが2件以上完了している impact 大のイシュー(動いているのに前進しないもの)。対策が続いているのに parts の末端が組み立て値のままのイシュー(原因を分解しないまま試している印)。期限を2回以上延ばしたタスク | resolution、DR の議事録、タスクの status、parts と value_kind、due とノート履歴の最初の due |
| 人やリソースは足りているか | 担当者ごとの進行中タスク数・待ちの数・期限切れ数・確認待ちの数と、確認を頼まれた数(review_request)。マイルストーンの計画日と見込み日のずれ | owner、due、status、review_request、reviewed_by、プロジェクトの節目の表 |

作業時間はひとまず管理しない。PC を使わない作業(試作・試験・現場対応)が多く、正確に記録できないため。人・リソースは、担当者ごとのタスク数・期限切れ・確認待ちとマイルストーンのずれだけで見る。Day Planner のタイムラインは本人の段取り用で、集計には使わない。

**週報の形**

- 1枚目: プロジェクトの見込み(〇 予定どおり / △ 遅れそう / × 間に合わない)、出荷準備度、残っている候補の数の推移(下)、マイルストーンの計画日と見込み日、管理者への判断依頼。
- 2枚目以降: 上の4点の一覧。該当がなければ「なし」と書く。
- **候補の数の推移**: 開発の前半は出荷準備度がほぼ 0% のまま動かず、進んでいないように見える。そこで、一組の候補(同じ parent を持つソリューション。ノードの parts に候補を並べた場合も含む)のうち、不採用・中止でないものの数を週ごとに出す(例: 「センサー 3→1、無線 3→2」)。絞れていく様子で前半の進み具合を表す。
- 機密フォルダの中身は出さない。secret_refs の件数だけを出す(週報は権限のない人も見るため)。
- **載せる節を選ぶ**(Yu 2026-10-25): 週報を作る人が、チーム設定(`_仕組み/同期設定.yaml`)の `report_sections` で節ごとに載せる・外すを決める。見込みはいつも載せる。「他のプロジェクトと同じノードを使うもの」は既定で「自動」にし、進めているプロジェクトが1つのうちは出さない。1回だけ変えて作り直すときは `python -m notesync weekly --hide 同じノード` のように指定する。
- 表は見出しを押すと並べ替えられ、行の多い表には絞り込み欄がつく(Excel の代わり)。目次に節ごとの件数を出し、注意の要る節(目的に沿わない・反論・同じノード・行き詰まり)に件数があれば色をつける。外のファイルやネットを読まないので、Box Drive からダブルクリックで開ける。印刷もできる。

**現場が書くのは3行だけ**: プロジェクトのノートの outlook(〇△×)、その理由1行、管理者に判断してほしいこと1行。金曜の定例の最後に更新する。更新を忘れないよう、金曜の朝に同期レポートとデイリーノートで知らせる。2週間更新されていなければ週報に「見込み未更新」と出す。

**足す属性**

- プロジェクト: 本文の「期間・主な節目」の表(節目・計画日・見込み日)、outlook、outlook_reason、request_to_manager
- タスク: milestone(どのマイルストーンのためか)。使うときだけ書く。ガントの始点は id の作成日時を使う
- プログラムが自動で記録するもの: 最初の期限(due を変えても残る)と完了した日。ノートには書かず `_仕組み/記録/ノート履歴/<名前>.csv` に残す

## 現場の入力を減らす仕組み

現場の人は IT に詳しくなく、Obsidian も初めての想定にする。属性欄(YAML)を手で書かなくても回るようにする。

- QuickAdd の質問に答えるだけでノートができる。例: イシューなら「名前は？」「どの目的を邪魔する？(一覧から選ぶ)」「インパクトは？(答えで方向が変わる？ 候補が減る？ 解けないと出荷できない？ を順に はい / いいえ)」「すぐできる？」の4問。ただし、この質問はまだ作っていない(v0.41 時点)。いまの QuickAdd のボタンは質問せず、impact は既定の「出荷」で作るので、金曜の定例で直す。急ぐときは質問なしのショートカット(「ショートカットキー」)で作る。属性欄は Templater が書く。
- priority は impact と speed から同期プログラムが自動で計算して書く(人は書かない)。
- 必須5項目はナレッジだけで、人が書くのは risk_reduction と usefulness の2つ。ノードは人が毎回書く属性がない。属性は使うときだけ書く(「標準テンプレート」の表)。
- 共有されなかった理由は、同期レポートだけでなく今日のデイリーノートの先頭にも「共有されていないノート」として出す。
- 設定済みの .obsidian(プラグイン・ホットキー・QuickAdd のボタン)を共有の `_仕組み/設定/` に置き、新しい人は最初にそれをコピーするだけで始められる。
- 段階導入: 最初の1か月は「目的・イシュー・タスク・デイリー」だけを使い、ナレッジ・ナレッジ図・K-Plex は慣れてから足す。
- 現場向けの手順は `00_現場向け1枚.md`(A4 1枚、PDF にも書き出す)にまとめ、共有 vault の直下に置く。「メモを書く」「イシューを作る」「タスクを終える」の3つだけを説明する。
- **着手前に過去の知見を見せる**: イシューやタスクを作ると、同期プログラムが次の同期で、同じノードを friend に持つ他のプロジェクトのイシューと、usefulness が A・B のナレッジを、ノートの末尾の「類似・参考ナレッジ」に足す(F-36。作って7日以内のものに5件ずつまで)。作った瞬間には入らない。同じ試作を繰り返さないための入り口にする。

## 週の定例(金曜35分)

まとめ役の定例は金曜の35分の1本にまとめる。順番も決めておく。

| 順 | やること | 目安 |
| --- | --- | --- |
| 1 | 同期レポートの「対応が必要」(共有されなかったノート、競合、「やめますか」の候補)を片付ける | 10分 |
| 2 | impact が「未判定」のイシューの impact を決める。priority 1・2 のイシューの speed・status を見直す。value_kind が空の値のノードを分類する | 15分 |
| 3 | プロジェクトのノートの outlook の3行を更新する(月曜の管理者向け週報に載る) | 5分 |
| 4 | 各自の inbox とデイリーノートのメモで、1週間以上残っているものを、ノートにつなぐか捨てる | 5分 |

- 月末の金曜だけ、15分足して仕組みの振り返りをする(「リーン開発との関係」)。
- 解像度の段階は定例では変えず、DR で決める。
- 年1回の停止訓練(「同期プログラムが止まっても回るようにする」)は、月末の振り返りの回で日程を決める。

## 計算・検証プログラムの管理

計算や検証のプログラムは、知見ノートと分けて Git で履歴を残す。GitHub は使っても使わなくてもよい。どちらでも、ノートの書き方とフォルダは変わらない。

| 置くもの | 場所 |
| --- | --- |
| プログラム(.py など) | Git リポジトリ「計算・検証」。各自の PC の Box の外(例: C:\\dev\\計算・検証)に置く |
| リポジトリの控え・共有 | GitHub を使うとき: 非公開リポジトリへ push。使わないとき: Box の 開発データ/_コード/ に Git のバンドル(履歴ごと固めた1ファイル)を置き、他の人はそこから pull する |
| 入力データ・出力データ | 開発データ/<プロジェクト>/<id>/ |
| グラフ・結論 | 実験・試作記録やナレッジに PNG で貼り、数値を書く |
| ファームウェア | 製品ごとの Git リポジトリ(GitHub は任意)。ノートの fw_ver にタグかコミットを書く |
| 回路図・基板データ | `開発データ/<プロジェクト>/設計/<版>/`(例: 設計/B2/)。ソリューションから版のフォルダへリンクする。見るための PDF の書き出しは、そのソリューションの `_仕組み/attachments/<id>/` に置いて Obsidian で見られるようにする |
| 知見同期プログラム | 別のリポジトリにする |

- リポジトリの中身を Box Drive の中に直接置かない。同期中に .git の中身が壊れることがあるため。バンドルは1ファイルなので Box に置いてよい。
- リポジトリは1つにし、中を <プロジェクト名>/ と 共通/(単位換算、材料データの読み込みなど使い回すもの)に分ける。
- 各スクリプトの先頭に、元のノートの id と目的を1行書く(例: # 0RDGPG001 保圧を変えて試作する: ヒケ深さの集計)。
- 実験・試作記録とナレッジの属性欄に code: 計算・検証@<コミット番号>/<ファイル> を書き、どの版のプログラムで出した数値かをたどれるようにする。GitHub の URL ではなくコミット番号で書くので、GitHub があってもなくても同じ書き方になる。
- 段階3(原理)の因果モデルもここに置き、ノードから code: でつなぐ。
- 機密フォルダのデータはリポジトリに入れない。読み込み先は設定で渡す。

## 仕組みの正本と配布

仕組み(テンプレート・設定・スクリプト・同期プログラム・仕様書)は今後も直していくので、配った物を直すのではなく、GitHub に置いた正本を直して版を出す(Yu 2026-10-24)。

| 置き場所 | 中身 |
| --- | --- |
| GitHub `rd-notebase` | 正本。`docs/`(仕様書3点)、`vault/`(個人・共有・機密のひな形)、`manifest.toml`(配布の目録)、`tools/`(配布物を組み立てるスクリプト)。のちに同期プログラムのソースも置く |
| 共有の `_仕組み/tools/配布/<版>/` | 版ごとの配布物(個人・共有・機密の3つ)。全員が GitHub のアカウントを持たなくてよいように、Box に置く |
| 各 vault | 配布物を当てた結果。ノートは各自のもの |

- 版は `v1.0.0` のような番号で出し、GitHub のリリース(タグ)と `_仕組み/tools/配布/<版>/` の名前をそろえる。
- 配布物は2種類のファイルに分ける(`manifest.toml`)。「仕組みのファイル」(テンプレート・スクリプト・README・仕様書の写し・一覧の .base)は、版を当てるたびに上書きする。「最初だけのファイル」(メンバー.csv、個人設定.md、ノート履歴/、各自の .obsidian のうち配る設定以外)は、なければ置くだけで上書きしない。ノートには触れない。
- 版を当てるのは同期プログラムの仕事にする(要件書 F-46)。できるまでは、まとめ役が `_仕組み/tools/配布/<版>/` から仕組みのファイルを手でコピーする。
- テンプレートの正本はリポジトリの `vault/共有/_仕組み/templates/` の1か所にする。個人 vault 用の配布物には、組み立てるときにここから写す。
- 直したいことは GitHub の issue か、金曜の定例で出す。直すのはまとめ役で、版を出す前に仕様書の変更履歴に書く。

### 書きためたノートを壊さずに仕組みを直す

ノートを書きためた後でも仕組みを直せるように、直し方を2つに分ける(Yu 2026-10-25)。

| 直すもの | 例 | 既存のノート |
| --- | --- | --- |
| 自由に直してよいもの | テンプレートの見出しや説明の行、一覧(.base)の列や並び、スクリプトの中身、マニュアル | そのままでよい。古いノートは古い形のまま読める |
| 手順を守って直すもの | 属性の名前や値(type の名前など)、フォルダの名前、ファイル名と id の形、リンクの書き方 | 移し替えが要る |

手順を守って直すときは、次の4つを守る。

1. **古い名前も読み続ける**。プログラム・一覧・スクリプトは、新しい名前と一緒に古い名前も同じものとして扱う(前例: type: 設計記録 はソリューション、3文字の人の記号の id はそのまま有効)。古い名前を読まなくしてよいのは、全員の vault の移し替えが終わり、変更履歴に書いてから。
2. **版ごとに移し替えのスクリプトを1本作る**(`tools/migrate_v<版>.py`。前例: `tools/migrate_v031.py`)。まず vault ごとの控え(zip)を作る。`--run` なしでは、することを表示するだけにする。何度走らせても同じ結果になるようにする。
3. **飛ばした版も順に当てる**。各 vault の `_仕組み/記録/版.txt` に今の版がある。同期プログラムは、その版より新しい移し替えを古い順に全部当ててから、仕組みのファイルを上書きする(要件書 F-46)。
4. **版を出す前に試験用の vault で確かめる**。いろいろな種類と古い形のノートを入れた試験用の vault を正本に置き、移し替えと同期プログラムを走らせ、ノートが消えないこと・リンクが切れないこと・一覧に出ることを自動テストで確かめる。

- 変更履歴には、その版で既存のノートに何が起きるか(「なし」か、どの移し替えを当てるか)を1行書く。
- 個人 vault の `.obsidian` は、配る設定(`hotkeys.json` と、配ったプラグインの `plugins/<名前>/` の設定)を版ごとに上書きし、それ以外(画面の配置、各自が足したプラグイン、`app.json`、`community-plugins.json`)は最初だけ置く(`manifest.toml`)。キーや QuickAdd を直した版が、すでに使っている人にも届くようにするため。

## 100人規模への拡張

人数が増えてもフォルダとファイル形式はそのまま使い、「誰が共有に入れてよいか」と「探し方」だけを段階的に足す。

| 段階 | 目安 | 足すもの |
| --- | --- | --- |
| 1 | 2〜5人 | この仕様書のまま。同期プログラムで集めて配る |
| 2 | 10〜30人 | 分野やプロジェクトごとに担当者を置く。impact に関係なく、担当者の確認(reviewed_by)が入るまで共有に出さない |
| 3 | 30〜100人 | 共有 vault の編集は担当者のみ、他は閲覧(Box の権限で分ける)。人の記号が足りなくなりそうなら、新しい id だけ人を4文字にする(「ノートの id」)。競合が多ければ Git や社内 Wiki へ移し、検索・AI 要約を使う |

- 移行しやすいよう、今のうちから Markdown・属性欄・命名規則を守る。これがそろっていれば一括で移せる。
- 機密フォルダは、Box の共同作業者をその案件の担当営業・担当技術者だけにする。
