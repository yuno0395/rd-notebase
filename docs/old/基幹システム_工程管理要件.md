# 基幹システム 工程管理 要件

- 上位文書：「基幹システム 基本方針」「ID体系とコアデータモデル」「Obsidian基幹システム vault設計」
- 目的：案件の工程とロードマップを、**A4横1枚のガント図**で計画・共有・追跡する。図には人が直接書き込める（Excalidraw）
- ISO 9001との関係：設計・開発の計画（8.3.2）、計画変更の管理と記録（7.5、8.3.6）

---

## 1. 基本の考え方

| 原則 | 内容 |
|---|---|
| データが正本 | 計画（タスク・日付・担当・依存・見積・計画の版）は「工程表ノート」が正本。進捗・実績・見込みは各個人の週報とやることから集計する。ガント図は見た目と書き込みの場 |
| 進捗は数で数える | 進捗は「やること」の完了数／総数（例：3/8）。％や「何割進んだ」の感覚は使わない |
| 操作はドラッグ | 日程は表を編集せず、専用の編集画面で棒をドラッグして調整する。表は人に見せない |
| 図は自動生成＋書き込み | ガント図は「自動生成の層」と「書き込みの層」に分ける。自動生成の層は毎回作り直し、書き込みは残す |
| 予定と結果を辿れる | 当初計画・実績・見込みを重ねて表示し、計画変更は理由と承認を記録する |
| 1つの処理で描く | データ→ガント図の処理は1つだけ作り、編集画面のプレビューとExcalidrawへの書き出しの両方で使う（見た目のずれを防ぐ） |

## 2. 表示の種類

すべて**A4横1枚**（Excalidrawの1フレーム、A判比率）。

| 表示 | 期間 | 1マス | 列数 | 主な用途 | 載せる階層 |
|---|---|---|---|---|---|
| 月間 | 1か月 | 1日 | 約22〜31 | 担当者の日々の作業 | 作業（工程を帯で表示） |
| 3か月 | 3か月 | 1週 | 13 | 案件の進捗確認 | 工程・マイルストーン |
| 半年 | 6か月 | 1週 | 26 | 案件全体の見通し | 工程・マイルストーン |
| 5年 | 5年 | 半期 | 10 | 製品・技術ロードマップ | ロードマップ項目 |
| 10年 | 10年 | 年度 | 10 | 中長期ロードマップ | ロードマップ項目 |

### 2.1 暦のルール

| 項目 | 決定 |
|---|---|
| 週の始まり | 月曜日 |
| 年度 | 4月始まり |
| 半期 | 上期（4〜9月）／下期（10〜3月） |
| 休日 | 土日は休日。それ以外の会社休日（祝日・連休など）は**休日リスト**として毎年登録する |
| 休日の作業 | 基本は入れない。急ぎの時だけ、休日にもタスクを置ける（休日の列は灰色のまま、棒は描く） |

### 2.2 表示期間

| 方式 | 内容 | 例 |
|---|---|---|
| 今日起点 | 今日から自動でずれていく | 3か月表示：今週の月曜から13週 |
| 期間固定 | 開始日を任意に指定 | 2026-10-01 から |

- 表示の設定（種類・方式・開始日）は名前を付けて保存でき、同じ見え方で何度でも開ける
- 期間がずれると、書き込みも連動して動く（6章）

### 2.3 描き方

- 細かいタスクを粗い表示に出す時は、**マス内で比率どおりに描く**（3日の作業は1週マスの3/5）
- 行数の上限は30行。超えたら下の階層を畳む
- **一直線の流れは1行（レーン）**：グループの子が一直線につながる（設計検討→検討まとめ→詳細設計→小DR のように、各段が前の1つだけに続き、担当が同じ）場合、グループの1行に区切って並べる。区切りの名前は棒の上、小DRなどの節目は◆でその行の中に置く。各区切りは個別に押す・ドラッグできる。分けて見たいグループは `expand: true`
- **節目（◆）は一番上の1行にまとめ**、名前と日付を◆の横に書く（節目で行を使わない）。名前が重なる時は上下2段に分ける
- タスク名を押すと、その工程タスクの**まとめのノート**（工程表の `note:` で指定。なければ紐づくノートの最新）をプレビューする
- 表示要素：今日線、マイルストーン（◆）、進捗の塗りと「完了数/総数」（7.3）、依存の矢印、遅れ（赤）、当初計画との差（7章）

## 3. データの階層と置き場所

| 階層 | 例 | 置き場所 | 鍵（機密タグ） |
|---|---|---|---|
| ロードマップ項目 | 次世代X300の開発 | ロードマップノート（`type: roadmap`、製品・部署単位） | **技術ロードマップ**（保持者：上司） |
| 工程 | 案A試作、中間DR | 案件の工程表ノート（`type: schedule`、案件に1つ） | 案件の既定タグ |
| 作業 | ブラケット図面作成 | 同上（工程の子） | 同上 |

- 工程表ノートは**案件のリポジトリ**に置き、**計画だけ**を持つ。進捗・実績・見込みは個人の週報ノート・やることから集計して表示する（1つのノートを全員で書き換えない）
- 親の期間・進捗（やることの数）は子から自動で積み上げる。親に**目標期限**を置いた場合、子がはみ出したら赤で警告
- 工程はロードマップ項目に紐づける。ロードマップから「どの案件が担っているか」へ辿れる
- 鍵と公開の扱いは、vault設計 7章（見せる相手）と同じ

### 3.1 工程表ノートの形（人には見せない内部形式）

```yaml
type: schedule
project: P00042
roadmap: "[[ロードマップノート]]#R03"     # 紐づくロードマップ項目
baselines:                                  # 確定した計画（名前付きの版）
  - {name: 当初計画, version: a1b2c3d, approved_by: boss, at: 2026-10-01, reason: 着手時の計画}
tasks:
  - {id: T01, name: ボトルネック分析, start: 2026-10-01, end: 2026-10-10, owner: yamada, est: 6}   # est＝見積（人日）
  - {id: T02, name: 案A試作, start: 2026-10-11, end: 2026-10-31, owner: yamada, after: [T01], est: 12, alloc: 60, parent: P1}  # alloc＝割当率%
  - {id: M01, name: 中間DR, date: 2026-11-05, milestone: true, ref: "doc:DR-2026-0123"}
# 進捗・実績・見込みはここに書かない（週報・やることから集計）
```

### 3.2 見積と負荷

| 項目 | 内容 |
|---|---|
| 見積 | 工程タスクに人日（`est`）を付ける。担当者が付け、上司が計画の確定時に確認 |
| 割当 | 期間中にそのタスクへ割く割合（`alloc`、省略時100%） |
| 負荷の表示 | 「人×週」の負荷表：全案件の割当を人ごと・週ごとに合計。100%超は赤 |
| 休み | 本人の休暇・出張を負荷表に反映（稼働日から引く）。祝日は暦の台帳 |

- 見積は計画の確定時の値を残し、後からの増加は計画変更として扱う（9章）

### 3.3 ロードマップ項目の中身

| 項目 | 内容 |
|---|---|
| 目標期間 | 上司が手で決める（半期・年度単位）。案件の積み上げとは別に持つ |
| 予算 | 人月 |
| 状態 | 構想／計画中／実行中／完了／中止 |
| 関門 | 技術確認・試作完了・量産移管などの判定点（◆）。判定は案件のDR・マイルストーンに紐づける |
| 自動の見直し | 紐づく案件の見込みが**半期をまたいで遅れた**時、保持者（上司）の確認待ちに「ロードマップ見直し」を出す |

### 3.4 ID

| 対象 | 形式 | 例 |
|---|---|---|
| タスク | 工程表ノートID＋`#T`連番 | `261010-k4p8r#T02` |
| マイルストーン | 工程表ノートID＋`#M`連番 | `261010-k4p8r#M01` |
| ロードマップ項目 | ロードマップノートID＋`#R`連番 | `261001-x7h2m#R03` |

- 番号は再利用しない。ノートからは `task: 261010-k4p8r#T02` で作業とノートを紐づける

## 4. 日程の調整（dotpm）

工程表の編集は、Obsidian の工程管理プラグイン **dotpm**（コミュニティ拡張、MIT、社内で版を固定して配布）で行う。自作の編集画面は作らない（試作した Web の編集画面は廃止）。

### 4.1 取りまとめ役と置き場所

| 項目 | 決め |
|---|---|
| 編集する人 | 案件の**取りまとめ役**（台帳 `projects.<案件>.managers`。複数人）。担当者は今までどおり Day Planner・やること・週報 |
| 置き場所 | 工程表は**案件のリポジトリ**に置く（個人の vault に置かない）。取りまとめ役の vault では notebase が `20_工程/<案件>/` に取得し、更新・定期 push のたびに取り込み・送る |
| 継続 | 誰かが休む・辞める時は、台帳の `managers` を書き換えるだけ。工程表・履歴・申請は案件のリポジトリに残る |
| 衝突 | 2人が同じタスクを近い時間に直したら、**先に送った人の内容を正**にする。後の人の変更は `_衝突/` に控え、vault にお知らせを置いて直し直してもらう |

### 4.2 形式（dotpm のファイル）

- 案件のリポジトリ直下に `<案件>.md`（`pm-project: true`）と `_tasks/`（1タスク1ファイル、`pm-task: true`）
- dotpm が使う名前（`id`・`title`・`status`・`type`・`progress` など）は dotpm のもの。こちらの番号・見積は dotpm が触らない項目に持つ：`task_no`（T02・M01・G1）、`est`（人日）、`alloc`、`note`。dotpm はこれらを残す
- 子のあるタスク＝グループ、`type: milestone`＝節目、`dependencies`＝前のタスク、`assignees` の先頭＝担当
- 進捗の％（`progress`）は使わない（7.3 のやることの数）
- 変更理由は、プロジェクトの独自項目「変更理由」「理由の区分」に書く（dotpm のタスクの画面で入力）
- dotpm のファイルは普通のノートとして扱わない（id の付与・ファイル名の検査・分類の対象外）

### 4.3 承認との関係（サーバ）

dotpm には承認の仕組みがないので、**承認済みの計画（工程表ノート `type: schedule`）はサーバが持つ**。

1. 取りまとめ役が dotpm でドラッグ・追加・削除して保存 → notebase が案件のリポジトリに送る
2. サーバ（`pm.py sync`）が dotpm の内容と承認済みの計画を比べ、差分を申請にする。判定は 9章のまま（実働5日超の遅れ・節目の移動・範囲の変更は承認、それ以外は記録のみで即反映）
3. dotpm で足したタスクには、サーバが番号（`task_no`）を振って書き戻す（使ったことのある番号は使わない）
4. 申請中は dotpm に変更が残り、ガント図は「申請中」として描く。**却下されたら、サーバが dotpm を承認済みの計画に戻す**。申請中にさらに直したら、申請を出し直す
5. 理由が未記入の時は「その他・理由が未記入」で申請する（上司が判断で差し戻せる）

- Excalidraw の A4 ガント図（書き込み）、当初計画・実績・見込みの比較、週報との連携は今までどおりサーバが承認済みの計画から作る
- dotpm の自動ずらし（前のタスクが動くと後ろも動く）で動いたタスクも、差分としてまとめて申請に入る

**Excalidrawで直接棒を動かさない理由**：書き込みと棒を一緒に動かしやすい。日単位の吸着・依存の連動・行の並べ替えなど、工程表らしい操作の後付けが難しい。

## 5. ガント図の構成

| 層 | 内容 | 更新 |
|---|---|---|
| 自動生成の層 | 軸、棒、マイルストーン、今日線、依存の矢印、遅れの色、当初計画の影、遅れ日数 | データが変わるたびに作り直す |
| 書き込みの層 | 人が描いたコメント、矢印、メモ | 残す（6章のルールで位置だけ追従） |

- 自動生成の要素には印を付け（要素の付加情報）、人の書き込みと区別する
- 表示の種類ごとに、別のフレーム（またはExcalidrawファイル）にする

## 6. 書き込み（コメント）

コメントは**表示の種類ごと**に属し（3か月表示に書いたものは3か月表示にだけ出る）、図の座標ではなく「何に付いているか」で記録する。

| 付き方 | 例 | 期間・日程が変わった時 |
|---|---|---|
| タスクに付く | 「試作遅れ注意」→ 案A試作 | タスクの棒と一緒に動く |
| 日付に付く | 「工場停止日」→ 11/3 | その日付の位置へ動く（行は自由） |
| 用紙に付く | 凡例、注記 | 動かない |

- 付き方は描いた場所から自動で判定する（棒の近く→タスク、空き地→日付、余白→用紙）。後から変更できる
- 付き先が表示期間の外に出たコメントは隠し、図の端に「範囲外のコメント n 件」と出す
- 付き先のタスクが削除された場合は、図の端の「行き先のないコメント」欄に集める（黙って消さない）
- コメントは**書いた人ごとに別に保存**し（本人のvault）、ガント図には重ねて表示する。同じ図を複数人が書き換えて衝突しない。人ごとに表示・非表示を切り替えられる

## 7. 当初の予定と実際の結果

### 7.1 3本の線

| 線 | 意味 | 描き方 |
|---|---|---|
| 当初計画 | 確定した計画（初版または選んだ版） | 薄い影の棒 |
| 実績 | 実際に始めた日・終えた日 | 塗りつぶしの棒 |
| 見込み | 未完了分の現在の予定 | 点線の棒 |

- 棒の横に当初計画との差を**実働日**で表示（例：+5日）

**試作で決めた描き方**（部下・上司役の評価から）

| 要素 | 描き方 |
|---|---|
| 当初計画 | 棒の下の細い灰色の影 |
| 今の計画 | 枠だけの棒（承認済みの計画） |
| 実績 | 枠の中を塗る（実行中は今日まで） |
| 見込みの遅れ | 計画を越える分・押し出された位置を赤の点線 |
| 申請中 | 橙の点線（承認前） |
| 節目 | ◇灰＝当初、◆黒＝計画、◆赤＝見込み（遅れ）、◆緑＋「済」＝実施済み |
| 範囲外 | 表示期間の外にあるタスクは端に「1/6〜 ▶」 |
- **計画と見込みは別物**：見込みは担当者が週報でいつでも直せる（承認不要）。計画（確定した版）を変える時だけ承認（9章）。遅れの見込みを隠さずに出せるようにするため

### 7.2 計画の確定（ベースライン）

- 「当初計画」「第2版計画」のように**名前を付けて確定**する（Gitの版に名前を付ける）
- 確定には上司の承認と理由を残す（9章）
- 重ねて比べる計画の版は、表示ごとに選べる

### 7.3 進捗：やることの数で数える

％は主観で決まり意味がないため使わない。工程タスクに紐づく**やること**（Obsidian Tasks、`task::` で紐づけ）の数で数える。

| 表示 | 内容 |
|---|---|
| 進捗 | 完了数／総数（例：**3/8**）。棒の塗りはこの比率 |
| 週の動き | 今週の完了数・追加数（例：完了 +3、追加 +2）。追加が続くタスクは「やることが増え続けている」と分かる |
| 未着手 | やることが0件の工程タスクは「0/0（未分解）」と表示し、分解を促す |
| 親 | 子の完了数・総数を合計 |

- やることは誰でも、いつでも追加してよい（承認不要）。総数が増えるのは計画の詳細化として記録に残す
- 1件の重さはそろえない（そろえる手間をかけない）。見通しは見込みの終了日で別に示す

### 7.4 実績の記録

| 項目 | 候補のきっかけ |
|---|---|
| 実績の開始日 | 最初のやることが完了した日（または紐づくノートが最初に作られた日） |
| 実績の終了日 | やることが全件完了した日 |

- 自動で決めず**候補として出し、本人が週報で確定**する（直した記録も残す）

### 7.5 辿り方

| 見たいこと | 方法 |
|---|---|
| タスクの変更の経緯 | タスクを押すと「変更の履歴」：いつ、誰が、何日から何日へ、なぜ、承認者 |
| 過去の任意の日時点の計画 | 日付を選ぶと、その時点の計画で図を再現（Gitの履歴から） |
| 当初計画と現在の差 | 当初計画の影と、遅れ日数の表示 |
| 遅れの一覧 | Web閲覧の工程タブに、当初計画より遅れているタスクを一覧 |

## 8. 他の機能との連携

| 連携先 | 内容 |
|---|---|
| ノート | ノートに `task:` を書くと、タスクから関連する検討・報告へ辿れる。ノート内のやること（`task::` 付き）が進捗の数になる |
| Web閲覧 | 「工程」タブ：ガント図、遅れの一覧、計画変更の確認待ち。上司はObsidianなしで見られる |
| 確認待ち | 計画変更のリクエストを、公開の確認と同じタブに並べる（9章） |
| PDF | A4横1枚で出力（既存のPDF出力を使う。余白にID・版・出力日時） |
| パワポ貼り付け | 既定は**申請中（未承認）を含めない**。ファイル名に案件・表示・日付。高さは行数に合わせて切る（Web閲覧も同じ。PDF・Excalidrawは A4 のまま）。**書き込みなしのガント図**（自動生成の層だけ）を画像で出す。SVG（拡大しても粗くならない）とPNG。コピーしてそのまま貼れる。余白に版・出力日時を小さく入れる |
| 見せる相手 | 工程表・ロードマップも、ノートと同じ鍵と公開の仕組みで扱う |

## 9. 計画変更の承認フロー

**公開範囲の変更（vault設計 7.4.1）と同じ流れ**にする。

1. 担当者が編集画面で、確定した計画より後ろへ日程を動かす（またはマイルストーン・計画の確定を変更する）
2. 保存時に**変更のリクエスト**が作られる。変更前→変更後の日程、影響するタスク（依存先）、理由（必須）を記録
3. 承認者（工程表の鍵の管理者＝上司）の**確認待ち**タブに並ぶ
4. 上司は内容を確認し、確認項目・コメントを入れて、確認ポップアップで**許可**または**却下**
5. 許可されると計画の新しい版として確定する。却下されると元の計画のまま、担当者に通知

| 対象 | 承認 |
|---|---|
| 確定した計画より後ろへの日程変更で、**マイルストーンに影響する**もの、または **実働5日を超える**もの | 必要 |
| 上記より小さい遅れ | 不要（記録のみ。上司の画面に一覧） |
| マイルストーンの移動 | 必要 |
| 計画の確定（ベースライン作成） | 必要 |
| 範囲の変更：工程タスクの追加・分割・削除・担当替え、見積の**20%を超える**増加 | 必要 |
| 確定前の計画の調整、前倒し、見込みの更新、やることの追加・完了、実績の確定 | 不要（記録のみ） |

- **承認待ちの状態**：承認前は計画は変わらず、図に「申請中」の点線で出す
- **代理と期限**：承認者が不在の時は鍵の代理（タグ台帳の代理）が承認できる。3営業日放置されたら代理にも通知
- **後ろへの連鎖**：「後ろも一緒にずらす」は、前の作業の終わりが次の開始に**食い込む分だけ**押す（空きがあればそこで止まる）。期間は実働日数で保つ。見込みの計算も同じ決まりを使い、申請と画面の日付を一致させる
- **申請の置き場所**：計画変更の申請は案件リポジトリ（工程表の隣）に置き、申請・判断・反映をすべて工程表側の履歴に残す
- **申請カード**：先頭に「承認すると当初比 最大 +n日（今は +m日）」「動く節目・動かない節目」「これまでの計画変更の回数」を出す
- **分割**：工程タスクを分割した時は、当初計画（ベースライン）の期間・見積を子に割り振り、当初との比較を続けられるようにする
- **理由は区分を選ぶ**（必須）＋自由記述：見積の誤り／仕様変更／外部待ち（部品・外注・顧客）／不具合・やり直し／人の都合（他案件・休み）／その他。区分ごとに遅れを集計できる
- ロードマップ（技術ロードマップのタグ）の変更も、同じ流れで保持者（上司）が承認する

## 10. 週次の進捗報告

各個人が毎週、担当するタスクの進み具合を報告する。個人は**複数の案件を並行して担当する**前提とする。

### 10.1 構造：入力は1人1枚、保存は案件ごと

```
週報の入力画面（1人・1週・1画面）
  └ 今週の担当タスク一覧（全案件の工程表から自動で集める）
       ├ 案件P00042のタスク ─┐
       ├ 案件P00051のタスク ─┼→ 保存時に案件ごとへ分ける
       └ 予定外の作業       ─┘
                               ▼
   週報ノート（type: weekly）  1人 × 1週 × 1案件 で1件
   鍵＝その案件の既定タグ   → 案件ごとの機密がそのまま守られる
```

- **入力は1画面**：担当者は案件ごとに別々の報告を書かない。全案件の担当タスクが1画面に並ぶ
- **保存は案件ごと**：1枚のノートに複数案件の機密が混ざると、鍵の仕組み（ノート単位）で守れないため、保存時に案件ごとへ分ける
- **本人の一覧は自動生成**：「自分の今週」は、案件ごとの週報ノートを集めて表示する画面（ノートは作らない）

### 10.2 週報の中身（タスクごとの記入欄）

| 項目 | 入力 | 内容 |
|---|---|---|
| タスク | 自動 | 工程表のタスク（`工程表ID#T02`） |
| 進捗 | **自動** | やることの完了数／総数と今週の増減（例：3/8、完了 +3・追加 +2）。入力しない（7.3） |
| 見込みの終了日 | 日付（必須） | 先週の値から開始。変えなければそのまま |
| 実績の開始・終了 | 確認（候補あり） | 候補（7.4）が出た週だけ、確定を押す |
| やったこと | 短文（任意） | 完了したやることを自動で並べる。足りない分だけ書く |
| 根拠 | リンク（任意） | 関連する検討・計算・報告ノート（その週に更新したノートを候補に出す） |
| 課題・相談 | 短文（任意） | 困りごと。記入すると上司の確認待ちに並ぶ |
| 来週の予定 | 自動＋短文（任意） | 来週が予定日のやることを自動で並べる。翌週の入力画面に「予定」として出す |
| 工数 | **自動（入力しない）** | 机上作業・開いているだけ・後から記入の区分で算出（10.6） |

- **必須は見込みの終了日だけ**（変更なしなら押すだけ）。他は自動か任意
- **締め切り**：毎週金曜。未提出は月曜に本人へ通知。未提出の週を推測で埋めない（「未提出」と表示）
- **手間を測る**：入力にかかった時間を記録し、目標は**1人週15分以内**。超える場合は項目を減らす
- **予定外の作業**：工程表にない作業も「予定外」として1行追加できる。案件を選ぶ（なければ「案件外」）
- **紐づけの手間を減らす**：`task::` の候補を自動で出す（ノートの案件・直近に使った工程タスク）。金曜の入力画面で、紐づけのない今週のやること・記入をまとめて工程タスクに割り当てられる

### 10.3 タスクの経過：ガント図の棒を押すと見られる

| 場所 | 動き |
|---|---|
| Web閲覧の工程タブ | 棒を押すと「タスクの経過」ポップアップ |
| Excalidrawのガント図 | 棒の要素に、そのタスクの経過ページへのリンクを付ける（押すと開く） |

**タスクの経過に出すもの（時系列）**

| 週 | 進捗 | 見込み | やったこと | 根拠 | 課題 | 担当 |
|---|---|---|---|---|---|---|
| 10月6日週 | 0/5 → 2/6（完了+2・追加+1） | 10/31 | 案Aの構想、剛性計算 | 剛性比較 | — | 山田 |
| 10月13日週 | 2/6 → 4/8（完了+2・追加+2） | 11/4 | 試作図面作成 | 図面検討 | 治具の手配待ち | 山田 |

- 同じ時系列に、**計画変更**（いつ、何日から何日へ、理由、承認者）と、**実績の開始・終了**も並べる
- 複数人が担当するタスクは、担当者ごとの記入をまとめて表示する
- 見る人の権限で絞る：案件の鍵を持たない人には、週報の中身は出さない（🔒）

### 10.4 ガント図への反映

- やることの完了数／総数を棒の塗りと数字に反映する（7.3）
- 週報で確定した実績の開始・終了日を実績の棒にする（7.4）
- 見込みの終了日を見込みの棒にする。計画の終了日を越えた時は、担当者に「計画変更のリクエスト」を提案する（自動で送らない。9章の条件に当たる時だけ承認が要る）

### 10.5 見る人ごとの画面

| 見る人 | 画面 | 内容 |
|---|---|---|
| 担当者 | 自分の今週 | 全案件の担当タスク、先週の予定、入力画面 |
| 案件の上司 | 案件の週報 | その案件の全員の記入、遅れ、課題・相談 |
| 所属の上長 | 部下の週報 | 部下の全案件の記入。鍵を持たない案件は🔒とタイトルのみ |

- 課題・相談の記入、計画変更の提案は、上司の**確認待ち**に並ぶ
- **上司の画面に個人の工数・順位を出さない**。上司が見るのは案件・タスク単位の合計だけ。個人ごとの内訳（日・区分ごと）は本人だけが見られる

### 10.6 工数の自動算出

工数は時間を手入力しない（入力させても正確にならず、手間だけが増えるため）。**文書の作業の記録**から自動で算出し、PCの外の作業だけを**後から出来事として記入**する。

#### 時間の区分

1日の時間を次の4つに分けて記録する。

| 区分 | 判定 | 割り当て先 | 例 |
|---|---|---|---|
| 机上作業 | ノート・図を手前に表示し、**マウス・キーボードの操作がある** | そのノートの案件・タスク | 検討を書く、図を描く |
| 開いているだけ | ノート・図を手前に表示しているが、**操作がない**（例：5分以上） | そのノートの案件・タスク（机上作業とは分けて保持） | 雑談、議論、考えごと |
| 後から記入した作業 | 本人が後から記入した出来事 | 記入した案件・タスク | 実験、打合せ、現場作業 |
| それ以外 | Obsidianが手前にない時間、記録のない時間 | 割り当てない | CAD・メール・表計算など他のツールでの作業、不在 |

- 「開いていた時間」（開いてから閉じる・切り替えるまで）と「机上作業の時間」（操作がある時間）の**両方を保持する**
- 机上作業と開いているだけの時間は、どちらもノートの `project` と `task:` で案件・タスクに割り当てる
- **他のツールでの作業は追跡しない**。Obsidianの外の時間は、まとめて「それ以外」とする（他のアプリの監視はしない）

#### 後から記入（PCを開かずに実験に入った日など）

デイリーノートに、その日の**時間の帯**を表示する。

```
 9:00        11:00        13:00        15:00        17:00
 ███机上████░░開いているだけ░░  [　記録なし　]  ███机上███
                                 ↑ 押して「実験：案A試作の振動測定」を記入
```

- 記録のない時間（またはそれ以外の時間）を押し、**何をしていたか**を選ぶ：実験・打合せ・現場作業・移動・その他、案件・タスク、ひとことメモ
- 入力するのは「何をしたか」と時間帯であって、工数の数字ではない
- 開いているだけの時間を、後から「打合せ」や「それ以外」に付け替えることもできる（雑談だった時間など）
- 予定表の会議は、時間帯の候補として自動で表示する

#### 集計

| 単位 | 内容 |
|---|---|
| 日次 | デイリーノートに、案件・タスクごとの「机上作業」「開いているだけ」「後から記入」と「それ以外」を書き込む |
| 週次 | 週報に、案件・タスクごとの時間を自動で載せる（3区分を分けて表示） |
| 案件の工数 | 机上作業＋開いているだけ＋後から記入。どの区分を工数に含めるかは集計時に選べる |

#### 記録の扱い

- 操作の細かい記録（何時何分に操作があったか）は本人の端末に置き、短期間で消す。サーバに送るのは日ごとの集計だけ
- 本人は集計を確認・修正できる（修正した記録は残す）
- 自動の工数は**参考値**である（Obsidian外の作業は入らない）。原価・見積の比較では「参考値」と明示して使い、正確な値として扱わない
- 工数は案件の負荷・原価の把握に使い、**個人の評価には使わない**ことを運用ルールで明記する

### 10.7 週の呼び方

- 「**n月m日週**」（その週の月曜日の日付）。例：10月6日週
- 週をまたぐ年度・年の区切りでも、月曜日の日付で一意に決まる

### 10.8 閲覧の範囲

- 所属の上長と案件の上司が違う場合も、特別な扱いはしない。週報ノートは案件の鍵で守られるので、**見せる相手の設定どおり**に見える・見えないが決まる

### 10.9 日々の計画と「やること」

日々の作業計画は **Day Planner**（Obsidianの拡張機能）、後でやらなければいけないことは **Obsidian Tasks** を土台にする。

#### 3種類の「タスク」を呼び分ける

| 呼び方 | 中身 | 置き場所・道具 |
|---|---|---|
| 工程タスク | ガント図の棒（案件の計画） | 工程表ノート（3章） |
| 今日の予定 | 時間帯付きの作業の予定と記録 | デイリーノート（Day Planner） |
| やること | 今はできないが後でやること | 発生したノートの中（Obsidian Tasks） |

#### 今日の予定（Day Planner）

- デイリーノートの「今日の予定」に、時間帯付きで書く。Day Plannerが1日の時間軸で表示する
  ```
  - [ ] 10:00 - 12:00 案A 振動測定 #実験 [task:: 261010-k4p8r#T02]
  - [x] 13:00 - 14:00 試作打合せ #打合せ [task:: 261010-k4p8r#T02]
  ```
- 予定表（会議）を取り込んで同じ時間軸に表示する（Day Plannerの予定表連携）
- **後から記入（10.6）もこの形式で行う**。PCを開かずに実験した時間は、終わった後にこの形式で書く（チェック済みにする）
- 自動記録（机上作業・開いているだけ）は、予定と並べて比べられるように別の帯で表示する（予定と実績の比較）

#### やること（Obsidian Tasks）

- やることは、**発生したノートの中に書く**（議事録の中の宿題、検討ノートの中の確認事項など）。後から見た時に、なぜそれが生まれたかを辿れる
  ```
  - [ ] 治具の見積もりをA社に依頼する 📅 2026-10-10 [task:: 261010-k4p8r#T02]
  ```
- **デイリーノートに、未完了のやることを常に表示する**（テンプレートに一覧の問い合わせを入れておく）。期限切れ → 今日 → 期限なし の順
- やることに日付（予定日）を付けると、その日の「今日の予定」にも出る（Day PlannerがObsidian Tasksの予定日を読む）
- `task:` で工程タスクに紐づけると、完了したやることが週報の「やったこと」の候補に出る
- やることは書かれたノートの鍵を引き継ぐ。デイリーノートの一覧は本人の手元だけで集計するので、他人には見えない
- 他人からのコメントで「やることにする」としたもの（指摘、vault設計 7.10）も担当者に届き、デイリーノートの一覧に並ぶ

#### 拡張機能への依存（vault設計 13章の方針どおり）

- 正本はMarkdownの文字（チェックボックス、時刻、日付、`task::`）であり、拡張機能が使えなくなってもデータは残る。サーバは自前の処理でこの書き方を読む
- 2つとも個人が開発するコミュニティ拡張。社内で版を固定して配布し、更新は検証してから行う
- Day Plannerでの予定のドラッグ調整、Obsidian Tasksとの連携の範囲は、試作で動作を確認する

## 11. 決定事項

| 項目 | 決定 |
|---|---|
| 表示の種類 | 月間（日）、3か月（週）、半年（週）、5年（半期）、10年（年度）。すべてA4横1枚 |
| 表示期間 | 開始日は任意。今日起点と期間固定を切り替え可能。書き込みも連動して動く |
| 週の始まり | 月曜日 |
| 年度・半期 | 4月始まり。上期（4〜9月）・下期（10〜3月） |
| ロードマップの鍵 | 「技術ロードマップ」タグ。保持者は上司 |
| 計画変更 | 上司の承認が必要。リクエストを送り、公開範囲の変更と同じ流れで処理 |
| 日程の調整 | Obsidian の dotpm でドラッグ（取りまとめ役、複数人）。工程表は案件のリポジトリに置き、承認はサーバが承認済みの計画と比べて行う |
| 週次の進捗報告 | 入力は1人1画面、保存は案件ごと（1人×1週×1案件）。ガント図の棒を押すとタスクの経過を表示 |
| 工数 | 時間は入力しない。机上作業（操作あり）・開いているだけ（操作なし）を自動で分けて記録し、PCの外の作業は後から出来事として記入。Obsidian外の時間は「それ以外」。個人評価には使わない |
| 週の呼び方 | n月m日週（月曜日の日付） |
| 日々の計画・やること | 今日の予定はDay Planner、やることはObsidian Tasks。やることは発生したノートに書き、デイリーノートに未完了を常に表示 |
| 進捗 | ％は使わない。工程タスクに紐づくやることの完了数／総数。1件の重さはそろえず、見通しは見込みの終了日で示す |
| 計画と見込み | 分けて持つ。見込みは承認不要、計画の変更は条件付きで承認 |
| 置き場所 | 工程表ノートは案件リポジトリで計画だけ。進捗・実績は個人の週報から集計。コメントは書いた人ごとに保存して重ねる |
| 実績の日付 | 自動は候補。本人が週報で確定 |
| 範囲の変更 | 工程タスクの追加・分割・削除・担当替え、見積の大きな増加は承認。分割は当初計画を子に割り振る |
| 理由 | 区分の選択が必須 |
| 承認なしの遅れ | 実働5日まで（マイルストーンに影響するものは日数によらず承認） |
| 見積の増加 | 20%を超えたら承認 |
| 承認の放置 | 3営業日で代理にも通知 |
| ロードマップ項目 | 目標期間（手で決める）、人月予算、状態、関門。半期をまたぐ遅れで見直しを自動提示 |
| 工数の扱い | 参考値。上司の画面に個人の工数・順位は出さない |
| 週報 | 必須は見込みの終了日だけ。金曜締め。未提出を推測で埋めない。入力は1人週15分以内を目標に測る |
| 休日 | 土日は休日。他の会社休日は毎年リストで登録。急ぎなら休日にもタスクを置ける |
| 部署をまたぐロードマップ | 特別な扱いはしない（通常の鍵と見せる相手の仕組みで扱う） |
| 上司とガント図 | 上司は書き込まない。書き込みなしのガント図を画像（SVG・PNG）で出し、パワポに貼れる |
