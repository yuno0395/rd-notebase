# Box 版の仕様：個人 vault・プロジェクト vault・セットベース開発

状態：仕様の検討（未実装）。2026-10-17、2026-10-18 更新（同時編集、プロジェクトの見つけ方、ノートの種類を A3 中心に、A3 は Excalidraw で描く）
これまでの GitHub 前提の実装（`client/run.py`・`tools/*.py`）は残っているが、この仕様では使わない。移行の扱いは「9. 今の実装からの移行」。

## 1. 方針

- **GitHub をやめ、Box Drive だけで動かす。**
  - 保存・共有・版の履歴は Box に任せる。容量は無制限の前提。
- **性善説で作る。**
  - 誤操作は起きない前提。
  - 守りの仕組み（ハッシュの鎖、権限で書けなくする、警報など）は作らない。
  - 正しいやり方が一番手軽になるように作る（ボタン1つ、選ぶだけ、日本語のテンプレート）。
- **プロジェクトごとに別の vault にする（案A）。**
  - Box の共有フォルダは置き場所が決まっていて、自分の vault の中に置けないため。
- **セットベース開発（SBCE）を前提にする。**
  - プロジェクト vault では、次の3つを扱う。
    - 案の並行検討と絞り込み
    - 知見の集積
    - 問いを解くためのタスク
  - 問いを解く単位は **A3 1枚**（要求→問い→計画→検証→知見→今後の展望）。リーン開発の A3 の考え方に合わせ、1つの問いを1つのノートに書く。
- **判断は誰でも記入できる。** 誰が判断したか・誰が記入したかは必ず残す。

## 2. Box のフォルダ構成

```
Box/
├─ 個人/山田/vault/                ← 個人 vault（本人だけ）
│   ├─ 01_daily/                      デイリー・週ノート（マイタスクが入る）
│   ├─ 10_notes/                      下書き・思考の記録
│   ├─ 50_添付/
│   ├─ _プロジェクト/<案件>/           取り込んだ写し（元の id 付き。読むだけ）
│   └─ .obsidian-山田/
│
├─ プロジェクト/P001_X200/          ← プロジェクト vault（メンバーで共有）
│   ├─ 00_案件/                       案件まとめ・要求・統合イベントの日程
│   ├─ 10_機能と案/<機能>/            機能ごとに、案を1ノートずつ
│   ├─ 20_A3/                         問いごとの A3（1問い1ノート）
│   ├─ 50_添付/                       検証のデータ・計算のファイル・図
│   ├─ 80_記録/                       採用時に凍結した記録（sha256・PDF）
│   └─ .obsidian-<人>/                人ごとの設定
├─ プロジェクト/P001_X200_ログ/<人>/ ← 記入のログ（vault の外）
│
├─ ナレッジ/                        ← 全社の知見ライブラリ（vault）
└─ notebase/                        ← 配布物（プログラム・テンプレート・設定の元）
```

- **見せる範囲**
  - Box のフォルダの共有設定で決める。
  - プロジェクトの vault とそのログのフォルダは、同じメンバーに共有する。
- **バックアップ**
  - Box の版の履歴を使う。
  - 採用など大事な時点の記録は `80_記録/` に凍結する（6章）。
- **Box Drive の設定**
  - 使う vault のフォルダは「オフラインで使用可能」にする。
  - Obsidian の起動と検索の速さのため。

### 2.1 同時編集した時（Box の競合）

**Box の動き**

- 2人が同じファイルを同時に編集すると、後から編集し始めた人の内容は別のファイル（コピー）に保存される。
- コピーのファイル名の末尾には、その人のメールアドレスが付く。
- 元のファイルには、先に編集し始めた人の内容が残る。どちらの内容も消えない。

**困ること**

- コピーも Obsidian ではふつうのノートに見える。中の `id` が元と同じなので、次のことが起きる。
  - 検索・マイタスク・索引に二重に出る。
  - リンクは元のノートだけを指すので、コピーの内容が忘れられる。

**仕様**

1. **見つける**
   - notebase は、ファイル名の末尾がメールアドレスのノートを「競合のコピー」として扱う。
   - 索引・マイタスク・横断検索には入れない（二重に出さない）。
2. **知らせる**
   - 競合のコピーがあれば、そのコピーを作った本人（メールアドレスの人）に知らせる。
   - 知らせる先は、デイリーノートの一覧と Obsidian の通知。
3. **まとめる**
   - コマンド「競合をまとめる」で、元とコピーの違いを並べて表示する。
   - 本人が元のノートに内容をまとめたら、コピーは notebase が消す（Box のごみ箱に入るので戻せる）。
   - まとめたことはログに1行残す。

**起きにくくする作り**

ルールで縛らず、ファイルの分け方で、同じファイルを2人が書く場面を減らす。

- **1つのものは1つのノートに。** 案は1案1ノート、A3 は1問い1ノートにする。人が違えば、ふつうは別のファイルを書く。
- **A3 は持ち主が書く。** ほかの人に頼んだタスクも A3 の計画に書く。
  - A3 は図ごと1つのファイルなので、競合すると図ごとコピーになり、まとめにくい。
  - 担当の人が完了のチェックを付けてよいかは未決（10章）。
- **大勢が書き足すノートを作らない。**
  - 案件まとめ・一覧・ボードは、手で書き足さず、見る時に作る。
    - 作る方法は、Obsidian の中の表示（ブロックの中の問い合わせ）か、notebase が個人の vault に作る。
  - 何人もの notebase が同じ一覧のファイルを書き直すと、それ自体が競合になるので、共有のフォルダには作らない。
- **ログは人ごとのファイル。** 自分のファイルにしか追記しないので、競合しない。
- **設定は人ごとのフォルダ**（`.obsidian-<人>`）。画面の配置（workspace.json）も人ごとなので、競合しない。
- **書き手を決める。**
  - 判断の履歴（6.3 の表）は、notebase が案のノートに追記する。判断はまれなので、競合はまれ。
  - Excalidraw の図（A3 を含む）は1つのファイルが大きく、まとめにくいので、図ごとに作る人を1人にする。

## 3. Obsidian での使い方

- **vault の登録**
  - notebase が Box を見て、参加しているプロジェクトの vault を Obsidian に登録する（3.1）。
  - 利用者は vault の切り替えから選ぶだけ。プロジェクトごとに別ウィンドウで開いたままでもよい。
- **設定**
  - 人ごとに設定フォルダを分ける（Obsidian の「設定フォルダの上書き」、`.obsidian-<人>`）。
  - 他人の設定とぶつからない。
  - 中身は `notebase/` の配布物から入れるので、全員同じ設定・プラグインになる。
- **notebase のコマンド**：Obsidian のコマンドパレットから実行する。

| コマンド | すること |
| --- | --- |
| 提出 | 個人のノートをプロジェクトに写す |
| 取り込み | プロジェクトのノートの写しを個人に置く |
| マイタスク | 全プロジェクトの A3 から自分のタスクを集め、今日のデイリーノートに一覧で入れる |
| 判断を記録 | 案の除外・採用などを記録する（6章） |
| 横断検索 | 全 vault を検索する |
| A3 の PDF | A3 のノートを A3 横の1枚の PDF にする（4.2） |
| ナレッジへ昇格 | プロジェクトの A3 をナレッジに送る |

- コマンドは引数なしで動く（選ぶものは画面のリストで選ぶ）。
- 「プロジェクトを探す」のコマンドもある（3.1）。

### 3.1 プロジェクトの vault を見つけて登録する

1. **目印のファイル**
   - プロジェクトを作る時に、vault の一番上に `notebase-project.yml` を置く。
   - フォルダの名前や場所ではなく、このファイルで見分ける。共有された人の Box で、フォルダが別の場所に現れても見つけられる。

   ```yaml
   案件: P001
   名前: X200 改良
   ログ: ../P001_X200_ログ   # vault から見たログの置き場
   ```

2. **探し方**
   - Box Drive のフォルダの一番上（既定は `C:\Users\<人>\Box`）から、2〜3階層までを探す。
     - 場所を変えている人もいるので、初回の setup で一度確かめて設定に保存する。
   - 見るのは目印のファイルがあるかだけ。見つけたフォルダより下は探さない。
     - Box Drive は仮想ドライブで、フォルダの一覧を取るたびにネットへの問い合わせが起き、深く探すと遅くなるため。
   - 見つけたプロジェクトは notebase の設定に一覧で持つ。
     - 前回あったのに見つからないもの（共有を外されたもの）は、一覧から外す。
3. **Obsidian への登録**
   - Obsidian の vault の一覧（`%APPDATA%\obsidian\obsidian.json`）に書き足す。
   - Obsidian が動いている間に書き換えると、閉じる時に上書きされる可能性がある。そのため次のようにする。
     - Obsidian が閉じていれば、すぐに書き足す。
     - 開いていれば、通知で「新しいプロジェクトが n 件あります。Obsidian を開き直すと一覧に出ます」と知らせる。
   - `obsidian://` の URL では、知らないフォルダを vault として登録できないため、この方法にする。
4. **探す時**
   - notebase を動かした時（PC の起動時の自動実行）に毎回探す。
   - すぐに使いたい時は、Obsidian のコマンド「プロジェクトを探す」で探す。

## 4. ノートの種類（プロジェクト vault）

テンプレートは日本語。どの種類にも次のプロパティを付ける。

- `id`
- `種類`
- `作成者`
- `作成日`
- `更新日`
- `状態`

種類は5つ。

| 種類 | 置き場 | 主なプロパティ | 内容 |
| --- | --- | --- | --- |
| 要求 | 00_案件 | 目標の範囲（下限〜上限）、出所、優先度 | 最初から1点に決めず、範囲で持つ。統合イベントごとに範囲を狭める。多くの A3 から参照されるので独立したノートにする |
| 機能 | 10_機能と案/<機能> | 関係する要求 | 製品の機能・部位の単位。案をまとめる |
| 案 | 10_機能と案/<機能> | 機能、状態（検討中・除外・採用）、根拠の A3 | 1案1ノート。各要求に対する見込みを書く |
| A3 | 20_A3（`.excalidraw.md`） | 対象（要求・機能・案のどれか、複数可）、持ち主、状態（計画中・検証中・完了）、検証の方法（試験・計算・調査・実績） | 1つの問いを、要求から今後の展望まで A3 1枚に描く（4.1） |
| 統合イベント | 00_案件 | 日付（固定）、対象の機能、狭める要求の範囲 | 日程が先に決まる節目。ここで案を絞る |

**リンクのつながり（一本の糸）**：

```
要求 → 機能 → 案
 ↑      ↑     ↑  ↓ 根拠
 └──── A3（対象）←┘
        └→ 今後の展望 → 次の A3
```

- A3 の対象は、要求・機能・案のどれでもよい。
  - 例：「最大の月産で物流が滞らないか」は、特定の案ではなく要求が実現できるかの問い。
- 案の除外・採用の根拠は、A3 の裏面の知見の節を指す（`[[A3の名前#知見]]`）。

### 4.1 A3 のファイル（Excalidraw とマークダウンの組み合わせ）

A3 1枚は、Excalidraw の1つのファイル（`<日付>_<問い>.excalidraw.md`）にする。

- 図を多く使える。
- A3 の枠に収まっているかを、目で見て分かる。
- 文字は決まった場所にあるので、機械で検索できる。

ファイルの中は4つの層に分かれる。

| 層 | 書く人 | 中身 |
| --- | --- | --- |
| プロパティ（先頭） | 作る時にテンプレートが入れる | 種類 A3、対象（要求・機能・案）、持ち主、状態、検証の方法 |
| 裏面のマークダウン | 持ち主（担当） | 計画のタスク、知見の表。正確に読みたいものだけ |
| 文字の一覧 | Excalidraw が自動で書く | キャンバス上の全部の文字（プレーンテキスト。Obsidian の検索で見つかる） |
| 図のデータ | Excalidraw が自動で書く | 要素の位置・形・どのフレームに入っているか（JSON） |

**キャンバス**

- テンプレートは、A3 横の枠と、その中の6つの名前付きフレーム。

| フレーム | 位置 | 書くもの |
| --- | --- | --- |
| 背景（要求） | 左の列・上 | なぜこの問いが要るか。対象の要求・案へのリンク。図 |
| 問い | 左の列・中 | 「〜は成り立つか」を1文で |
| 計画 | 左の列・下 | 裏面の「計画」の節を埋め込んで表示 |
| 検証 | 右の列・上 | 方法・前提と条件・結果。グラフや図が主。データは添付へのリンク |
| 知見 | 右の列・中 | 裏面の「知見」の節を埋め込んで表示 |
| 今後の展望 | 右の列・下 | 次の問い（次の A3 へのリンク）、案への影響、要求への影響 |

- フレームの中には、文字も図も自由に置ける。
- 埋め込みもフレームの中で場所を取るので、1枚に収まるかが見える。

**裏面のマークダウン**

計画の書き方（形は実装の時に決める。例）：

```
## 計画
- [ ] 現行機種の部品表から、調達のリードタイムと供給能力を集める @tanaka 📅 2026-11-06
- [x] 月産 N 台で必要数を試算する @yamada 📅 2026-11-13
```

知見の書き方（1つの A3 に複数あってよい）：

```
## 知見
| 知見 | 適用範囲 | 確からしさ |
| --- | --- | --- |
| 部品 X の調達リードタイムは 12 週。今の仕入れ先では月 ○台が上限 | 現行の仕入れ先・現行の部品構成 | 調査 |
```

- 確からしさは、推定・計算・試験・調査・実績のどれか。
- 適用範囲を書いておくと、次の機種で「どこまで使えるか」をすぐ判断できる。

**notebase が読むもの（読むだけで、A3 のファイルは書き換えない）**

| 読むもの | 使い道 |
| --- | --- |
| プロパティ | 一覧・判断の根拠のリスト・マイタスクの絞り込み |
| 図のデータの、フレームごとの文字 | 節を絞った検索（例：知見の節に「リードタイム」がある A3）。問いのフレームの1文目を A3 の題として一覧に出す |
| 裏面の計画 | マイタスク |
| 裏面の知見の表 | ナレッジの検索、判断の根拠 |
| 今後の展望のリンク | 次の A3 へのつながり |

- 図のデータは、圧縮しない設定にする（読み取りを簡単にするため）。
- 図が壊れる心配と競合を増やす心配がないよう、notebase は書かない。

**例：これから開発する機種のリードタイムを見積もる**

- 背景：要求「受注から出荷まで ○〜○週」
- 問い：予想最大の月産 N 台の時、現行の部品の調達で物流が滞らないか
- 計画：部品のリードタイムと供給能力を集める（担当・期限）、月産 N 台で試算する
- 検証：方法は調査と計算。前提は現行の部品構成・今の仕入れ先。部品ごとの必要数と供給能力のグラフ。部品表とリードタイムの一覧は添付
- 知見：部品 X が律速。12 週・月 ○台が上限（適用範囲：現行の仕入れ先）
- 今後の展望：
  - X を使う案は見直しの候補にする。
  - 新しい案「X を他機種と共通化して在庫を持つ」を出す。
  - 次の A3「別の仕入れ先で X の上限を上げられるか」につなげる。

### 4.2 1枚に収める・PDF

- A3 の枠の外にはみ出した要素があれば、notebase が知らせる（止めない。性善説）。
- 検証の細かいデータ・計算の過程は添付に置き、A3 には要点と結果のグラフだけを置く。
- コマンド「A3 の PDF」で、A3 の枠をそのまま A3 横の1枚に出す。
  - 今ある Excalidraw → PDF の仕組み（`render/pdf_out`）を使う。
  - 埋め込んだ裏面（計画・知見）の描画は、新しく作る。
- 打ち合わせやデザインレビューでは、この PDF をそのまま配れる。

## 5. 個人とプロジェクトの間の行き来

- **提出**（個人 → プロジェクト）
  - 個人のノートを選び、「提出」でプロジェクトの決まった置き場に写す。
  - 種類はテンプレートで選ぶ。
  - 個人側のノートには、提出先のリンクと日時が付く。
  - 個人側は下書きとして残してよい。正はプロジェクト側。
- **取り込み**（プロジェクト → 個人）
  - プロジェクトのノートを選び、写しを `_プロジェクト/<案件>/` に置く。
  - 写しには元の id を持たせ、「元を開く」（`obsidian://`）で元のノートに飛べる。
  - 写しは読むだけ。もう一度取り込むと最新に置き換わる。
- **マイタスク**
  - 全プロジェクトの A3 の計画から、担当が自分で未完了のタスクを集める。
  - 今日のデイリーノートに、期限順の一覧で入れる。
  - 一覧の各行は元の A3 へのリンク。完了のチェックはプロジェクト側の A3 で付ける。
- **横断検索**
  - notebase が全部の vault（個人・参加中のプロジェクト・ナレッジ）を読んで索引を作る。
  - 結果のノートは、その vault で開く。

## 6. 判断の記録（案の除外・採用など）

### 6.1 決まり

- **誰が判断してもよい。** 判断した人（判断者）を記録する。
- **誰が記入してもよい。** 判断者に代わって、別の人が記入してよい（代理）。
  - 記入した人（記入者）は自動で記録する。
  - 判断者と記入者が違えば「代理」の印が付く。
- **履歴は上書きしない。** 判断を変えたら、新しい判断を追記する（除外した案を戻すことも追記）。

### 6.2 記入のしかた

- 案（または統合イベント）のノートで「判断を記録」を押す。画面で次を選んで入れる。
  - **判断**：除外・採用（1案に決める）・保留・戻す
  - **判断者**：メンバーのリストから選ぶ（既定は自分）
  - **根拠の A3**：その案・機能・要求を対象にした A3 のリストから選ぶ（複数可）。リンクは A3 の知見の節を指す
  - **理由**：自由記述
- **根拠の A3 がない時**
  - 止めずに「根拠の A3 がありません。このまま記録しますか」と一度だけ聞く（性善説）。

### 6.3 どこに残るか

判断は、次の2か所に同じ内容で残る。

1. **ノートの中**：案のノートの末尾の「判断の履歴」の表と、`状態` のプロパティ。読むためのもの。
2. **ログのファイル**（vault の外）
   - 置き場：`プロジェクト/<案件>_ログ/<記入者>/<年月>.jsonl`
   - notebase だけが追記する。1行1件。
   - Obsidian の外にあるので、プラグインなどで書き換わらない。
   - ノートの表が崩れても、ログから戻せる。

```json
{"日時":"2026-10-17T10:12","記入者":"tanaka","判断者":"yamada","代理":true,
 "判断":"除外","対象":"<案の id>","対象の版":"<sha256 の先頭12桁>",
 "根拠":["<A3 の id>"],"理由":"剛性が要求の下限に届かない","案件":"P001"}
```

- ログは便利さと検索のためのもの。改ざん防止の仕組みは付けない（性善説）。
- 「判断の一覧」：ログから、案件の全判断を時系列で表示・PDF 出力できる。
- **判断の記録以外のログ**
  - 提出・取り込み・ナレッジへの昇格も、同じログに1行ずつ残す。
  - ふだんのノートの編集は記録しない（Box の版の履歴で足りる）。

### 6.4 採用（1案に決める）時の凍結

採用を記録すると、notebase が次を `80_記録/<日付>_<機能>_採用/` に保存する。

- その機能の全部の案と、根拠の A3（と A3 の添付）の、その時点の写し
- 各ファイルの sha256 の一覧
- まとめの PDF（案ごとの状態・判断の履歴・根拠）と、根拠の A3 の PDF

後から中身が変わっても、決めた時点の根拠を示せる（ISO 9001 7.5 の記録）。

## 7. ナレッジ（全社）

- `ナレッジ/` は独立した vault。全社で読める。
- **昇格**
  - プロジェクトの終わり（または随時）に、A3 を選んで「ナレッジへ昇格」で送る。
  - 知見だけでなく A3 ごと送る。なぜその問いを立て、どう確かめたかの文脈が残るため。
  - 添付も一緒に写す。元のプロジェクトと元の id を持たせる。
- **探し方**：ナレッジの横断検索は、A3 の知見の表（知見・適用範囲・確からしさ）を主に探す。
- 昇格した A3 は、次のプロジェクトで「取り込み」して案の根拠に使える。
- 昇格の判断・記録のルール（誰でもよいか、記入の履歴を残すか）は未決（10章）。

## 8. 今の実装から残すもの・やめるもの

| 区分 | 項目 |
| --- | --- |
| 残す | テンプレート（Templater）、デイリー・週ノート（Periodic Notes）、dotpm（工程表）、Excalidraw と PDF 出力、添付の手入れ（説明の .md・重複・縮小）、索引（SQLite）の考え方 |

| 変える | 承認 → 6章の「判断の記録」、案件アーカイブ → プロジェクト vault ごと Box で保管、`notebase.cmd` の引数付きコマンド → Obsidian のコマンド |
