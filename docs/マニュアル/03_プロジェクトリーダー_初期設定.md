# プロジェクトリーダー 初期設定

> 正本は rd-notebase の `docs/マニュアル/`。仕様書 v0.42 に合わせています。

プロジェクトを始めるときに PL(まとめ役)が1回だけやることです。先に [[01_チームメンバー_初期設定]] を終えておいてください。PL は共有 vault をよく使うので、共有 vault の設定(01 の 6)も必ず行います。

一度やれば、あとは現場のノートが自動でここにつながります。

## 1. プロジェクトの台帳を作る

台帳は、プロジェクト名・メンバー・節目を決める1枚です。ここで決めた名前が、全員のイシューの `project` の書き方になります。

1. **共有 vault** で Ctrl+N →「プロジェクト」(個人 vault の一覧にはありません)。
2. 置き場所を聞かれたら、新しいフォルダの名前としてプロジェクト名を打ちます(例: `樹脂カバー量産`)。台帳は `樹脂カバー量産/<id>_樹脂カバー量産.md` になります。
3. 属性欄を書きます。

| 属性 | 書くこと | 例 |
| --- | --- | --- |
| members | 参加する人。メンバー.csv と同じ名前 | `[Yu, 佐藤]` |
| status | 進行中 / 完了 / 中断 | 進行中 |
| outlook | 〇 予定どおり / △ 遅れそう / × 間に合わない | 〇 |
| outlook_reason | 理由を1行 | |
| request_to_manager | 管理者(上司)に判断してほしいこと。なければ空 | |

- 節目(DR、試作、量産開始など)は属性欄ではなく、本文の「期間・主な節目」の表に1行ずつ書きます。列は 節目・計画日・見込み日 です(例: `| DR1 | 2026-12-10 | 2026-12-10 |`)。日付は 2026-12-10 の形で書きます。
- members に書いた人の個人 vault に、このプロジェクトのノートが配られます(同期プログラムが読みます)。人が増えたらここに足すだけです。
- 台帳を開くと、下の「このプロジェクトのイシュー」に、解消・中止でないイシューが priority 順に出ます。この行は消さないでください。

## 2. 目的を置く

1. Ctrl+N →「目的」→ 置き場所に `樹脂カバー量産/01_目的` を選びます(一覧になければ、そのまま打てばできます。イシュー・タスク・ナレッジも同じように `03_イシュー`・`04_タスク`・`05_ナレッジ` に作ります)。
2. 名前は「〜する」で終わる文にします(例: 外観不良ゼロで樹脂カバーを量産する)。
3. 属性欄の project に台帳と同じ名前を書きます(`project: [樹脂カバー量産]`)。
4. 本文の「誰に何を届けるか」「達成の判定基準」を書きます。
5. 台帳の「目的」の行に、Ctrl+K で探して目的へのリンクを入れます。

## 3. 価値の仮説を3〜5個置く

1. 目的のノートの「価値の仮説」に、仮説を1行ずつ書きます(例: 電池が3年もつ、後付けが10分でできる、1週間前に故障の予兆がわかる)。数値で書けると確かめやすくなります。
2. 行ごとに Ctrl+H。parent に目的が入った仮説のノートが `01_目的/` にできます。
3. 仮説は最初は粗くてかまいません。知見が増えたら直し、仮説の下に仮説を置いて筋道を木にしていきます(04 の「仮説の木を育てる」)。

## 4. 成果物の候補を出す

価値の仮説(何を満たすか)と並べて、成果物の候補(何で満たすか)を出します。2つの軸は friend でつなぎます。

1. 目的のノートの「成果物の候補」に、目的を果たす成果物の案を複数書き、行ごとに Ctrl+U。parent に目的が入った成果物候補(status: 候補)ができます。同じ目的の下の候補が「一組」になり、比べて絞る単位になります(例: 「A案 クランプ式」「B案 ねじ止め式」)。
2. 成果物候補のノートの「部分の案」に、部分ごとの案を書き、行ごとに Ctrl+U。parent にその候補が入った部分の案ができます(例: A案の下に「電池ユニット」「マグネット取付」)。
3. 部分の案(か成果物候補)の「価値の仮説を実現できるか」に `[[仮説]]` を書き、右クリック →「関係としてつなぐ」で friend に入れます。1つの案が複数の仮説を実現してもかまいません。週報の「成果物候補ごとの残り」に、候補ごとに実現していない仮説が出ます。
4. 案ごとに「価値の仮説を実現できるか」に前提を1行ずつ書き、崩れそうな前提はその行で Ctrl+I でイシューにします。最初の大きなイシューは PL が出しておくと、メンバーが続けやすくなります。

## 5. 全体を K-Plex で確かめる

1. 目的のノートで Ctrl+G。目的が中心になり、下に仮説が並びます。
2. 仮説をクリックして中心を移すと、その下に候補が、候補の下にイシューが出ます。
3. カードの色は priority です(1 赤、2 橙、3 黄、4 灰)。色がまったくつかないときは、K-Plex の設定でテーマが「開発ノート」になっているか確かめます。priority は同期プログラムが書くので、動く前は色がつかないこともあります。

## 6. システム管理者に頼むこと

| 頼むこと | なぜ |
| --- | --- |
| メンバーを共有フォルダに招待し、番号を メンバー.csv に入れてもらう | 招待がないと共有 vault が見えず、番号がないと id が作れない |
| 顧客の資料を扱うなら、機密フォルダを作ってもらう | 共同作業者を担当者だけにするため |
| 週報の届け先(上司)に `開発ノート_報告/` を共有してもらう | 上司は Obsidian を使わないため |
| 週報に載せる節を決めてもらう(`report_sections`) | 「同じノード」はプロジェクトが2つ以上になるまで自動で外れる。ほかに外したい節があれば言う |

機密フォルダができたら、PL かその案件の担当が「機密の窓口」ノートを1つ作ります。Ctrl+N →「機密の窓口」→ 名前は顧客名を使わない呼び名(例: 案件A)。readers(見てよい人)と owner(社内の担当)だけを書き、顧客名・図番・相手の担当者の名前は書きません。機密フォルダの `00_README.md` にも、この窓口の名前を書いておきます。

## 7. 会議の予定を決める

| 会議 | いつ | 中身 |
| --- | --- | --- |
| 金曜の定例 | 毎週金曜、35分(月末は50分) | 同期レポートの片付け、未判定の impact、見込み3行(04 の「金曜の定例」) |
| DR(デザインレビュー) | 節目ごと(台帳の「期間・主な節目」の表) | impact 大のイシューの解像度の判定と、候補の絞り込み |

## 8. メンバーを迎える

1. メンバーに `00_マニュアル/01_チームメンバー_初期設定.md` を渡し、最後のチェックリストまで済ませてもらいます。
2. 最初の1か月は、目的・イシュー・タスク・デイリーだけを使います。ナレッジ図や K-Plex は、慣れてから足します。
3. 同期プログラムがまだ動いていなければ、全員が共有 vault に直接書きます(仮運用)。新しいノートは、共有 vault の `<プロジェクト名>/` の種類ごとのフォルダ(ノードは `共通/02_ノード/`)に作ります。同じノートを2人が同時に開いて書かないよう、声をかけ合ってください。
