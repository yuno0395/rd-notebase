# プロジェクトリーダー 普段の仕事

> 正本は rd-notebase の `docs/マニュアル/`。仕様書 v0.42 に合わせています。ノートの書き方は [[02_チームメンバー_普段の仕事]] と同じです。ここには PL が足してやることだけを書きます。

PL の仕事は、目的につながるリスクを優先順に減らし、成果物の候補を絞り、その進み具合を週1回管理者(上司)に渡すことです。決まった会議は金曜35分の定例と、節目の DR だけです。週報は同期プログラムが作るので、手では作りません。

## 1週間の流れ

| いつ | やること | 使うもの |
| --- | --- | --- |
| 毎日(数分) | デイリーノートの先頭の「同期プログラムから」を読む。確認を頼まれていれば見る | デイリーノート、`00_タスク一覧.base` の「確認待ち(確認する人ごと)」 |
| 金曜の定例(35分) | 下の4つ | 同期レポート、一覧(Bases)、台帳 |
| 月曜の朝 | 週報ができる。上司に読んでもらい、判断依頼の答えをもらう | Box の `開発ノート_報告/` |
| 節目 | DR で解像度を判定し、候補を絞る | DR 議事録、「DR 用」「候補の一組」ビュー |
| 月末の金曜 | 定例に15分足して、仕組みを振り返る | 週報の「仕組みの困りごと」 |

## 金曜の定例(35分)

| 順 | やること | 目安 |
| --- | --- | --- |
| 1 | `_仕組み/同期レポート.md` の「対応が必要」を片付ける。共有されなかったノート、競合、「やめますか」の候補、名前が重なるノードの「同じもの / 別もの」 | 10分 |
| 2 | `00_イシュー一覧.base` の「impact 未判定」で impact を決める。priority 1・2 の speed・status を直す。`00_ノード一覧.base` の「value_kind 未分類」で値のノードを 独立 / 組み立て に分ける | 15分 |
| 3 | 台帳の request_to_manager(上司に判断してほしいこと)と、「期間・主な節目」の表の見込み日を直す。月曜の週報に載る | 5分 |
| 4 | 各自の inbox とデイリーノートのメモで、1週間以上残っているものを、ノートにつなぐか捨てる | 5分 |

- 解像度(resolution)は定例では変えず、DR で決めます。
- priority 2 のイシューは大きいまま置かず、「すぐできる小さな検証」のタスクに切り出すよう声をかけます。
- 月末だけ15分足し、書いた本数・使い回された例・困ったことを話します。「記録に時間を取られたか」を必ず聞き、重い入力はシステム管理者に伝えて削ります。

### 同期レポートの片付け方

| 出ているもの | すること |
| --- | --- |
| 未入力(usefulness が空など) | 書いた人に直してもらう。直れば次の同期で消える |
| 確認待ち(impact 大で確認者がいない) | 確認する人を決め、review_request に書く |
| 競合(`<名前>_競合_<人>_<日時>.md`) | 共有側を正として元のファイルにまとめ、競合ファイルは `99_archive/` へ |
| 同じ名前のノード | 同じものなら「同じもの」にチェック。次の同期でまとまり、まとめたメモを書き直すタスクが本人にできる。違うものなら「別もの」 |
| やめますか(priority 4 で4週動かない、期限切れで4週) | 続けるか、status を中止にするか決める |
| 待ちが2週を超えた | 相手に催促するか、別の手を考える |
| inbox に1週間以上 | 4番目でまとめて片付ける |

## 優先順位の決め方

priority は impact と speed から自動で決まります。PL が決めるのは impact と speed だけです。

| priority | impact と speed | 扱い |
| --- | --- | --- |
| 1 | 方針・すぐ、絞込・すぐ | 最優先で着手 |
| 2 | 方針・時間がかかる、絞込・時間がかかる、出荷・すぐ、未判定 | 時間がかかるものは、すぐできるタスクに切り出す |
| 3 | 出荷・時間がかかる、中・すぐ | 手が空いたら |
| 4 | 中・時間がかかる、小 | 保留(見直しのたびに確認) |

- 時間がかかる「絞込」を後回しにしないでください。早く始めないと、目標が決まった日に候補を絞れません。
- 「出荷」のイシューは、候補が絞られてから解く方が無駄がありません。
- 認証・金型・長納期部品のように何週もかかるイシューには `lead_weeks: 10` のように週数を書かせます。節目までの残り週数がそれ以下になると、priority 1 に上がります。

## K-Plex で全体を見る

Ctrl+G で今のノートを中心に開きます。基本の操作(多段階展開・戻り方・つなぎ方)は [[07_K-Plexの使い方]] にあります。上に親、下に子、左に関係(friend)・価値仮説・生んだ対策(previous)、右に反論(challenger)と、そのノートを脅かすイシュー(脅かす)が並びます。

| 見方 | 気づくこと |
| --- | --- |
| 目的を中心に | 下に仮説が並ぶ。仮説が3〜5個あるか |
| 仮説を中心に | 下に仮説の木、左にこの仮説を実現する案(価値仮説)、右にこの仮説を直接脅かすイシューが並ぶ。案が1つもない仮説は、成果物候補に部分の案を足す |
| 設計案(成果物候補や部分の案)を中心に | 上に目的か上の案、下に部分の案、左に目論見(価値仮説)、右に不安材料(イシュー)が並ぶ。週報の「開発の目処」で、候補ごとに方針リスクがいくつ残っているかを見る |
| 右のイシューを見る | 赤いカードがない案は、リスクが見えていないか、すでに解けている |
| 右にカードがある仮説 | 反論がついている。下の仕事を進めてよいか、DR か定例で決める |
| ノードを中心に | parts が下に並ぶ。末端が組み立て値のままなら、原因をまだ分解できていない |
| 左の previous をたどる | 対策から新しいイシューが次々生まれている箇所 |

- 解消・中止・不採用・外れたのカードは灰色の点線で薄く出ます。
- K-Plex を見ながら作るときは Ctrl+Shift+N。中心のノートから、種類を選んで名前を打つだけです。K-Plex の中の作成(Ctrl+矢印)と編集欄は使いません。

## 仮説の木を育てる

知見が増えると、「なぜその仮説で目的に近づくのか」の前提が見えてきます。

1. 仮説の「目的とのつながり」に、前提を1行ずつ書きます。
2. 確かめたい前提は、その行で Ctrl+H。下の仮説になります。
3. 覆す事実が出たら、その `[[ ]]` の上で右クリック →「反論としてつなぐ」。属性欄の challenger に入り、K-Plex の右に出ます。
4. 外れたら status を「外れた」にします。下につながる仕事は、別の仮説につなぎ直すか中止にします。

## DR の進め方

1. Ctrl+N →「DR 議事録」で議事録を作ります。属性に `kind: DR` が入り、週報はこれで前回の DR の日を知ります。
2. `00_イシュー一覧.base` の「DR 用」ビューで、impact 大(方針・絞込・出荷)のイシューを段階ごとに見ます。

| 段階(resolution) | 状態 |
| --- | --- |
| 未把握 | リスクの名前だけ。原因はわかっていない |
| 現象 | 何が起きるかを事実で確かめた |
| 設計空間 | どの寸法・条件の範囲なら起きないかが、数値でわかっている。物は作れる |
| 原理 | なぜ起きるかを式やシミュレーションで説明でき、範囲の外も予測できる |

3. 段階が上がるものを複数人で決め、議事録の「解像度の判定」に `- [[イシュー]]: 現象 → 設計空間(根拠)` の形で残し、イシューの resolution を直します。
4. `00_設計案一覧.base` の「候補の一組(目的・上の設計案ごと)」ビューで、同じ parent の候補を並べて比べます。「残りのイシュー」「うち impact 大」が少ないほど磨けている候補です。トレードオフ曲線(ナレッジや設計案の図)を見て、線が目標に届かない案は不採用の根拠にし、使った曲線を議事録の「使ったトレードオフ曲線」に [[ ]] で残します。絞った結果を議事録の「絞り込み」に残し、落とした候補の status を「不採用」、選んだ候補を「採用」にします。不採用の候補も消しません(目標が変われば最善になることがあります)。
5. 目標が決まって1つに絞ったら、量産までのタスクを一度に立て、台帳の「期間・主な節目」の表を直します。

**出荷できるかの目安**: その目的の impact 大のイシューがすべて段階「設計空間」以上で、status が 低減済み か 解消 になっていること。

## 週報の読み方

週報は毎週月曜の朝、プロジェクトごとに `開発ノート_報告/<プロジェクト名>/<年-週>.html` にできます。ブラウザで開く1ファイルで、表は見出しを押すと並べ替えられます。報告フォルダ直下の `週報の一覧.html` から、全プロジェクトの最新と前の週を開けます。PL が書くのは台帳の「判断してほしいこと」(request_to_manager)だけです。書いてあれば週報のいちばん上に出ます。

| 節 | 出ていたら PL がすること |
| --- | --- |
| 開発の目処(成果物候補ごと) | 不可能ではない候補の数と、候補ごとの方針リスク(impact 方針のイシュー)の解決数・未解決数。未解決が多い候補から、方針リスクを確かめるタスクを立てる。未解決が 0 の候補は開発の目処が立った候補。表の下の「どの候補にもつかない方針リスク」は、どの案を脅かすかをつなぐ |
| 残っている候補の数(例: センサー 3→1) | 減っていれば、候補が絞れて進んでいる |
| マイルストーン | 見込み日が計画日より遅れていれば、判断してほしいことを台帳に書く |
| 中途半端になっている仕事 | priority 3・4 なのに一部だけ進めたイシュー。続けるか、中止にするかを決める |
| 担当者ごとの数 | 進行中が3件を超えた人、確認を頼まれた数が多い人の仕事を振り直す |

- 目次の件数に色がついている節(中途半端な仕事)から読みます。
- 出荷準備度(目的ごとの、DR で段階2以上になった impact 大のイシューの割合)は、開発の後の方で載せます。既定では載りません。
- 週報に機密の中身は出ません。
- 載せる節を変えたいときは、システム管理者に `report_sections` を直してもらいます。

## 一覧(Bases)のビュー

vault 直下の4つの .base を開き、上のビュー名を切り替えます。個人 vault と共有 vault の両方にあります。

| ファイル | ビュー | いつ |
| --- | --- | --- |
| 00_イシュー一覧.base | priority 順 / impact 未判定 / DR 用 / 台帳用(台帳に入っている) | 次に何をやるか、金曜、DR |
| 00_タスク一覧.base | 進行中・待ち・確認待ち / 確認待ち(確認する人ごと)/ 未着手(期限順) | 手が詰まっている人がいないか |
| 00_設計案一覧.base | 候補の一組(目的・上の設計案ごと)/ すべて(不採用も) | DR で候補を絞るとき |
| 00_ノード一覧.base | value_kind 未分類 / maturity ごと | 金曜、何が検証済みか見るとき |

priority の列は一覧の中で計算しているので、同期プログラムが止まっていても priority 順に並びます。一覧を埋め込んでよいのは台帳だけです。

## プロジェクトが変わるとき

| こと | すること |
| --- | --- |
| 人が増えた・抜けた | 台帳の members を直す。新しい人には 01 から渡す |
| 節目が変わった | 台帳の「期間・主な節目」の表の見込み日を直す。計画日は変えない |
| プロジェクトが終わった | 台帳の status を 完了 にする。ノートは消さない |
| 別のプロジェクトでも使うイシュー | project に両方の名前を並べるか `共通` にする |
