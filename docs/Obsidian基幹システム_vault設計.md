# Obsidian基幹システム vault設計

前提：**1人1vault**ですべての業務を行い、**他人のvaultも参照できる**。アクセス権はvault単位ではなく、ノート単位の機密タグで制御する（7章）。思考過程の記録を一次資産とし、探す工数をゼロに近づける。

---

## 0. 設計原則

本書は「**基幹システム 基本方針**」の8原則に従う。本書（研究・開発の作業環境）で特に重要なのは次の5つ。

| 基本方針の原則 | 本書での現れ方 |
|---|---|
| 1 思考過程と確定事項の両方を資産とする | 個人vaultで考え、プロジェクトリポジトリで確定。IDでつなぐ（1章、6章） |
| 2 データごとに正本を1つ決める | 文書はGit、品目・取引はマスタDB、索引DBは派生物（1章、6.1） |
| 4 思考は自由に、確定は厳格に | 正式化のPR、版固定の引用、機密タグと開示グラント（6章、7章） |
| 7 正しい運用が最も楽な運用になる | ファイル名・IDの自動生成、ワンクリックの引用、従来の探し方が通用するファイル名（3章、6.4） |
| 8 特定の技術に依存しない | Markdown・JSONで保存、AIなしで全機能が動く、Obsidianなしでも閲覧できる（12章、13章） |

## 1. 全体構成

| # | リポジトリ／基盤 | 中身 | 書込権限 | 読取権限 |
|---|---|---|---|---|
| 1 | **個人vault**（1人1つ） | 日々の業務すべて：メモ、検討、図、計算、判断、報告 | 本人のみ | Git直接は本人とサーバのみ。他人はサーバ経由で、機密タグにより判定 |
| 2 | **プロジェクトリポジトリ** | 承認済みの正式文書（要求仕様、DR記録、試験成績、変更記録） | PR経由のみ（承認者がマージ） | プロジェクト関係者 |
| 3 | **共通リポジトリ** | テンプレート、社内規程、設計標準、用語集 | 品質保証・標準化担当 | 全員 |
| 4 | **マスタDB** | 部品、BOM、在庫・発注、試験生データ、計測器・校正 | システム経由 | 権限に応じて |
| 5 | **索引DB・配信サーバ** | 全リポジトリのノート・フレームの索引、リンク関係、引用関係、全文検索、本文配信、開示ビューの描画 | Gitから自動生成 | 機密タグで判定 |
| 6 | **アクセス管理台帳** | 機密タグ、管理責任者、有効期限、個人ごとの権限、開示グラントの索引 | 管理責任者 | — |
| 7 | **AI拡張（任意）** | 自然文検索、要約・チェックの下書き（12章） | — | 機密タグで判定 |

- Gitサーバは社内設置（GitLab／Gitea等）。機密データを外部に出さない
- 個人vaultはObsidian Gitプラグインで自動コミット・プッシュ（例：10分ごと）
- **思考は個人vault、確定は プロジェクトリポジトリ**。正式文書から元の思考ノートへリンクが残るので、判断の経緯をいつでも辿れる

## 2. 個人vaultのフォルダ構成とファイルの置き場所

### 2.1 フォルダ構成

```
vault-<ユーザーID>/
├─ 01_daily/          デイリーノート（作業ログ、その日の起点）
├─ 10_notes/          ノート本体。**新しいノートは全部ここに作る**（種類・案件はプロパティで管理、フラット）。図（図付きノート9.4・ガント図など）もここ
├─ 30_calc/           計算（Pythonスクリプトと結果）
├─ 40_attachments/    添付ファイル（中身はGit LFS）と、その付属ノート（2.3）
├─ 90_templates/      ← 共通リポジトリから配布（直接編集しない）
├─ _refs/             他人のノートのスタブ（読取専用、Git管理外、6章参照）
│   ├─ vault-tanaka/      スタブ（プロパティとリンク先のみ、約1KB/件）
│   └─ pj-X100/
├─ _cache/            開いた本文・引用した図・添付のキャッシュ（容量上限付き、Git管理外）
└─ _private/          （任意）Git管理外の完全ローカルメモ。通常は機密タグで制御する
```

**未整理のメモ（inboxフォルダは置かない）**
- 思いつき・電話メモ・走り書きも 10_notes に作る。作成時に自動で動く既定のテンプレートは「メモ」（id・タイトル・本文だけ）。`type` と `project` は空でよい
- **`type` が空のノート＝未分類**。一覧（Bases の「未分類」）が inbox の代わりになり、デイリーノートに埋め込んで表示する
- **振り分け＝プロパティを入れるだけ**（ファイルは動かさない。リンク・Gitの履歴が乱れない）。育てる（種類・案件を入れる）／やることだけ関係するノートに書き写して消す／寝かせる／消す
- 鍵（access）は空＝本人だけが既定なので、未分類のメモが人に見えることはない
- 目安：未分類は空に近く保つ。2週間を過ぎたものは一覧で目立たせる

**フォルダは「ファイルの性質」だけで分ける**
- 分けるのは、Obsidianのノートではないもの（`30_calc` のプログラム、`40_attachments` の添付）と、拡張機能が場所を決めるもの（`01_daily`）だけ
- ノート・図は種類によらず `10_notes`。図かどうかはファイルの形（`.excalidraw.md`）で分かる
- フォルダを移しても、版を固定した引用は効く（その版でのファイルの場所を、ファイル名末尾のhashで探す）

**フォルダを細かく切らない理由**
- 分類はプロパティとリンクで行い、フォルダ移動でリンクが壊れるのを防ぐ
- 案件別・種類別の一覧はObsidianのBases（データベースビュー）で動的に表示する

### 2.2 ファイルの置き場所

**Gitには「考えの本体（テキスト）」だけを入れ、重いファイルは「引換券」だけをGitに入れる。**

| 種類 | 置き場所 | Gitに入るもの | ノートからの参照 |
|---|---|---|---|
| ノート（.md）、Excalidrawの図（JSON）、計算スクリプト、テンプレート | **Git** | 中身そのもの | `[[…]]` |
| 画像、受け取ったPDF、Excel、CADのスクリーンショットなど | **Git LFS** | 引換券（約130バイト）だけ | `![[…]]`（通常のファイルとして見える） |
| 測定の生データ、動画など、1ファイル100MB超（仮） | データ保管庫 | 何も入れない | 型付きID・URL（例：`[[data:…]]`） |
| CADデータ・図面原紙 | PDM（既存の正本） | 何も入れない | 品番・図番（`[[part:…]]`、`[[doc:…]]`） |
| SVG・PNG・PDF出力などの派生物 | 入れない | — | サーバで元データから生成。ただし試験導入の第1期は、サーバ側の図の描画ができるまで、Excalidrawの自動出力SVGを暫定的にGit LFSで管理する |
| `_refs/`、`_cache/`、`_private/` | 入れない | — | — |

**Git LFSで紐付けが切れない理由**
- 添付の中身はサーバの保管庫に置かれ、Gitには「この場所に、この中身（ハッシュ値）のファイルがある」という引換券だけが入る
- 手元では `40_attachments/` に実際のファイルとして存在するので、`![[画像.png]]` もExcalidrawに貼った画像も、今まで通り表示される。ObsidianやExcalidrawはLFSを意識しない
- 画像を差し替えると引換券が新しくなり、どの版のノートがどの画像を使っていたかもGitの履歴で辿れる

**重いファイルを手元に持たない**
- LFSは、引換券を使うまで中身をダウンロードしない設定にする。開いたノートの添付だけを取得する
- 一時退避（8章）と連動：コールドになったノートの添付は手元から削除して引換券だけを残す。復活すれば再取得

**添付ファイルの名前**
- ノートと同じく `作成日_名前_hash.拡張子`。全社で重複せず、ファイル名から探せる
- 貼り付け・ドラッグ時にプラグインが自動で名前を付ける（2.4）

**Gitの除外設定（最初から登録）**
- `_refs/`、`_cache/`、`_private/`、派生物（SVG・PNG・PDF出力）
- LFSの対象：画像、PDF、Office文書、圧縮ファイルなどの拡張子

**保管庫の管理**
- 差し替え前の古い版も保管庫に残り、容量は増え続ける。記録の保管期限に合わせて古い版の削除ルールを定める（非機能要件 2章）

### 2.3 添付ファイルの機密管理

添付ファイル自体が機密性を持つ場合がある（顧客から受け取った図面、秘密保持契約の対象資料、未公開の測定結果など）。添付ファイルも**ノートと同じ機密タグで管理する**。

**付属ノート**

画像やPDFにはプロパティを書けないため、添付ごとに**付属ノート**（`type: attachment`）を自動で作り、そこに機密タグなどを持たせる。

```
40_attachments/
├─ 260915_A社提供図面_k3m8p.pdf     ← 中身（Git LFS）
└─ 260915_A社提供図面_k3m8p.md      ← 付属ノート（Git）
```

```yaml
---
id: 260915-k3m8p              # 添付のIDは付属ノートのIDと同じ
type: attachment
title: A社提供図面
file: 260915_A社提供図面_k3m8p.pdf
access: [A社-X100-GrA]        # 添付の機密タグ
source: 顧客提供（A社、秘密保持契約 NDA-2026-015）
project: P00042
parts: [123456-AB12]
summary: ""
---
```

- 貼り付け・ドラッグ時にプラグインが付属ノートを自動作成する（2.4）。利用者は普段開く必要はない
- 付属ノートを持つことで、添付も**ノートと同じ仕組み**（ID、索引、検索、機密タグ、引用、退避、開示グラント）でそのまま扱える
- 由来（`source`）を書けば、顧客提供資料などの出所も検索できる

**機密タグの付け方**

| ルール | 内容 |
|---|---|
| 既定値 | 最初に貼り付けたノートの機密タグを、付属ノートに自動でコピー |
| 引き上げ | 添付自体がより機密性が高い場合は、付属ノートのタグを追加・変更する |
| 埋め込み時の継承 | 添付を埋め込んだノートには、添付のタグが必要（引用と同じルール、7.2）。不足時はプッシュ時に警告 |
| 複数のノートから使う | 添付のタグは添付自体に付くので、どのノートから使われても同じ判定になる |

**配信と表示**

- 他人への添付の配信は、ノートと同じく**サーバ経由**。サーバが付属ノートのタグで権限を判定する（LFSの保管庫を直接読めるのは本人とサーバだけ）
- 権限がない場合、ノートやWeb閲覧・PDF出力では添付の位置に「🔒」を表示
- Excalidrawの図に埋め込まれた画像も、画像ごとに判定する。開示グラントでフレームを見せる場合も、埋め込まれた画像にグラントがなければ除外（7.4）
- 添付だけを開示したい場合は、開示グラントの対象に添付のIDを指定できる

**秘密保持契約の終了**

顧客提供資料は、契約終了時に廃棄（返却・破棄）を求められる場合がある。

| タグの期限切れ時の扱い | 内容 |
|---|---|
| 閲覧停止（既定） | 誰も閲覧できなくする。データは保持 |
| 廃棄 | 保管庫から中身を削除し、付属ノートに「廃棄済み（日時・実施者）」を記録。Gitの引換券は残るが、中身は取得できなくなる |

- 廃棄は、タグの管理責任者の承認を得て実施し、記録を残す
- 各端末の `_cache/` と40_attachments/ にある該当ファイルも自動で削除する

### 2.4 添付の自動処理（ドラッグ＆ドロップ・貼り付け）

添付は、MarkdownやExcalidrawへのドラッグ＆ドロップや貼り付けで入れる。この動作をきっかけに、2.2・2.3の処理をプラグインが自動で行う。

**動作の流れ**

1. ファイル名を `作成日_名前_hash.拡張子` に付け替え、`40_attachments/` に保存
2. 付属ノートを作成し、ドロップ先のノート（またはExcalidrawの図）の機密タグをコピー
3. ノートや図に、新しい名前でリンクを挿入
4. 画面の隅に「A社-X100-GrA のタグで保存しました［変更］」と小さく通知

- **確認画面は出さない**。作業の流れを止めず、タグを変えたい時だけ［変更］を押す
- 中身のLFSへの送信は、次の自動コミットの時に行う（オフラインでも作業は止まらない）

**処理を差し込む場所**

| 場面 | 仕組み | 確実さ |
|---|---|---|
| Markdownへのドロップ・貼り付け（スクリーンショットの貼り付け含む） | Obsidianの、エディタへのドロップ・貼り付け時のイベント | ◎ 標準機能 |
| Excalidrawへのドロップ | Excalidrawプラグインのスクリプト用の仕組み（ドロップ時の処理を差し込むフック） | ○ プラグインの版によって変わり得る。**試作で検証** |
| それ以外（ファイル一覧へのドラッグ、OSからのコピー等） | Obsidianの「vaultにファイルが追加された」イベントで後から処理 | ◎ 取りこぼし防止の受け皿 |

- Obsidianの設定で、新しい添付ファイルの保存先を `40_attachments/` に指定しておく
- Excalidrawへのドロップを直接処理できない場合は、受け皿で後から名前を付け替える。その際、**図の中のリンクが追従するか**を試作の最初の確認項目とする

**あわせて行う処理**

| 処理 | 内容 |
|---|---|
| 重複の防止 | 中身のハッシュ値が同じ添付が既にあれば、新しく保存せず既存の添付を再利用する（正本を1つに保つ、基本方針 原則2）。既存の添付のタグが不足していれば、埋め込み時のルール（2.3）で警告 |
| 大きなファイルの振り分け | 100MB超（仮）のファイルは、ドロップ時に警告し、データ保管庫へ送ってリンク（`[[data:…]]`）だけを挿入 |
| 外部資料の由来 | PDFなど社外から受け取りそうな形式の場合だけ、通知に由来（顧客名、契約番号など）の入力欄を出す。入力は任意 |

## 3. ファイル名と識別子（ID）

**役割分担：人はタイトルと日付で探し、システムはhashで辿る。**

フォルダ型管理に慣れた人は「あの文章どこに書いたっけ？」をファイル名と日付から探す。プロパティで絞り込む方法は初学者には難しく、思考の妨げにもなる。そこで、ファイル名は人が読める形にし、一意性はhashで担保する。

### 3.1 形式

```
{作成日YYMMDD}_{タイトル}_{hash}.md

例：260915_X100仮目標値_7k2m9.md
```

- **作成日**：変わらない
- **タイトル**：変更可
- **hash**：作成時に決める5文字の乱数。変わらない

| 項目 | 内容 |
|---|---|
| ID | **作成日＋hash**（例：`260915-7k2m9`）。どちらも作成後に変わらない部分なので、IDは不変 |
| プロパティ `id` | ファイル名と同じIDを持たせる。**正本はプロパティ** |
| hash | 内容から計算する値ではなく、作成時に決める**5文字**の乱数。文字は英小文字＋数字から、読み間違えやすい `0` `o` `1` `l` を除いた32種（約3,355万通り/日） |
| 一意性 | **オンライン時**：作成時にプラグインがサーバから未使用のhashを受け取る（重複ゼロ）。**オフライン時**：手元で乱数を作り、プッシュ時にサーバが確認。重複していたら自動で作り直し、vault内のリンクはObsidianの標準機能で更新（初回プッシュ前＝他人にリンクされる前なので影響なし）。全社で1日5,000件作成しても、オフライン時の重複確率は1件あたり約0.015% |
| 生成 | ノート作成時に、テンプレート（Templaterプラグイン）が作成日とhashを自動で付与し、ファイル名とプロパティ `id` に書き込む。人はタイトルを入力するだけ |
| 抜け道の対策 | 普通の「新規ノート」でもテンプレートが動くよう、Templaterの「作成時に自動適用」をオンにし、フォルダごとの既定テンプレートを設定（10_notes＝検討、01_daily＝デイリー）。図付きノートはテンプレート「検討_図付き」から作る（Excalidrawの「新しい図」ではIDが付かない）。IDのないノートはpush時に拒否 |
| 種類 | ファイル名には入れない（メモ→設計判断のように種類は変わり得るため）。プロパティ `type` で管理 |

### 3.2 タイトル変更とhash消失への対策

| 対策 | 内容 |
|---|---|
| タイトルはプロパティで変更 | `title` を変えると、プラグインがファイル名のタイトル部分を自動で付け替える。ファイル名を直接変えた場合は、逆に `title` を更新する（ファイル名が `title` の先頭40文字と一致している間は、省略された部分を消さない） |
| 食い違いの自動修正 | ファイル名とプロパティ `id` が食い違ったら（hashを消した等）、**プロパティ側に合わせて**ファイル名を自動修正 |
| サーバでの検査 | プッシュ時に、ファイル名のID部分とプロパティ `id` の一致を検査。食い違いは受け付けない |
| 使えない文字 | `/` `\` `:` `*` `?` `"` `<` `>` `\|` `#` `^` `[` `]` は自動で置き換える |
| 長さ | ファイル名のタイトル部分は最大40文字（3.3） |

### 3.3 タイトルの長さ

**プロパティとファイル名で長さを分ける**

| 対象 | 上限 | 扱い |
|---|---|---|
| プロパティ `title` | 100文字 | 書く側は文字数を気にせず付けられる |
| ファイル名のタイトル部分 | 40文字 | `title` の先頭40文字を自動で使う。超えた分はファイル名から省く |
| 推奨 | 20〜30文字 | 30文字を超えたら入力中に目安を表示 |

**40文字にする理由**
- ファイル名の上限は多くのファイルシステムで255バイト。日本語は1文字3バイトのため、約80文字が物理的な限界
- Windowsは標準でパス全体が260文字まで。`_refs/` や `_cache/` の下に置かれる分も含めて余裕を持たせる
- Obsidianのファイル一覧やタブで見えるのは日本語20〜30文字程度。長すぎるとファイル名から探す利点が薄れる

**良いタイトルの目安**
- 「**何の・何を**」を先頭に置く（例：「X100ブラケット材質選定」）。ファイル名が切れても先頭で区別できる
- 詳しい内容は `summary` に書く

### 3.4 リンクの解決

- **自分のvault内**：タイトルを変えてファイル名が変わっても、Obsidianの標準機能でvault内のリンクは一括更新される
- **他人のvaultから（購読者）**：所有者がタイトルを変えると、購読者のプラグインがスタブのファイル名を変更し、Obsidianの標準機能でそのスタブへのリンクも一括更新される
- **最後の砦はhash**：リンク先の文字列には必ずhashが含まれる。タイトル部分が古くなっていても、プラグインがhashで索引DBを引いて正しいノートを開き、リンクの修正も提案する
- **リンクの表示**：表示テキストは書かず、プラグインが閲覧者の権限に応じてタイトルを表示する（7.3）

### 3.5 フレームと版の指定

```
260915_X100仮目標値_7k2m9#F01           ← フレーム指定
260915_X100仮目標値_7k2m9#F01@a1b2c3d   ← フレーム＋固定したコミット
```

フレームIDもノート内で不変。システム内部では `260915-7k2m9#F01` のようにIDで管理する。

## 4. ノートの種類

思考の流れ「**情報を集める → 考える → 整理する → 結論を出す → 説明する → 行動する**」に沿って定義する。

| 種類 | type | 用途 | 思考の段階 | 正式化先 |
|---|---|---|---|---|
| デイリー | `daily` | 作業ログ、その日の起点 | 記録 | — |
| 週ノート | `weeknote` | 1人1週。今週のねらい・週報の記入欄・終わったやること・来週の予定・ふりかえり。本人だけ。週報の欄は金曜に案件ごとの週報（`weekly`、工程管理 10章）に分けて出す | 記録 | — |
| メモ | `memo` | 断片的な気づき、情報の抜き書き | 集める | — |
| 議事録 | `meeting` | 打合せ記録、決定事項 | 集める | 必要に応じて |
| 検討 | `study` | 構想・比較・解析（Excalidraw中心） | 考える・整理 | — |
| 計算 | `calc` | 計算スクリプトと結果の説明 | 考える | 試験・判断の根拠として |
| **設計判断** | `decision` | 何を・なぜ決めたか | 結論 | ○ |
| 要求 | `req` | 要求1件＝1ノート | 結論 | ○ |
| DR記録 | `review` | デザインレビューと指摘 | 結論 | ○ |
| 試験 | `test` | 試験計画・結果・合否 | 結論 | ○ |
| 課題・不具合 | `issue` | 不具合、原因、是正処置 | 行動 | ○ |
| 変更要求 | `ecr` | 設計変更の要求と影響評価 | 行動 | ○ |
| 報告 | `report` | 説明用（スライドショー、PDF出力） | 説明 | 必要に応じて |
| 図 | `drawing` | 文章を持たない図だけ（ガント図など）。検討の図は**図付きノート**（9.4）にする | 全段階 | 埋め込み先に従う |
| 添付の付属ノート | `attachment` | 添付ファイルの機密タグ・由来（2.3）。自動作成 | 全段階 | — |
| 開示グラント | `grant` | 機密フレームの部分開示の許可（7.4） | 説明 | — |
| コメント | `comment` | 資料へのコメント。担当・期限を付けると「やること」（指摘）になる（7.10） | 行動 | — |

## 5. プロパティ設計

### 5.1 全ノート共通

```yaml
---
id: 261003-k4p8r           # ファイル名：261003_ブラケット材質選定_k4p8r.md
type: decision
title: ブラケット材質選定   # 最大100文字。ファイル名には先頭40文字を使用
aliases: [ブラケット材質選定]
owner: yu
project: P00042           # 案件ID（案件台帳で採番。なければ空）
status: draft            # draft / review / approved / obsolete
access: [A社-X100-GrA]   # 機密タグ（台帳登録済みのみ、複数はAND）。なし＝本人のみ。社内公開は [社内]
created: 2026-10-03
updated: 2026-10-03
summary: ""              # 3行程度の要約（退避時のスタブに使う。設計判断・報告・検討では必須）
tags: []
---
```

### 5.2 関係プロパティ（トレーサビリティの骨格）

本文中のリンクに加え、**意味のある関係**はプロパティで持たせる。一覧・ルールでの追跡が確実になる（AIを使う場合も精度が上がる）。

| プロパティ | 意味 | 例 |
|---|---|---|
| `derived_from` | このノートの元になった要求・情報 | 設計判断 → 要求 |
| `based_on` | 根拠にした検討・計算・試験 | 設計判断 → 計算、検討 |
| `verifies` | 検証対象の要求 | 試験 → 要求 |
| `affects` | 影響する品目・図面（マスタDBのID） | 変更要求 → 部品番号 |
| `supersedes` | 置き換えた旧ノート | 新判断 → 旧判断 |
| `promoted_to` | 正式化した先（プロジェクトリポジトリのID） | 個人ノート → 正式文書 |

### 5.3 種類別の主な追加プロパティ

**設計判断（decision）** ― 思考過程を残す中核

```yaml
options: [SUS304, A5052, SPCC]
chosen: A5052
decided_by: yu
decided_on: 2026-10-03
derived_from: [[260915_ブラケット耐荷重要求_m3x7q]]
based_on: [[261001_ブラケット強度計算_b9t2w]], [[260928_ブラケット構想比較_h6n4z]]
```

本文テンプレート：
1. 背景・目的
2. 選択肢と評価（Excalidrawの比較図を埋め込み）
3. 結論と判断理由
4. 却下した選択肢と理由 ← **最も失われやすく、最も価値がある情報**
5. 前提条件（これが変わったら再検討）

**検討・報告（study / report）** ― 管理職向けの状況表示に使う（基本方針 7.4）

```yaml
progress: 検討中        # 検討中 / レビュー待ち / 完了 / 保留
next: 案Bの応力解析     # 次にやること（1行）
```

**要求（req）** ― 前回整理した必須属性16項目をプロパティ化（出所区分、合否判定基準、検証方法、未達時の影響度など）

**試験（test）**

```yaml
verifies: [[260915_ブラケット耐荷重要求_m3x7q]]
result: pass             # pass / fail / conditional
instruments: [GAUGE-0123, TC-0456]   # マスタDBの計測器ID（校正期限を自動チェック）
raw_data: db://test/2026/1003-001    # 生データはマスタDB
```

**課題・不具合（issue）**

```yaml
severity: major
root_cause: ""
corrective_action: ""
effectiveness_check: pending   # 是正処置の有効性確認（ISO 10.2）
```

### 5.4 プロパティを追加する時の決まり

プロパティは仕事に合わせて育ててよい。ただし決まりなく足すと、次の不整合が起きる。

| 不整合 | 例 | 困ること |
|---|---|---|
| 同じ意味の名前が乱立 | `due`・`deadline`・`期限` | 検索・一覧（Bases）で拾い漏れる |
| 値の書き方がばらばら | `2026/10/5` と `2026-10-05`、品番の大文字・小文字 | 並べ替え・比較ができない |
| 型がぶつかる | あるノートでは文字、別のノートでは一覧 | Obsidianはvault全体で1つの名前に1つの型を持つため、表示が崩れる |
| 正本が二重になる | 品名・顧客名をプロパティに写す。`owner` と別に `担当者` | 元が変わっても古い値が残る |
| **機密が漏れる** | `customer: A社` | 他人に配るスタブ（6章）はプロパティを持つ。本文を鍵で隠しても顧客名が見える。配ったスタブは戻せない |
| システムの名前とぶつかる | 自分の意味で `status`・`type` を使う | 承認・集計・権限の判定が狂う |
| 移行で取りこぼす | 構成を変える時に知らない名前がある | 変換スクリプトが意味を扱えない |

#### 追加してよいレベル

| レベル | 例 | 誰が足せるか | 決まり |
|---|---|---|---|
| 0. システム予約 | id, type, title, owner, project, access, status, created, updated, summary, 関係（5.2）, parts, tool, env など | 足せない・意味を変えない | 誤用はpush時に拒否 |
| 1. 全社共通 | 試験の判定結果、要求の重要度など、ISO・品質で集計するもの | タグ台帳（registry）に登録して足す | 名前・型・取りうる値・説明・**スタブに載せるか**を決める |
| 2. 部署・案件の共通 | 試験装置、材料、評価条件など | 台帳に「使う範囲」付きで登録 | レベル1と同じ。範囲の外では使わない |
| 3. 個人 | 自分用の印、作業の分類 | **自由** | 名前の頭に `my_`。検索・集計の対象外、スタブ・Web閲覧に出さない、移行ではそのまま残す |

#### 判断の目安

- 他人が検索・集計に使うなら台帳に登録する（レベル1・2）。自分だけなら `my_` を付けて自由に足す（レベル3）
- 他のシステムに正本があるもの（品名・顧客名・価格）はプロパティに写さない。型付きIDで参照する（`[[part:…]]`）
- 顧客名・機密に関わる値はプロパティに書かず本文に書く（本文は鍵で守られる）
- 台帳の登録例：

```yaml
properties:
  test_result: {type: text, values: [合格, 不合格, 保留], scope: 全社, stub: true, desc: 試験の判定}
  material:    {type: text, scope: P00001, stub: false, desc: 評価した材料}
```

#### 仕組みで支えること

- push時の検査（ID体系 5章）：台帳にない名前（`my_` 以外）・型や書き方の違反は警告、予約名の誤用は拒否、プロパティ値に顧客名リストの語があれば警告
- **スタブに載せるのは、予約名と台帳で `stub: true` のものだけ**。それ以外のプロパティは他人に配らない
- **昇格**：`my_` のプロパティを何人も使い始めたら、台帳への登録を提案する。名前を変える時は変換スクリプトで一括変換し、旧名は別名として残す
- vaultに構成の版（`.rdnb/schema`）を置き、構成を変える時は変換スクリプトがその版から変換する

## 6. 他人のvaultを参照する仕組み

他人のvaultを丸ごと同期すると容量を圧迫するため、**本文は同期せず、索引（メタデータとリンク関係）だけを索引DBに集約し、本文は必要な時に取得する**。

### 6.1 索引DB

**原則**
- **正本はGit、索引DBは派生物**。各vaultへのプッシュをきっかけ（Webhook）にサーバがノートを解析し、索引DBを更新する。DBが壊れてもGitから再構築できるため、二重管理にならない
- **キーはノートID（作成日＋hash）**。プロパティ `id` とDBのIDが常に1対1で紐付く。タイトル変更でファイル名が変わっても、IDは変わらない（3章）

**索引DBに持つもの**

| 対象 | 主な項目 |
|---|---|
| ノート | ID、タイトル、種類、所有者、案件、状態、公開範囲、プロパティ一式、Gitのリポジトリ・パス・最新コミット、内容ハッシュ |
| フレーム（Excalidraw） | フレームID、所属ノートID、フレーム名、フレーム内の文字、フレーム内のリンク |
| リンク関係 | リンク元ID → リンク先ID、関係の種類（`derived_from` 等のプロパティ／本文リンク） |
| 引用関係 | 引用元（ノート／フレーム）ID、固定したコミット、引用先ノートID |
| 検索索引 | 全文検索索引（AI拡張を使う場合のみ、ベクトル検索索引を追加） |

本文、画像、Excalidrawの図データそのものは持たない（Gitから配信する）。

### 6.2 手元のvault側の動き

- **スタブ（軽量な代理ファイル）**：購読範囲のうち閲覧権限のあるノートについて、プロパティとリンク先だけを書いた約1KBのファイルを `_refs/` に生成する。Obsidianのリンク解決・グラフ表示・被リンクがそのまま動く（1万ノートでも約10MB）
- **本文は開いた時に取得**：スタブを開くと、カスタムプラグインがサーバから本文を取得して表示し（サーバは配信時に機密タグの権限を判定、7章）、`_cache/` に保存する。キャッシュは容量上限付きで、古いものから自動削除
- **Excalidrawと添付は同期しない**：容量の大半を占めるため、閲覧はサーバ側でSVG化したものを表示する。引用した図だけ取得する（6.4参照）
- **オフライン**：キャッシュ済み以外は読めない。出張等に備え、案件単位で「オフライン保持」を指定できるようにする

### 6.3 参照の3段階

**レベル1：閲覧・検索（取り込み不要）**
- 索引DBで、権限のある全vaultを全文検索・プロパティ検索・閲覧
- 例：部品IDで検索すれば、その部品について過去に誰が何を検討したかが全員のvaultから一覧できる（AI拡張があれば自然文でも質問可）
- Webビューアで他人のノートや図を表示

**レベル2：購読・リンク（スタブを生成）**
- 参照したいvault・プロジェクトリポジトリを「購読」すると、`_refs/` にスタブが生成される
- IDが全社一意なので、`[[260801_筐体材料選定_r5c2v]]` のように**自分のノートから直接リンク**できる
- 購読はvault単位またはプロジェクト単位
- 未購読のIDへのリンクは、プラグインがサーバに問い合わせてプレビュー表示、ワンクリックで購読

**レベル3：正式化（プロジェクトリポジトリへのPR）**
- 個人vaultのノートを、プロジェクトリポジトリへプルリクエストで提出
- 承認者のレビュー・マージで `status: approved` の正式文書になる
- 元の個人ノートには `promoted_to` が付き、正式文書から思考過程へ辿れる

### 6.4 他人のExcalidrawの引用

他人の図を引用する場面は多い。例：要求仕様の担当者が書いた**仮目標値**に対し、設計技術者が検討してレポート（スライド風Excalidraw）にまとめる場合、レポートの1枚目は仮目標が書かれたスライドの引用になる。

**フレーム単位で引用する**
- Excalidrawのフレーム（スライドに相当する枠）単位で、別の図を埋め込む
- 引用される側は、引用されそうな内容（仮目標、前提条件など）を**1フレーム1テーマ**でまとめておく
- フレームにもIDを付与し、索引DBに登録する

```
260915-7k2m9#F01      ← ノートID＋フレームID（3.5）
```

- フレーム内の文字も索引するので、「X100 仮目標」で検索すればそのスライドが見つかる

**引用時に版を固定する**
- 引用した瞬間のコミットに固定したスナップショットとして取り込む
- 相手が後で書き換えても、レポートの1枚目は「検討の前提にした値」のまま残る（根拠の記録として必須）
- 取得するのは**引用したフレームを含む図だけ**。容量は引用した分で済む

**引用の記法（例）**

```markdown
![[260915_X100仮目標値_7k2m9#F01@a1b2c3d]]   ← @以降が固定したコミット
```

**引用元が更新された時**
- 索引DBが「どのノートが、どのフレームの、どの版を引用しているか」を把握しているので、**引用元が更新された瞬間に、引用しているノートの作成者へ通知**する
- 引用箇所に「引用元が更新されています」と表示し、固定版と最新版を並べて比較できる
- 確認後、「最新版に更新」または「固定版のまま（理由を記録）」を選ぶ
- 仮目標が変わったのに古い値のまま設計検討が進む手戻りを、構造的に防ぐ（ISO 8.2.4、8.3.6）

**図と数値を二重に持つ**
- 仮目標の数値そのものは、要求ノートのプロパティにも持たせる
- スライドは人が見るための引用、プロパティは機械が追うための値
- レポートのノートには `derived_from` で要求IDも記録し、目標値（プロパティ）と検討結果の比較をルールで自動チェックできるようにする（12.2）

**ノートの引用・リンクにも同じ考え方を適用**
- 通常のリンク `[[ID]]` は最新版を指す
- 正式文書から根拠ノートを参照する場合は、コミットを固定したリンク `[[ID@コミット]]` にする

### 6.5 他人のノートへの意見・指摘
- 他人のノートは直接編集しない
- 自分のvaultにノートを作ってリンクする。意見・指摘は**コメント**（7.10）として書く
- 索引DBが**他vaultからの被リンク・引用**を集計し、相手のObsidianに表示（カスタムプラグイン）→ 自分のノートや図が誰にどう参照されているか分かる

## 7. アクセス制御と開示

個人は複数の案件で秘密保持の責任を負っており、デイリーノートはそれらすべてへリンクできないと意味をなさない。案件ごとにvaultを分けるとフォルダ分け運用と変わらず、思考の妨げになる。そこで、**1人1vaultのまま、ノート単位のタグでアクセスを制御する**。

### 7.1 原則：Gitを直接読ませず、サーバが配信時に判定する

- 個人vaultのGitリポジトリを直接読めるのは**本人とサーバだけ**
- 他人のノートの本文・図は、すべてサーバ経由で取得する（6.2のオンデマンド取得）。サーバは配信のたびに、閲覧者がそのノートのタグ権限を持つか判定する
- これにより「Gitの権限はリポジトリ単位」という制約が消え、vaultの分け方とアクセス権を切り離せる
- vaultを分けるのは、チームで共同編集する場合（プロジェクトリポジトリ等）に限る

### 7.2 機密タグ

ノートのプロパティ `access` に機密タグを付ける。

```yaml
access: [A社-X100-GrA]      # 複数指定時はAND条件（すべての権限が必要）
```

**タグ台帳（管理サーバ）**

| 項目 | 内容 |
|---|---|
| タグ名 | 例：A社-X100-GrA限定 |
| 管理責任者 | 権限付与・開示承認を行う人（必須、7.7） |
| 代理 | 管理責任者が不在の時に権限付与・開示承認を行う人（必須、7.7） |
| 有効期限 | 秘密保持契約の期間など |
| 存在の秘匿 | オンにすると、権限のない人にはリンク自体を表示しない |
| AI利用可否 | 不可のタグのノートはAI拡張に一切渡さない |
| PDF出力可否 | 不可のタグのノートはPDF出力できない（9.3） |
| 権限保持者 | 個人ごとにアクセス可能なタグを管理（人事・案件アサインと連動） |

**判定ルール**

| ルール | 内容 |
|---|---|
| 自由記述禁止 | タグは台帳に登録されたものだけ使える。未登録タグはプッシュ時にエラー |
| 複数タグはAND | A社とB社の両方を含むノートは、両方の権限を持つ人だけが読める |
| 添付も同じ判定 | 添付ファイルは付属ノートのタグで判定。埋め込んだノートには添付のタグが必要（2.3） |
| タグなし＝本人のみ | 誤公開を防ぐ。社内公開したいノートは `access: [社内]` を明示 |
| 引用は制限を引き継ぐ | 機密ノート・フレームを引用したノートには、引用元のタグが必要。不足時はプッシュ時に警告 |
| 索引DBも同じ判定 | 検索結果、タイトル、プロパティ、被リンク表示もすべて閲覧者の権限で絞る |
| AIも同じ判定 | AI拡張を使う場合、AIが使えるのは質問した人が読めるノートだけ（12.3） |

### 7.3 デイリーノートとリンクの表示

- **デイリーノートは本人のみ**（`access` なし）。全案件へのリンクを持てるので、思考が途切れない
- **リンクの表示は閲覧者の権限で変える**：権限のない人には、タイトルを出さず「🔒 アクセス権なし」と表示
- リンクの表示テキストにタイトルを直接書くと漏れるため、表示テキストは書かず、プラグインが権限に応じてタイトルを表示する
- 「存在の秘匿」タグの付いたノートへのリンクは、権限のない人には何も表示しない

### 7.4 部分開示：開示グラント

**課題**：権限のない人が、機密資料の一部だけを必要とする場面がある。
例：特定技術の実験者が実験報告をまとめる際、製品戦略のうち該当項目の目標値だけが必要だが、製品戦略そのものは見せたくない。

**コピーで渡さない理由**：スクショやコピペで派生資料を作ると、元資料が更新されても追従できず、データが追えなくなり、無駄なデータが増え続ける。

**解決策**：元のフレームそのものに対して、**開示グラント（開示許可）**を発行する。サーバが許可の範囲だけを描画して渡すので、閲覧者は元データに一切触れない。データの源は1つのまま、更新も追従できる。

#### 開示グラントの項目

グラントは機密側のノート（`type: grant`）として作成し、版管理する。誰が・何を・いつ・誰に・なぜ開示したかが監査証跡として残る。

```yaml
---
id: 261004-w2j6d
type: grant
access: [A社-X100-GrA]            # グラント自体は機密側
target: 260915-7k2m9#F03        # 開示するフレーム（ID指定）
target_props: [target_value]      # プロパティ単位の開示（任意）
audience: [X100-実験Gr]           # 開示先（タグまたは個人）
purpose: 材料Aの耐熱試験の目標値として
update_policy: reapprove          # reapprove（再承認） / follow（自動追従）
approved_version: a1b2c3d         # 承認した版
approved_by: suzuki               # タグの管理責任者
expires: 2027-03-31
---
```

#### 流れ

**開示の単位**：ノート、フレーム、添付のいずれか。ノートを開示すると、そのノートの本文が承認時点の版で見える。ノートに埋め込まれた他の図・画像は、それぞれの鍵の判定に従う（必要なら同時に開示する）。

開示は3つの入口から始まる。

- **管理責任者の判断**：タグの管理責任者（または代理）が、申請を待たずに、自分の判断で開示範囲を変更する（Web閲覧の「開示範囲」タブ。ノートを選び、開示先とコメントを入れ、確認ポップアップで許可）。ノートの作成者には変更を通知する
- **閲覧者からの依頼**：権限のない人が、鍵の付いた資料に表示される「開示の相談先」（7.7）に依頼する
- **作成者からの申請**：資料の作成者が、報告の公開範囲を広げる時などに、見せてよい資料を自分で選んで申請する

1. 作成者（または権限を持つ人）が、見せてよい**フレーム・添付**を選んで**開示申請**を作る（`type: grant`）。選んだフレームに埋め込まれた画像は、自動で申請の対象に加える
2. タグの管理責任者（または代理）が、Web閲覧の**開示申請タブ**で一括処理する（7.4.1）
3. 承認された資料だけが、開示先の人に**承認時点の版**で見えるようになる
4. 閲覧者は開示された資料を引用して報告などを書ける

#### 7.4.1 開示申請の一括処理画面（承認者用）

承認者は、内容を確認してから判断する。**判断の前に権限の許可などを求めない**（2周目の試作で確認した順序）。

| 要素 | 内容 |
|---|---|
| 申請の一覧 | 申請ごとに、申請者・開示先・目的・状態（未処理／承認済み／却下）を表示 |
| 資料ごとの表示 | **プレビュー**（フレームの描画・画像）、チェックボックス、**「開示範囲 変更前 → 変更後」**の文字列（例：`P00001-team → 社内`） |
| 一括選択 | 「すべて選択」で全件をまとめて処理。一部だけ外して承認することもできる |
| 見られるタグ | 資料ごとに「見られるタグ」をチェックボックスで表示する（元の鍵と、開示先のタグ）。チェックを付けると開示、外すと開示の取り消し。**外すと操作している本人が見られなくなるタグは外せない**（灰色で表示） |
| 確認項目 | よくある理由をチェック項目で用意する（例：**顧客情報なし**）。項目は台帳で追加できる |
| コメント | 確認項目にチェックがない場合は**必須**（承認・却下とも）。理由がないと確認に進めない |
| 確認ポップアップ | 「開示範囲」の文字列または確認ボタンを押すと表示。選んだ資料の変更前→変更後の一覧とコメントを示し、**「許可する」で確定** |
| 記録 | 判断（承認／却下）、対象、理由、承認者、日時、承認版を開示申請ノートに記録し、監査証跡とする |

#### 閲覧時の動き

1. 閲覧者のプラグインが、埋め込まれたフレームの描画をサーバに要求
2. サーバは閲覧者のタグ権限を確認。権限がなければ、該当するグラントを探す
3. グラントがあれば、Gitから承認済みの版の図を読み、**そのフレームだけを描画したSVG**を返す
4. グラントがなければ「🔒 アクセス権なし」

**サーバ側の無害化（必須）**
- 図のJSONは絶対に渡さず、描画結果（SVG）だけを返す
- フレーム外の要素、要素に張られたリンク、メタデータを削除
- 入れ子で埋め込まれた別の図・画像は、それぞれにグラントがなければ除外
- 開示ビューには閲覧者名の透かしを入れる

#### 元資料が更新された時

更新されたフレームに、新しい機密情報が書き足される可能性があるため、慎重に扱う。

| update_policy | 動き | 使いどころ |
|---|---|---|
| `reapprove`（既定） | 承認済みの版を表示し続ける。グラント作成者に差分付きで通知 → 承認で新しい版を開示 → 閲覧者に引用元更新の通知 | 通常の機密フレーム |
| `follow` | 更新に自動追従 | **開示用フレーム**（最初から外部に見せる前提で作ったフレーム） |

**推奨運用**：機密資料の作成者が、資料の中に**開示用フレーム**を最初から用意しておく。例えば製品戦略の資料の中に「実験者向けの目標値」フレームを作り、`follow` で開示する。データの源は1つのまま、更新も自然に伝わる。

#### 開示ビューを再引用した場合

- 開示ビューを引用したノートには、元のタグではなく**グラントの開示先タグ**が自動で付く
- 開示範囲の外への再配布を防ぐ。さらに広く共有するには新しいグラントが必要
- 逆方向（実験結果を戦略側が引用する）は、情報が上位に流れるだけなので制限不要

#### トレーサビリティ

- 権限のある人：報告 → 派生ノート／開示ビュー → 製品戦略 と辿れる
- 実験者：開示ビューまでしか見えない
- 引用元更新の通知が、機密を越えずに連鎖する

### 7.5 スクショ・コピペ対策

技術的に完全には防げないため、抑止と動機付けで対応する。

- 開示ビューへの閲覧者名の透かし（撮影されても出所が分かる）
- **リンクの方が楽で正確にする**：常に最新、引用はワンクリック。正しいやり方が一番楽な状態にすることが、データを追える状態を保つ近道

### 7.6 端末と権限の取り消し

- 本人のvaultには全案件の機密が入るため、**ディスク暗号化は必須**
- 異動・契約終了で権限が外れたら、その人の `_cache/` にある該当ノート・図・添付を自動削除
- グラントの有効期限が切れたら、開示ビューは「🔒 アクセス権なし」に戻る

### 7.7 鍵の管理者台帳と開示の相談先

鍵（機密タグ）の付いた資料を権限のない人が見た時、**誰に相談すれば見られるか**が分からないと、開示の依頼が起きず、コピーやスクショでの回避を招く。そこで、鍵の管理者を台帳にまとめ、鍵の位置に相談先を表示する。

#### 台帳の要件

| 要件 | 内容 |
|---|---|
| 管理責任者と代理は必須 | すべての機密タグに、管理責任者と代理の両方を登録する。どちらかが空のタグは登録できない |
| 1つの台帳にまとめる | タグごとの管理責任者・代理・有効期限・PDF出力可否・AI利用可否・対象ノート数を、アクセス管理台帳で一元管理する |
| 引き継ぎ | 異動・退職時は、管理責任者・代理を引き継ぎ先に変更してから権限を外す。空席のまま残さない |
| 定期点検 | 管理責任者が不在（退職・長期不在）のタグ、期限切れのタグを定期的に一覧化し、品質保証・情報管理部門が是正する |
| 一覧の公開 | 「存在の秘匿」タグを除き、鍵の管理者一覧を社内に公開する（Web閲覧の「鍵の管理者」タブ） |

#### 鍵の位置に表示する内容

| 場所 | 表示 |
|---|---|
| 本文中の鍵 | 🔒とタイトル（フレームはフレームの名称のみ）。🔒を押すと、必要な鍵と開示の相談先（管理責任者・代理）を表示 |
| タイトルも秘密のタグ | タグ台帳で「タイトル非公開」を設定したタグは、タイトルの代わりに「（タイトル非公開）」と表示（顧客名を含む議事録など） |
| ノートの先頭 | 「このノートには、閲覧できない資料が N 件あります」と相談先をまとめて表示 |
| 報告の補足資料一覧 | 見えない補足資料ごとに相談先を表示 |
| 存在の秘匿タグ | 何も表示しない（相談先も出さない） |

- 複数のタグが付いた資料は、不足しているタグすべての相談先を並べる


### 7.8 管理職向けの公開範囲表示

管理職（タグの管理責任者・代理）が、**一般社員からどう見えているか**を自分の画面で把握できるようにする。

| 場所 | 表示 |
|---|---|
| ノートの先頭 | 「公開範囲 P00001-team ＋開示 社内 ・ 一般社員から見える／見えない」 |
| 埋め込まれた図・フレーム・画像 | 資料ごとに同じ表示を見出しとして付ける |
| 案件の一覧 | ノートごとに同じ表示 |

- 一般社員から見える資料と見えない資料を色で区別する
- 管理職以外の画面には表示しない

### 7.9 版の表示と再承認の依頼

**版の表示**
- ノートのヘッダー、引用した図・フレーム、開示された資料には、表示している版の**更新日時（分単位）**を出す。版番号（コミットのhash値）は直接出さない
- 新しい版がある場合は、日時に「＋」を付ける。フレームは、そのフレームの中身が変わった時だけ「＋」を付ける
- 日時を押すと、表示中の版のhash値・コミットした人・日時を表示。新しい版があれば、最新版の同じ情報も表示
- 時刻まで出すのは、同じ日の中の更新を区別するためと、**コミットし忘れ（最新が反映されていない）に気づけるようにする**ため

**再承認の依頼**
- 開示した資料が更新されると、一般社員には開示時点の版を表示し続け、承認者の開示申請タブに**再承認の依頼**を自動で並べる
- 依頼には、開示中の版と最新版の日時、更新した人、変更点（ノートは差分、フレームは最新のプレビュー）を表示する
- 承認者は確認項目・コメントを入れて最新版を開示する。承認しない限り、一般社員には古い版のまま

### 7.10 コメント（指摘を含む）

資料への意見・質問・指摘は、チャットや口頭に流さず、**資料に紐づくコメント**として残す。**見られる人は誰でも書ける**（上司に限らない）。担当・期限を付けたコメントは**やること**になり、相手に届く（＝指摘）。後から「誰に何を言われ、どう直したか」を辿れる（ISO 9001 8.3.4 レビュー、7.5 記録）。

| 種類 | 中身 | 届き方 |
|---|---|---|
| コメント | 意見・質問・メモ | 対象の資料に表示。資料の担当者に通知 |
| やること（指摘） | コメント＋担当・期限 | 担当者のやること一覧に届く。対応済みにするまで残る |

**書き方（Obsidian、Web閲覧の両方）**
- すべてのノートの上部に「＋ コメント」。図はフレームごとにも「＋ コメント」
- 対象を選ぶ：ノート全体／図のフレーム／埋め込んだ添付／引用したフレーム（他人の図でも可）。**自分が見られるものだけ**
- 入力：内容（必須）、**画像**（任意・複数。選ぶ・ドロップ・貼り付け。スクショに赤ペン等）
- 「やることにする」にチェックすると、担当（既定は資料の担当者）と期限（既定は1週間後）を付けられる

**保存と鍵**
- コメントのノート（`type: comment`）を**書いた人のvault**に作る（他人のノートは書き換えない）。画像は添付の自動処理（2.3）で保存
- 鍵は**書いた人がその資料を見ている範囲**：
  - 元の鍵で見ている人（案件メンバー）のコメント → 資料と同じ鍵（チーム限定なら、チームの中だけで見える）
  - 公開された版を見ている人（一般社員など）のコメント → 公開先の鍵（例：社内）
  - 見られない資料にはコメントできない
- やることはObsidian Tasksの書き方：
  ```
  - [ ] 荷重条件の根拠を追記 📅 2026-10-11 [assignee:: user:yamada] [about:: 261004-gzz7r#F02]
  ```

**表示**
- 対象のノートの上部に「コメント（n件・未対応のやること m件）」。未対応のやることを先頭に。フレームには「コメント n」の印
- 「コメント」タブ：あなたのやること → 未対応のやること（期限の近い順） → コメント・対応済み
- 担当者のデイリーノートの「やること」一覧に、届いたやることも並ぶ（サーバの索引から集める。Obsidian Tasksは自分のvaultしか見ないため）

**閉じ方**
- やること：担当者が直して「対応済み」にする（対応したノート・版を添える）→ 書いた人が確認して閉じる。差し戻しもできる
- コメントへの返信は、そのコメントを対象にしたコメントとして書く（同じ鍵の範囲）
- 工程タスクに紐づくやること（`task::`）は、工程管理の「やること」の数に入る

## 8. vaultの軽量化：一時退避と復活

業務量が増えるとvaultが巨大化し、読み込みが遅くなる。アクセスの少ないノートや終了案件のノートを手元から**一時退避**して、速度を維持する。

**大前提：退避は削除ではない**。本文を手元から外すだけで、データはGitと索引DBに全て残る。**いつでも、どのレベルからでも、同じIDのまま元に戻せる**。手元の机から一時的に片付けるだけの操作であり、倉庫送りではない。

### 8.1 仕組み

自分のノートにも、他人のノート参照と同じ**スタブの仕組み**（6.2）を使う。退避したノートは本文を外して約1KBのスタブに置き換え、開いた時だけサーバから取得する。仕組みが1つで済み、リンクも検索も壊れない。

### 8.2 保管レベル

| レベル | 手元にあるもの | 対象 |
|---|---|---|
| **ホット** | 本文・図・添付すべて | 進行中の案件、最近開いたノート |
| **コールド** | スタブのみ（本文は開いた時に取得） | 長期間開いていないノート、終了案件のノート |
| **アーカイブ** | 何も置かない（索引DBにだけ存在） | 終了から年単位が経った案件 |

**コールドのスタブの中身**
- プロパティ一式、リンク先、フレーム一覧
- **要約**：ノートの `summary` プロパティ（作成者が書く。設計判断・報告・検討ではテンプレートで必須）。未記入なら本文冒頭の段落を自動抽出
- → グラフ表示・被リンク・Basesの一覧はそのまま動く。全文検索は索引DB側で効くので、アーカイブ済みも検索で見つかる

### 8.3 退避の判定

| 判定 | 内容 |
|---|---|
| 案件の終了 | 案件マスタで「終了」にすると、その案件のノートが一括でコールド候補 |
| アクセス履歴 | プラグインが本人の閲覧履歴を記録。一定期間（例：半年）開いていないノートを候補に。他人の参照はサーバ経由なので判定に含めない |
| デイリーノート | 数か月経ったら月単位でコールドへ |
| 優先度 | 大きなExcalidraw・添付を多く含む終了案件から優先（重さの主因はMarkdownより図・添付・Git操作） |
| 除外 | ピン留めしたノートは退避しない |

週1回、候補をまとめて提示し、本人が確認して実行する。慣れたら自動実行に切り替え可能（取り消し可）。

### 8.4 復活

| 方法 | 内容 |
|---|---|
| ノート単位 | スタブ上の「復活」ボタンで、本文・図・添付をまとめて手元に戻す |
| 案件単位 | 案件名を指定して一括復活。終了案件の再開・流用設計の時に。件数が多い場合は裏で順次取得 |
| 検索から | 索引DBの検索結果（アーカイブ含む）から、そのまま復活 |
| 編集で自動 | コールドのノートを編集しようとした瞬間に自動で復活（本文を取り戻してから編集するので食い違わない） |
| 一覧から | 退避中のノートを案件別・時期別に一覧表示し、選んで復活 |
| 先回り | 出張などオフラインで必要な案件は、事前に案件単位で復活 |

**復活の約束**
- IDとリンクは変わらない。他人からのリンク・引用も、退避中・復活後を問わず切れない
- アーカイブからも、コールドを経由せず直接ホットへ戻せる
- 開くだけなら復活しない（キャッシュで表示）。復活したら閲覧履歴が更新され、すぐ再退避されることはない

### 8.5 Git側の対策

手元からファイルを外しても、Gitの履歴に過去の版が残りリポジトリは膨らむ。

- **部分クローン**：手元のvaultは中身を必要になるまで取得しない形式（`git clone --filter=blob:none`）で取得し、過去の版のデータを手元に持たない
- **大きなファイルはGitの外へ**：画像・PDF・Excel等はGit LFS、100MB超のデータはデータ保管庫に置く（2.2）

### 8.6 記録の保管との関係

退避は削除ではないため、ISO 9001の記録の保管（7.5）と矛盾しない。保管期限が来た記録の廃棄は、アーカイブのレベルで別途ルールを定める（例：製品の販売終了から○年）。

## 9. 文書・図表・計算・説明の扱い（Office置き換え）

### 9.1 置き換え

| 従来 | 置き換え | 差分管理 |
|---|---|---|
| Word | Markdownノート | テキスト差分 |
| PowerPoint（考える用） | Excalidraw | JSON（圧縮オフ）＋自動エクスポートSVGで目視比較 |
| PowerPoint（説明用） | Excalidrawのフレーム（1フレーム＝1スライド）。画面ではスライドショー、配布・発表は**PDF出力**（9.3） | JSON差分 |
| Excel（表） | Markdown表、Bases | テキスト差分 |
| Excel（計算・グラフ） | `30_calc/` のPythonスクリプト → 結果とグラフをノートに埋め込み（扱いは9.5）。移行期間中はExcelファイルの添付も認め、IDでノートと結ぶ（基本方針 7.3） | スクリプト差分（式が見える） |
| 共有フォルダ | リンク＋索引DBの横断検索 | — |
| 社外への提出・印刷 | **PDF出力**（9.3） | 出力したPDFに元ノートのIDと版を記載 |

### 9.2 Excalidrawの設定

- 「JSONを圧縮して保存」をオフ（差分を取れるようにする）
- SVGの自動エクスポートをオン（手元での確認用。Gitには入れず、レビューやWeb閲覧ではサーバが生成したSVGを使う。第1期は暫定的にLFSで管理、2.2）
- 図の要素から関連ノートへリンクを張る（図が思考の地図になる）
- スライドとして使う図は**1フレーム＝1スライド**で作り、フレームに名前を付ける（他人からの引用単位になる）
- フレームのテンプレートは**A判の縦横比（1:1.414）**で用意する。どのA判サイズで出力しても余白なくページに収まる

### 9.3 PDF出力（出口）

社外・他部署への提出、印刷、発表のための出口は、**A4〜A0の複数ページPDF**に絞る。PDFは「完成形を渡す」形式であり、編集は元のノートで行う。PowerPoint・Word形式への変換は、レイアウト崩れの対応コストが大きいため対象外とする。

#### 出力の単位

| 元 | 出力 | 主な用途 |
|---|---|---|
| Markdownのノート | 文書として自動でページ分割（例：A4縦） | 報告書、仕様書の提出 |
| Excalidrawのフレーム | **1フレーム＝1ページ**（選んだフレームを順に並べる） | 発表スライド、DR資料 |
| Excalidrawの図全体 | 大判1枚に縮尺を合わせて出力（例：A0） | ポスター、壁貼りのレビュー |

- 用紙サイズ：A4〜A0、縦・横を選択
- 複数ノート・複数フレームを1つのPDFにまとめて出力できる

#### 綺麗に見せる条件

| 条件 | 内容 |
|---|---|
| ベクター出力 | 図はSVGのままPDFにする。A0に拡大しても線・文字がぼやけない |
| フォント埋め込み | 日本語フォントをPDFに埋め込み、どのPCでも同じ見た目にする |
| 縦横比 | フレームをA判比率で作っておけば余白なく収まる（9.2）。16:9のプロジェクターでは左右に少し余白が出るが実用上問題なし |
| 画像の解像度 | 貼り付けた写真等が出力サイズに対して粗い場合は警告（目安：出力サイズで150dpi未満） |

#### 追跡情報（各ページの余白に自動で記載）

| 項目 | 目的 |
|---|---|
| ノートのID、版（コミット）、出力日時、ページ番号 | どの版から出力したかを特定する |
| 状態（下書き／承認済み） | 下書きの印刷物を正式なものと誤認させない |
| 機密タグ | 取扱区分を明示する |
| QRコード | 読み取るとWeb閲覧で元のノートが開く |

紙やPDFが社内外に出回っても、どの版のどのノートから出たものかが必ず辿れる。印刷物が最新版かどうかの判別にもなる（ISO 9001 7.5）。

#### 機密との関係

- 出力されるのは、**出力する人が閲覧できる範囲だけ**。権限のないフレームは「🔒」のまま出力される
- 開示ビューを含む場合は、閲覧者名の透かしも出力される（7.4）
- 機密タグごとに「PDF出力の可否」を台帳で設定できる（7.2）
- **誰が・いつ・何を出力したか**を記録する

#### 作り方

Web閲覧（13.4）と同じ描画の仕組みを使い、サーバ側で動かすブラウザ（Chromium）の印刷機能でPDFにする。Web閲覧ができていれば追加の開発は小さい。

### 9.4 図付きノート（文章と図を1ファイルに）

検討の文章と図を別ファイルに分けず、**1テーマ1ファイル**にする。Excalidrawプラグインの形式（`.excalidraw.md`）の前半に普通のMarkdownの文章を書き、後半（`%%` の後）に図のデータを置く。

| ノート | 形 |
|---|---|
| 検討・構想・解析など、図が主役 | 図付きノート（前半に目的・結論・やること、後半に図） |
| 要求・議事録・週報・計算など、文章が主役 | 普通のMarkdown。図が要る時は他のノートのフレームを `![[ID#F02]]` で引用 |
| 報告 | 普通のMarkdown。各ノートのフレームを引用して並べ、PDFにする |

- `type` は中身（検討など）で付ける。図を持つかどうかはファイルの形（`.excalidraw.md`）で判断する
- 鍵・ID・タイトル・履歴が文章と図で1つになり、「報告は公開、引用元の図はチーム限定」のような食い違いが起きにくい
- フレームの引用（`ID#F02`）・版の固定・開示・PDF出力は今まで通り
- Web閲覧では、文章を先に、図（フレームごと）を後に表示する
- **図データの圧縮はオフ**（Excalidrawプラグインの設定）。オンだとGitの差分が読めない
- 1ファイルに図は1枚。スライドはフレームで分ける
- 注意：開くと「図」と「文章」の表示を切り替える形になる。スマホで重い場合は文章側で開く設定にする

### 9.5 計算プログラムの扱い

#### 段階に応じて置き場所を変える（育ったら昇格）

| 段階 | 状態 | 置き場所 |
|---|---|---|
| 1. その場の計算 | 1つの検討のためだけ。1〜数ファイル | 自分のvaultの `30_calc/`。vaultごとGitで版が残る |
| 2. 何度も使う道具 | 他の検討・他の人も使う。入力を変えて繰り返し回す | 共通の計算リポジトリ（例：`rd-calc`）へ**昇格** |
| 3. 独立したソフト | 大きくなった。製品・設備に組み込む。専任で保守する | 独立したリポジトリ |

- **昇格の目安**：2人目が使いたくなった時、または設計判断の根拠として繰り返し使われ始めた時
- 昇格したら、元の計算ノートに昇格先を書く（`promoted_to`。ノートの正式化と同じ考え方）
- 共通リポジトリでは、テスト（既知の答えとの照合）、変更のレビュー、版のタグ（例 `v1.2.0`）を必須にする
- 設計判断に使う道具は、持ち主・検証の記録・版を残す（ISO 9001 7.1.5 監視・測定のための資源の考え方）
- **やらないこと**：vaultの中に別のGitリポジトリを入れる（入れ子・サブモジュール）。道具をコピーして各自のvaultで直す（正しい版が分からなくなる。直す時は共通リポジトリに変更を出す）

#### 計算ノートには「何で計算したか」を残す

```yaml
type: calc
tool: "calc:bracket-stiffness@v1.2.0"   # 計算ツールと版（共通リポジトリのタグ、またはコミット）。30_calc の場合はスクリプトへのリンク
env: "rd-calc-env@2026.10"              # 計算環境の版
inputs: "[[入力条件のノート]]"
result_hash: "3f9a…"                    # 出力のハッシュ（後から差し替えると分かる）
```

- 半年後でも「どの版の道具で、どの条件で出した数字か」を再現できる（基本方針 0章「判断の根拠を偽らずに残す」）
- push時の検査：`type: calc` に `tool`（または `30_calc` のスクリプトへのリンク）と `env` がなければ警告
- Web閲覧の計算ツールのページに「この版で計算したノートの一覧」を出す。道具に不具合が見つかった時、影響する計算をすぐ洗い出せる

#### 計算環境（venv）

venv は**vaultの中に置かない**（数千〜数万ファイル、OS・PCごとに中身が違う。Gitや同期に巻き込まれる）。vaultには「どの環境か」だけを書く。

| 対象 | venvの場所 | Gitに入れるもの |
|---|---|---|
| vaultの `30_calc`（その場の計算） | vaultの外に全員共通の**標準環境**を1つ（例 `~/.venvs/rd-calc`） | 何も入れない。標準環境の定義は共通リポジトリから配る |
| 共通の計算リポジトリ・独立したソフト | そのリポジトリの作業フォルダの `.venv/`（Git管理外） | `pyproject.toml` と、版を固定した一覧（ロックファイル） |

- **標準環境**：Pythonの版とライブラリ（numpy、scipy、matplotlib 等）を固定した一覧を「計算環境 2026.10版」のように配る。各自は一覧どおりに作る（`uv` を推奨。一覧から一瞬で作り直せる）
- 標準にないライブラリが要る時は、その計算のフォルダに小さな一覧（`requirements.txt`）を置く。何度も要るなら標準環境への追加を提案する
- vaultの `.gitignore` に `.venv/`・`venv/`・`__pycache__/` を入れる（うっかり作ってもGitに入らない）

### 9.6 持ち出し（vaultから切り離して人に渡す）

一部のノート・計算を、Obsidianなしで読める**持ち出しパッケージ**にして渡す。Obsidianの記法とvaultの構造は外し、普通のファイルだけにする。

#### プログラムを渡すか

| 相手 | 渡すもの | 理由 |
|---|---|---|
| 社内の他部署 | 再現できる一式（プログラム込み） | 検証・再利用してもらえる |
| 協力会社・顧客 | 原則は結果と計算方法の説明だけ。プログラムは必要な時だけ、承認を取って渡す | プログラム自体が技術の資産。顧客の数値が埋め込まれていることもある |

#### パッケージの中身

Markdownに馴染みのない人も多いため、**見る形はHTMLとPDF**にする。Markdownは「原本」として奥に置く。

```
X200_ブラケット剛性_261004-359dy/
├─ 開く.html            ブラウザで見る（ダブルクリックで開く。ネット接続・インストール不要）
├─ 資料.pdf             印刷・保存・メール添付用（9.3のPDF出力。ID・版・QRのフッター付き）
├─ はじめにお読みください.txt   中身の説明、開き方、問い合わせ先（3〜5行）
└─ 原本/                 再利用・再現したい人向け
   ├─ notes/            Markdown（[[…]] は通常のリンクか文字に、図は画像に）
   ├─ calc/             スクリプト、inputs/（入力条件）、outputs/（こちらで出した結果）
   ├─ requirements.txt  版を固定したライブラリ一覧（venvは渡さない）
   └─ MANIFEST.yml      ノートID・版（コミット）・計算ツールの版・環境の版・結果のハッシュ・渡した相手と日付
```

**開く.html（ブラウザで見る形）**
- 1ファイルで完結（図・画像・文字を中に持つ）。社内のWeb閲覧と同じ見た目で、**持ち出した資料だけ**が入る
- 持ち出した資料どうしのリンクは、その中で移動できる。持ち出していない資料へのリンクは名前だけ（中身は入れない）
- 図はフレームごとの画像（SVG）。拡大しても粗くならない
- 外部のフォント・スクリプトを読まない（社外のネットワークや閉じた環境でも開ける）
- 印刷するとA4で崩れない（印刷用の見た目を付ける）
- 各ページの下に、ノートID・版（日時）・持ち出し日・渡した相手を表示

**資料.pdf（保存・印刷の形）**
- 報告ノートがあれば、その順（9.3と同じ）。なければ持ち出したノートを順に並べ、先頭に目次
- 鍵でPDF出力が禁止されたノートは、そもそも持ち出せない（次の「守ること」）

**原本**
- `30_calc` のスクリプトはその時点の版をコピー。昇格した道具は、社内なら場所と版（タグ）だけ、社外ならその版の中身を同梱
- **再現の確認**：渡す前に、まっさらな環境で一度動かし、結果のハッシュが一致することを確かめる（動かないパッケージを渡さない）
- プログラムを渡さない場合（社外の原則）、`calc/` は入れず、計算方法の説明と結果だけをHTML・PDFに載せる

#### 守ること

- **鍵の決まりに従う**：PDF出力が禁止の鍵のノートは入れない。鍵の付いた資料は開示の手続き（7.4）を経てから
- **持ち出しの記録**：何を・誰に・いつ・なぜ渡したかを、開示と同じ形で記録する。「どの版を渡したか」に必ず答えられるようにする
- **顧客情報の確認**：プログラム・入力に顧客名・顧客の数値がないか、タグ台帳の顧客名リストで自動チェック
- 社外の相手、またはプログラム付きの場合は、上司の確認待ちに並べる（理由・確認項目付き）

#### 戻ってきた時

相手が直して返してきたものは、元のノートを上書きしない。新しいノートとして取り込み、どのパッケージ（MANIFEST）から来たかを書く。

#### 操作（予定）

```
kv.py export <ノートID…> --to <相手> [--with-code]   # 変換・同梱・再現の確認・持ち出しの記録まで
```

## 10. 1日の業務の流れ（例）

1. **デイリーノート**を開く（その日のタスク、昨日の続き）
2. 打合せ → **議事録**、出てきた要求 → **要求**ノート
3. 構想を**検討**ノートとExcalidrawで描く。購読中の同僚の過去の**設計判断**にリンクして参考にする。要求担当者の仮目標のフレームを版固定で引用する
4. 強度を**計算**（Python）、結果を検討ノートに埋め込む
5. 方針が決まったら**設計判断**ノートに、却下案と理由も含めて記録
6. DR用に**報告**を作り（Excalidrawのフレーム）、スライドショーで説明。配布資料はPDFで出力
7. DR後、設計判断と要求をプロジェクトリポジトリへ**PR** → 承認で正式化

すべてが自動コミットされ、リンクでつながるので、後から「なぜこうなったか」をいつでも辿れる。

## 12. AIの位置付け：任意の拡張層

AIの導入はセキュリティ上の理由で認められない可能性がある。そのため、**全機能をAIなしで動く仕様にし、AIは「使うとより便利になる」拡張層**として設計する。

### 12.1 原則

- **基本機能はAIに依存しない**：検索・トレース・チェック・通知・退避は、全文検索・プロパティ・リンク関係・ルールで実現する
- **AIは差し替え・停止が可能**：「AIなし／社内設置のモデル／外部サービス」を組織単位で選べる。既定は「AIなし」
- **AIの出力は下書き**：AIがプロパティやリンクを直接書き換えることはしない。人が確認して確定する
- **構造化しておくほどAIなしでも強い**：関係プロパティ・数値プロパティ・テンプレートの必須項目を整備することが、AIなしの機能を支え、AIを入れた時の精度も上げる

### 12.2 機能ごとの「AIなし」と「AIあり」

| 機能 | AIなし（基本） | AIあり（拡張） |
|---|---|---|
| 横断検索 | 全文検索、プロパティでの絞り込み（案件・種類・部品ID・タグ）、リンク・被リンクの辿り | 自然文での質問（「この部品について過去に誰が何を検討したか」）、意味の近さでの検索、回答の要約 |
| 類似案件・過去不具合の提示 | 同じ部品ID・案件・タグ・キーワードを持つノートの一覧 | 内容の類似度による提示 |
| 退避ノートの要約 | 作成者が書く `summary` プロパティ、本文冒頭の自動抽出 | 要約の下書きを自動生成（作成者が確認） |
| 要求品質チェック | ルールで判定：必須項目の記入、合否判定基準が数値と単位で書かれているか、検証方法の指定、曖昧語リスト（「十分な」「なるべく」等）の検出、同一IDの重複 | 曖昧さ・要求間の矛盾の指摘 |
| 目標値と結果の比較 | 要求の `target_value` と試験の `result_value`（数値・単位）をプロパティで比較し、未達を一覧表示 | 自由記述の考察を読んで、目標との関係を指摘 |
| トレースの抜け | リンク関係の照会：試験に紐づかない要求、要求に紐づかない設計判断などを一覧表示 | リンク候補の提案 |
| 引用元更新の影響 | 引用関係から影響先を一覧表示・通知 | 差分の要点を要約 |
| 退避候補・開示ビュー・権限判定 | ルールのみ（AIは使わない） | — |

### 12.3 AIを使う場合のセキュリティ管理

| 管理項目 | 内容 |
|---|---|
| 閲覧権限 | AIが使えるのは、質問した人が読めるノートだけ（7.2の判定と同じ） |
| タグ単位の除外 | タグ台帳に「AI利用可否」を持たせ、不可のタグのノートはAIに一切渡さない |
| 開示ビュー | 開示グラントで見せた範囲も、グラントに「AI利用可」がなければAIに渡さない |
| 設置場所 | 社内設置のモデルを優先。外部サービスを使う場合はデータを保持・学習しない契約を前提 |
| 記録 | AIへの問い合わせ（誰が・何を・どのノートを参照したか）をログに残す |
| 停止 | AIを止めても、12.2の「AIなし」の機能で業務が継続できること |

## 13. 依存性とリスク対策

このシステムはObsidianとExcalidrawに大きく依存する。**データの安定性は高いが、道具としての安定性は中程度**であり、設計で補う。

### 13.1 依存先とリスク評価

| 依存先 | 性質 | リスク | 止まった場合の影響 |
|---|---|---|---|
| Obsidian本体 | 小規模な独立企業の製品。ソース非公開。業務利用は無料（2025年2月〜） | 方針変更・事業停止 | 技術者の入口が使えなくなる。データ（Markdown）は残る |
| Excalidraw本体 | MITライセンスのオープンソース。データ形式（JSON）は公開 | 低い | 自社で描画・編集を継続可能 |
| ObsidianのExcalidrawプラグイン | オープンソースだが、開発はほぼ個人。独自の記法（フレーム埋め込み、ノートへのリンク）を含む | **最大のリスク** | Obsidian上で図の編集ができなくなる |
| その他のコミュニティプラグイン（Templater、Obsidian Git、Day Planner、Obsidian Tasks等） | それぞれ個人が保守 | 中 | 自動化・表示の一部が止まる。データ（Markdownの書き方）は残る |
| 自作プラグイン | ObsidianのプラグインAPIに依存 | API変更時に改修が必要 | 改修完了まで一部機能が止まる |

### 13.2 対策

| # | 対策 | 内容 |
|---|---|---|
| 1 | **記法を自社で仕様化** | ID、フレームID、版固定、開示グラントなどのリンク記法を自社の「記法仕様書」として定める。サーバは自前の解析処理で読み、正本の意味をプラグイン独自の書き方に依存させない |
| 2 | **Obsidianなしでも見られる状態を常に保つ** | サーバ側でMarkdownとExcalidrawを描画するWeb閲覧を用意する（13.4）。開示ビューの描画（7.4）と同じ部品を使う |
| 3 | **Excalidrawは圧縮オフ＋SVG自動出力** | JSONを読める形で残し、SVGを人が見る用の控えにする（9.2） |
| 4 | **プラグインは社内で版を固定して配布** | コミュニティから自動更新せず、検証環境で確認してから社内配布。Excalidrawプラグインは、いざとなれば**自社でフォークして保守できる**体制と予算を見込む |
| 5 | **プラグインの数を最小限に** | 本文にプラグイン専用の書き方（クエリ等）を増やさない。一覧はObsidian標準機能（Bases）か、サーバ側で提供する |
| 6 | **乗り換え先を想定** | Excalidraw本体がオープンソースなので、将来は自社のWeb編集画面も作れる。Obsidianは「技術者向けの入口の1つ」（基本方針 原則6・8） |
| 7 | **開発元の支援** | 業務で使う以上、Obsidianの商用ライセンス購入やプラグイン開発者への支援で、継続性に貢献する |

### 13.3 Obsidianが使えなくなった場合

| 機能 | 影響 |
|---|---|
| データ（ノート、図、履歴） | **失われない**（Git上のMarkdownとJSON） |
| 閲覧・検索・リンクの辿り | Web閲覧で継続 |
| 承認・正式化 | Gitサーバのプルリクエストで継続 |
| 開示ビュー・アクセス制御 | サーバ側の機能なので継続 |
| ノート・図の編集 | 代わりの入口（別のMarkdownエディタ、自社のWeb編集画面）を用意するまで制限される |

「データが読めなくなる」事態は起きない。起きるのは「入口を作り直す必要が出る」ことであり、対策をとっておけば、計画的に進められる移行プロジェクトになる。

### 13.4 Web閲覧（Obsidianなしの入口）

段階的に作る。工数は経験のある開発者1人での目安。

| 段階 | 内容 | 工数の目安 |
|---|---|---|
| 1. 個人用の静的プレビュー | 既存のオープンソース（Obsidianのvaultをサイトに変換するQuartz等）で、自分のvaultを閲覧できるWebページを生成。図はExcalidrawプラグインが自動出力したSVGを表示 | 数日〜1週間 |
| 2. 自前の閲覧画面（読み取り専用） | hashによるリンク解決、プロパティ表示、被リンク、全文検索、ExcalidrawのJSONからの直接描画（自動出力SVGに頼らない） | 1〜1.5か月 |
| 3. 社内向けの閲覧サーバ | 社内認証（SSO）、機密タグによる権限判定、索引DB連携、フレーム単位の描画と無害化、版固定の表示、開示グラント | 3〜6か月 |
| 4. 本番運用に耐える品質 | セキュリティ診断、監査ログ、性能、運用体制 | ＋2〜3か月 |

- 段階3は、索引DB・配信サーバ（6章）と開示ビュー（7.4）の開発そのものであり、Web閲覧のための追加開発ではない
- 段階1は、Obsidianへの依存を確認するための「保険」として、運用初期に作っておく

## 14. 開発ステップ

AIなしで全機能が動くことを先に完成させ、AI拡張は最後に任意で追加する。

1. **共通テンプレートとファイル名・IDの自動生成**（作成日＋タイトル＋hash、タイトルとファイル名の同期、食い違いの自動修正）と**添付の自動処理**（2.4。最初にExcalidrawへのドロップの動作を検証）を作り、自分のvaultで運用を試す
2. 社内Gitサーバと自動コミットを整備（個人vaultの直接読取は本人とサーバのみ、部分クローン、Git LFS、除外設定、添付の自動命名と付属ノート作成）。プラグインの社内配布（版固定）と記法仕様書もここで定める
3. **Web閲覧 段階1**（静的プレビュー。Obsidianなしで読める保険、13.4）
4. **PDF出力**（A4〜A0、フレーム単位、フォント埋め込み、ID・版・QRコードの余白記載、9.3）
5. **アクセス管理台帳**（機密タグ、管理責任者、個人ごとの権限、AI利用可否）
6. **索引DB**（プッシュ時にノート・フレーム・リンク・引用・機密タグを解析して登録、全文検索）
7. スタブ生成と本文のオンデマンド取得（配信時の権限判定、`_refs/`、`_cache/`）
8. **一時退避と復活**（閲覧履歴の記録、退避候補の提示、ノート・案件単位の復活）
9. プロジェクトリポジトリとPRによる正式化フロー
10. **開示グラント**（承認フロー、フレームのSVG描画と無害化、透かし、更新時の再承認）
11. カスタムプラグイン（版固定の引用、引用元更新の通知・比較、権限に応じたリンク表示、他vault被リンク表示、未購読IDのプレビュー）
12. **ルールによるチェック**（要求品質、目標値と結果の比較、トレースの抜け）
13. マスタDB連携（部品・BOM・計測器のID参照）
14. （任意）**AI拡張**（自然文検索、要約・チェックの下書き、問い合わせログ）
