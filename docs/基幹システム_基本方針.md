# 基幹システム 基本方針

有形の製品を研究・開発・製造・販売する研究開発型企業のための基幹業務システムについて、全体を通じて守る方針を定める。個別の設計書（要件整理、vault設計など）は、すべてこの方針に従う。

---

## 0. 目指す姿（最上位）

**判断の根拠が、信頼の根拠になる。**

### 0.1 B to Bのものづくり企業で、最も大切なこと（考え方の候補）

何を最も大切にするかには、いくつかの考え方がある。どれか1つを選ぶより、**役割で分けて関係を持たせる**のがよい。

| 価値観 | なぜ大事か | 壊れた時に起きること |
|---|---|---|
| 誠実さ（ごまかさない） | 検査データ・試験結果・記録を偽らない。悪い情報ほど早く出す | 品質不正が一度発覚すると、取引も社会的信用も失う |
| 安全 | 製品の安全と、作る人の安全 | 事故は信頼でも取り返せない。法的責任も伴う |
| 顧客の信頼（約束を守る） | 仕様・品質・納期・長期の供給を守る。取引が長く、採用までの評価にも時間がかかるので、一度の信頼が長く効く | 次の案件で選ばれない。乗り換えられると戻らない |
| 品質 | 信頼の中身そのもの。いつも同じ物が届くこと | 不具合の対応費用と信用の低下が同時に来る |
| 技術力・知の蓄積 | 差別化の源泉。価格競争から抜け出す力 | 人が辞めると技術も消える。同じ失敗を繰り返す |
| 人（技術者・現場の技能） | 技術も品質も、結局は人が生む | 育たない・定着しないと、すべてが細る |
| 顧客の成功への貢献 | 言われた物を作るだけでなく、顧客の課題を一緒に解く | 代わりのきく納入業者になる |
| 供給の責任 | 止めない・切らさない（補修部品・長期供給を含む） | 顧客のラインを止め、その損害が返ってくる |

**関係：土台・源泉・結果**

```
            結果   顧客の信頼（選ばれ続けること）
                     ▲
            源泉   人 ／ 技術力・知の蓄積   … 価値を生む力（育てる）
                     ▲
            土台   誠実さ ／ 安全            … 絶対に崩さない（守る）
```

- **顧客の信頼は「結果」**。旗印として正しいが、直接は作れない。毎日の判断で**守るのは土台**、**育てるのは源泉**
- 品質・供給の責任・顧客の成功への貢献は、土台と源泉が顧客に届いた形（約束を守ること）にあたる

### 0.2 このシステムの理想像

上の考え方の中で、このシステムが目指す姿を次のように定める。

> **正直であることが一番楽で、考えたことが人と会社に残り、いつでも顧客に根拠を示せる開発の場**

| 層 | 理想の状態 | このシステムの仕組み |
|---|---|---|
| 土台：誠実さ | **ごまかすより、正直な方が楽**。悪い知らせが早く出る | 記録は消せず、書き換えた履歴も残る（Git）。遅れは隠さず見込みとして出す（承認なしで更新できる）。却下した案も残す。実績は本人が確定し、推測で埋めない |
| 土台：安全・機密 | 預かった情報は、見てよい人にだけ見える | 鍵（機密タグ）をサーバが配信時に判定。開示は内容を確認してから、理由付きで |
| 源泉：人 | 書いた人の考えが評価され、引き継がれる。記録が監視の道具にならない | 工数は参考値で個人評価に使わない。上司の画面に個人の順位を出さない。誰が何を考えたかが残る |
| 源泉：技術・知 | 過去の検討を探さずに見つけ、引用して使える | 1人1 vault＋全社の索引。引用はコピーせず版を固定。同じ失敗を辿れる |
| 結果：顧客の信頼 | 「なぜこの設計か」「不具合の原因は何か」に、すぐ根拠を示せる。約束（納期）を守れる、守れない時は早く相談できる | 要求→判断→図面→試験を一本の糸で辿る。工程の当初計画と実際の差、変更の理由と承認が残る |

**やらないこと**（理想像に反するため）
- 記録の量で人を評価する
- 都合の悪い記録を消せるようにする
- 便利さのために、見せてはいけない人に見せる

### 0.3 目的・手段・結果

| 段 | 内容 |
|---|---|
| 目的 | **顧客の信頼に応え続ける開発**。約束（仕様・納期・品質）を守り、預かった情報を守る |
| そのために | **判断の根拠を、偽らず、いつでも説明できる形で残す**。なぜこの設計か、何を検討して何を捨てたかを、すぐに示せる |
| 結果として | 考えの過程が、次の開発と次の顧客対応に使える**資産**になる |

**信頼につながる場面**

| 場面 | このシステムが効くところ |
|---|---|
| 顧客に「なぜこの設計か」と聞かれた | 検討・計算・却下した案と理由を、版を固定した引用で示せる |
| 不具合が出た | 要求 → 設計判断 → 図面 → 試験の経路を辿り、原因と経緯をすぐ出せる。同じ失敗を繰り返さない |
| 担当が替わった | 前任者の考えの過程が残っており、対応の質が落ちない |
| 顧客の図面・要求を預かった | 鍵（機密タグ）で、見てよい人にだけ見せる |
| 納期を約束した | 計画・見込み・遅れを隠さず示し、早めに相談できる |

**以下の目的・原則はすべて、この姿に従う。** 原則同士で迷った時は、土台（誠実さ・安全）を最優先し、次に「顧客の信頼に資するか」で判断する（4章）。成果は、ノートの数ではなく顧客側の結果で測る（7.4.5）。

## 1. 目的

0章の姿を実現するための、システムとしての目的を定める。

仕事の本質は、**情報を集め、考え、整理し、結論を出し、人に説明して行動を起こしてもらう、または自ら行動すること**にある。このシステムの目的は、その一連の流れを妨げずに支え、次の3つを実現することである。

1. **探す・転記する・説明し直す工数をなくす**
2. **判断の経緯と確定事項を、つながった資産として残す**
3. **顧客の要求から市場での製品の振る舞いまでを、一本の糸で辿れるようにする**

## 3. 基本原則

| # | 原則 |
|---|---|
| 1 | 思考過程と確定事項の両方を資産とし、つながった状態で残す |
| 2 | データごとに正本を1つ決める |
| 3 | 製品の一生を一本の糸でつなぐ |
| 4 | 思考は自由に、確定は厳格に |
| 5 | 業務をこなすと記録が自動で残る |
| 6 | 使う人に合わせた入口、裏は同じデータ |
| 7 | 正しい運用が最も楽な運用になる |
| 8 | 特定の技術に依存しない |

以下、各原則の意味・理由・実現方法・判断基準を示す。**判断基準**は、設計や運用で迷った時に立ち返る問いである。

---

### 原則1　思考過程と確定事項の両方を資産とし、つながった状態で残す

**意味**
- 研究開発で最も価値があるのは、結論に至った**思考の過程**（何を検討し、何を却下し、なぜ選んだか）
- 製造・販売で最も価値があるのは、正確な**確定事項**（承認された図面、どのロットを誰に出荷したか）
- この2つを別々に持つのではなく、**確定事項から思考過程へ、いつでも辿れる状態**で残す

**理由**
- 確定事項だけでは、前提が変わった時に「なぜこうなっているか」が分からず、同じ検討を繰り返す
- 思考過程だけでは、何が正式に決まったのかが曖昧になる

**実現方法**
- 思考は個人の作業領域（vault）に、確定事項は正式な管理領域（プロジェクトリポジトリ、マスタDB）に置き、IDでリンクする
- 設計判断の記録では「却下した選択肢と理由」を必須にする

**判断基準**
- 3年後に別の人が見て、「何が決まっていて、なぜそうなったか」が分かるか？

---

### 原則2　データごとに正本を1つ決める

**意味**
- 同じ情報が複数の場所に存在し、どれが正しいか分からない状態を作らない
- 正本以外は、正本の参照・派生物（再生成できるもの）とする

**データの種類と正本**

| データ | 正本 | 例 |
|---|---|---|
| 思考・文書・図 | Git（個人vault、プロジェクトリポジトリ） | 検討、設計判断、要求、DR記録、報告 |
| 品目・構成 | マスタDB | 部品、E-BOM／M-BOM |
| 取引・在庫 | マスタDB（または既存の生産管理・会計システム） | 受注、発注、在庫、ロット、出荷 |
| 測定・試験データ | マスタDB／データストレージ | 試験の生データ、検査記録 |
| 形状データ | CAD・PDM | 3Dモデル、図面原紙 |
| 権限 | アクセス管理台帳 | 機密タグ、権限保持者 |
| 索引・検索 | 派生物（正本から自動生成） | 索引DB |

**判断基準**
- この情報が食い違った時、どちらが正しいと即答できるか？
- 消えても正本から再生成できるか？（できるなら派生物として扱ってよい）

---

### 原則3　製品の一生を一本の糸でつなぐ

**意味**
顧客の要求から市場での不具合まで、製品に関わる情報をIDで連続的に辿れるようにする。

```
顧客要求 → 要求仕様 → 設計判断 → 図面・BOM → 試験 → 製造ロット → 出荷 → 顧客・設置先 → 保守・市場不具合
   ↑                                                                                         │
   └─────────────────────────── 次の設計へのフィードバック ────────────────────────────────┘
```

**理由**
- 有形の製品では、不具合が出た時に「どの設計判断が原因か」「影響するロット・顧客はどこか」を素早く特定できるかが、損失の大きさを決める
- 研究開発の活動が顧客要求・事業目的とつながっていないと、成果が使われない

**実現方法**
- すべての開発活動は、顧客要求または事業目的のいずれかに紐付ける（紐付かない活動は理由を記録する）
- 品目・ロット・シリアル・顧客に全社共通のIDを付け、文書からはIDで参照する
- 市場不具合は、該当する部品・図面・要求・設計判断に紐付けて設計側へ戻す

**判断基準**
- この情報から、上流（なぜ必要か）と下流（何に影響するか）の両方へ辿れるか？

---

### 原則4　思考は自由に、確定は厳格に

**意味**
- 考える段階では、形式・承認・粒度にとらわれず自由に書ける
- 他者が使う段階（製造が使う図面、顧客に出す仕様、他部署が前提とする目標値）に入ったものは、承認・版固定・変更管理で厳格に扱う

**理由**
- 考える段階に厳格な手続きを課すと、記録されなくなる（思考過程が失われる）
- 確定したものが自由に変わると、製造・調達・顧客対応で事故が起きる

**実現方法**
- 個人vaultは自由、正式化はプルリクエストと承認者のマージで行う
- 確定した情報を引用する時は版を固定し、更新時は引用先へ通知する
- 機密は、ノート単位のタグで「必要な人に必要な範囲だけ」開示する。部分開示は複製ではなく、開示許可（グラント）で行う

**判断基準**
- この情報は、自分以外の誰かの行動の前提になっているか？（なっていれば厳格に扱う）

---

### 原則5　業務をこなすと記録が自動で残る

**意味**
記録のための作業を、業務とは別に発生させない。普段の業務手順そのものが、記録と証跡を生む構造にする。

**理由**
- 記録が別作業になると、後回しにされ、形骸化する
- ISO 9001などの監査対応が「記録を作る作業」になると、本来の業務を圧迫する

**実現方法**
- 承認、ゲート判定、変更管理をワークフローとしてシステムに組み込み、操作の履歴をそのまま証跡にする
- 必須項目はテンプレートで促し、未入力は次の工程に進めない
- 監査時は、記録を「作る」のではなく「抽出する」だけで済むようにする

**判断基準**
- 監査の前日に、新たに作らなければならない資料があるか？（あるなら設計を見直す）

---

### 原則6　使う人に合わせた入口、裏は同じデータ

**意味**
- 研究者・技術者は文書と図で考えるので、Obsidian＋Excalidrawを入口にする
- 製造現場はタブレット・バーコード、営業は顧客・案件の画面、購買は発注の画面、というように、**役割ごとに最適な入口**を用意する
- どの入口から入力しても、裏側では同じ正本（原則2）に記録される

**理由**
- 全員に同じ道具を強いると、使われないか、別の場所に記録が作られる
- 入口が違っても裏が同じなら、部門をまたいで情報が途切れない

**実現方法**
- 正本へのアクセスはAPIで統一し、入口（画面・アプリ）はAPIの上に作る
- 文書側からはIDで品目・ロット・顧客を参照し、取引側の画面からは関連する文書・設計判断へリンクする

**判断基準**
- この人は、普段の道具のまま、この情報を入力・参照できるか？

---

### 原則7　正しい運用が最も楽な運用になる

**意味**
ルールで縛るのではなく、正しいやり方が一番手間のかからないやり方になるように作る。

**理由**
- 手間のかかる正しい運用より、手軽な誤った運用（スクショ、コピペ、個人フォルダへの保存）が選ばれ、データが追えなくなる

**実現方法**
- リンクと引用はワンクリックで、常に最新。スクショより楽で正確にする
- ファイル名・ID・プロパティはテンプレートが自動で付け、人はタイトルを入力するだけ
- 初めて使う人でも、従来の習慣（ファイル名と日付で探す等）が通用するようにする

**判断基準**
- 正しいやり方と、誤ったやり方の、どちらが手数が少ないか？（誤った方が少ないなら設計を見直す）

---

### 原則8　特定の技術に依存しない

**意味**
- 製品の保守期間（10年、20年）を超えて、データを読み・使い続けられるようにする
- 特定の製品・ベンダー・AIが使えなくなっても、業務が止まらないようにする

**実現方法**
- **公開された形式で残す**：文書はMarkdown、図はJSON（＋SVG）、データは標準的な形式。特定ソフトがなくても読める
- **AIなしで全機能が動く**：AIは任意の拡張層。セキュリティ上の理由でAIを使えない環境でも、検索・トレース・チェックはルールと構造化データで動く
- **既存システムとはIDでつなぎ、段階的に置き換える**：既存の生産管理・会計・CAD・PDMを一度に捨てず、連携しながら効果の大きい所から置き換える
- **入口の道具は交換可能にする**：Obsidianも入口の1つであり、正本と索引はObsidianに依存しない

**判断基準**
- この道具が明日使えなくなったら、データは読めるか？業務は続けられるか？

## 4. 原則間の優先順位

原則同士がぶつかった場合は、次の順で判断する。

0. **土台（誠実さ・安全）と顧客の信頼（0章）**：迷った時の最終的な判断基準。誠実さ・安全は何とも引き換えにしない。例えば、記録を増やすことが顧客対応を遅らせるなら記録の方を軽くするが、記録を偽る・消すことはしない
1. **原則4（確定は厳格に）と機密保護**：製品の安全、顧客との契約、法令を守ることが最優先
2. **原則2（正本は1つ）・原則3（一本の糸）**：データの正しさと辿れることは、利便性より優先
3. **原則7（楽な運用）・原則6（入口）**：上記を守った上で、最大限楽にする

例：スクショで貼れば楽だが正本が増える → 原則2を優先し、代わりにリンク・引用を楽にする（原則7）ことで解決する。

## 5. 品質マネジメントとの関係

- ISO 9001（2026年版）に準拠する。品質マネジメントの要求事項を、運用ルールではなく**システムの仕様として組み込む**（原則5）
- 主な対応：文書化した情報の管理（7.5）、設計・開発（8.3）、識別とトレーサビリティ（8.5.2）、不適合と是正処置（8.7／10.2）
- 詳細は「開発業務システム 要件整理（ISO 9001対応）」を参照

## 7. 導入方針

導入の難しさは、技術よりも**人と組織の側**にある。誰が何に抵抗するかを明らかにし、それぞれに対策を持って進める。

### 7.1 想定される抵抗

| 誰が | 何がつらいか |
|---|---|
| 技術者（書く人） | Markdown、リンク、プロパティを覚える手間。PowerPointの方が速く描ける |
| 管理職（読む人） | 会議資料はPowerPointで見たい。新しい道具を覚える時間がない |
| 社外・他部署 | 顧客や取引先は、PowerPoint・Excel・Wordでのやり取りを前提にしている |
| 計算をする人 | Excelの計算をPythonに置き換えるのは、プログラミングをしない人には高い壁 |
| 品質保証・IT部門 | ISO文書の手順変更、セキュリティ審査など、承認する側の負担が増える |
| 全員 | 移行期間中の二重管理。既存のOffice文書の山の扱い |

### 7.2 根深い課題

1. **価値が出るまでに時間がかかる**
   横断検索やトレーサビリティは、記録が溜まり、使う人が増えて初めて効く。最初の利用者は手間だけが増え、恩恵が少ない
2. **考えの途中を見せることへの抵抗**
   未完成の考えや失敗を他人に見られ、評価されることを恐れる人は多い。「思考過程を資産にする」方針（原則1）は、ここで最も強く抵抗される

**最大の難所は「社外とのOfficeでのやり取り」と「価値が出るまでの時間」**。前者は出口の機能で解決できる。後者は、1人でも便利な道具にできるかどうかにかかっている。

### 7.3 導入の原則

| # | 原則 | 内容 | 対応する抵抗 |
|---|---|---|---|
| 1 | **1人でも得をする道具にする** | 他の人が使っていなくても、自分の思考整理・検索・デイリーノートだけで便利だと感じられること。最初の普及を左右する | 価値が出るまでの時間 |
| 2 | **出口を保証する** | A4〜A0の複数ページPDFをワンクリックで綺麗に出力できるようにする。印刷にも発表スライドにも使え、社外・他部署への提出はPDFで行う。各ページに元ノートのIDと版を記載し、出回った後も辿れるようにする（vault設計 9.3） | 社外・他部署 |
| 3 | **Excelを禁止しない** | 計算用Excelは当面添付として認め、IDでノートと結ぶ。よく使う計算から順にテンプレート化して置き換える | 計算をする人 |
| 4 | **管理職には覚えさせない** | Web閲覧・スライド表示・案件の状況一覧で、Obsidianを使わずに読めるようにする。管理職の利点は、判断の経緯と進捗がいつでも見えること | 管理職 |
| 5 | **既存文書は一括移行しない** | 既存ファイルは、IDを持つ「索引ノート」から参照するだけにし、触る必要が出た時に変換する | 二重管理・既存文書 |
| 6 | **下書きは本人のみを既定に** | タグのないノートは本人だけが読める（vault設計 7.2）。公開は本人が意図して行う。「下書きは評価の対象にしない」ことを明文化する | 考えの途中を見せる抵抗 |
| 7 | **品質保証部門を最初の味方にする** | 監査準備が「抽出するだけ」になる利点（原則5）を示し、承認する側を推進する側に変える | 品質保証・IT部門 |
| 8 | **従来の習慣が通用するようにする** | ファイル名と日付で探せる、テンプレートでIDやプロパティが自動で付く。新しい作法を覚えなくても始められる（原則7） | 技術者 |

### 7.4 試験導入

#### 7.4.1 目的

1. **1人でも便利**：参加者が、他の人の利用状況に関係なく、日々の業務が楽になったと実感する
2. **管理職も便利**：管理職が、Obsidianを使わずに、案件の状況と判断の経緯をいつでも把握できる
3. **つながると、もっと便利**（第2期）：要求と検討がつながることで、手戻りが減ることを示す

#### 7.4.2 対象チームと業務

**対象**：特定の電気機械構造物製品の**改良版**を開発するチーム（1チーム、数名〜十数名＋管理職）

**業務の流れと、本システムでの扱い**

| # | 業務 | 主に使うノート | 残るもの | 管理職から見えるもの |
|---|---|---|---|---|
| 1 | 顧客の要求の把握 | 議事録、要求 | 顧客要求、目標値、出所 | 要求の一覧 |
| 2 | 既存構造のボトルネックの洗い出し | 検討（Excalidraw）、計算 | 既存構造の分析、測定・計算の根拠 | ボトルネックの一覧と根拠 |
| 3 | 解決策の考案と検証 | 検討、計算 | 複数案の比較、**却下した案と理由**、検証結果 | 案の比較と状況 |
| 4 | 製品として採用可能な構造の探索 | 検討、報告 | 構造案の評価、採用に向けた課題 | 採用候補の構造と残課題 |
| 5 | DR・承認 | 報告（PDF出力） | 既存のDR・承認システムに添付、`doc:` で番号を記録 | DR資料（スライド形式、PDF） |
| 6 | 量産移管前の業務 | 報告、検討 | 移管資料、根拠となる検討へのリンク | 移管準備の状況 |

- 設計判断・DR記録・承認は、既存システムを使う（本システムからは `doc:` で参照）
- 計算は、試験ではExcelファイルの添付も認める（置き換えは試験後に検討）

#### 7.4.3 第1期：1人でも便利＋管理職も便利（3か月）

**参加者が使う機能**

| 機能 | 内容 |
|---|---|
| テンプレート | デイリー、議事録、要求、検討、計算、報告 |
| ファイル名・IDの自動生成 | `作成日_タイトル_hash`。人はタイトルを入力するだけ |
| Git自動コミット | 10分ごとに自動で保存・履歴化 |
| Excalidraw | A判比率のフレームテンプレート、1フレーム＝1スライド |
| PDF出力 | A4〜A0、フレーム単位、余白にID・版・状態・QRコード |
| 品番・案件の参照 | `parts`、`project` プロパティ、`[[part:…]]` |

**管理職が使う機能**（Web閲覧のみ。Obsidian不要）

| 機能 | 内容 |
|---|---|
| 案件の状況ページ | 案件ごとに、関連ノートの一覧、担当者、状況、次にやること、最終更新日、要約を自動表示 |
| 今週の更新一覧 | その週に更新された検討・報告を要約付きで一覧。週報の代わり |
| 報告の閲覧 | スライド形式で表示、PDFでダウンロード |
| 経緯を辿るリンク | 報告から、元の検討・計算・要求へクリックで辿れる |

**部下の負担を増やさない**：管理職向けの情報は、普段のノートから自動で作る。追加で書くのは、検討・報告のテンプレートにある次の2項目だけ。

```yaml
progress: 検討中        # 検討中 / レビュー待ち / 完了 / 保留
next: 案Bの応力解析     # 次にやること（1行）
```

**公開のルール**

| ノート | 公開範囲 |
|---|---|
| デイリー、メモ | **本人のみ**（考えの途中を見せる抵抗への配慮） |
| 案件に紐づく議事録・要求・検討・計算・報告 | **案件のチーム**（案件を選ぶと、案件台帳の既定のタグが自動で付く） |
| 公開したくないもの | 本人がタグを外せば本人のみに戻せる |

- 第1期のWeb閲覧は、参加チームだけが見られる社内ページとし、公開対象のノートだけを載せる。ノート単位の細かい権限判定は第2期に回す

**第1期の開発項目**

| 項目 | 内容 |
|---|---|
| テンプレート一式 | 上記6種類（`progress`・`next` 入り） |
| 自動化 | ファイル名・ID生成、タイトルとファイル名の同期、Git自動コミット |
| PDF出力 | vault設計 9.3 |
| Web閲覧 | 公開対象ノートの表示、案件の状況ページ、今週の更新一覧 |
| 案件台帳 | 案件ID、案件名、略称、既定のタグ（最初は一覧ファイルで可） |

**第1期で扱わないもの**：他人のvaultの参照（スタブ・引用）、引用元更新の通知、開示グラント、一時退避、AI

#### 7.4.4 第2期：チームでつながる（3か月）

| 項目 | 内容 |
|---|---|
| 狙い | 要求担当者の目標値を、設計者が版を固定して引用し、目標値が変わったら通知が届く流れを実現する |
| 追加する機能 | 索引DB、スタブと本文のオンデマンド取得、版固定の引用、引用元更新の通知、ノート単位の権限判定 |
| 対象業務 | 業務の流れ1〜3（顧客要求 → ボトルネック → 解決策）のつながり |

#### 7.4.5 計測

**開始前に、現状の値を必ず測っておく**（比較の基準がないと効果を示せない）。

**成果は顧客側の結果で測る**（0章）。ノートの作成数は利用状況の把握にだけ使い、成果の指標にしない。

| 成果の指標（顧客側） | 測り方 |
|---|---|
| 顧客からの技術的な問い合わせに答えるまでの時間 | 問い合わせの受付から回答までの記録 |
| 不具合の原因が分かるまでの時間、同じ不具合の再発件数 | 課題・不具合ノートの記録 |
| 過去の検討を引用・再利用した回数 | 他のノートからの引用・リンクを自動集計 |
| 担当替えの後、一人で対応できるまでの期間 | 担当替えの時に本人・上司が記録 |

以下は、その成果に至る途中の指標（業務の効率）である。

| 対象 | 計測項目 | 測り方 |
|---|---|---|
| 個人 | 検討資料・報告の作成時間 | 参加者の自己申告（作業ごと） |
| 個人 | 過去の検討・資料を探す時間 | 参加者の自己申告（週単位） |
| 個人 | 過去の検討を再利用した回数 | 他のノートへのリンク数から自動集計 |
| 管理職 | 進捗確認のための会議・問い合わせの時間 | 管理職の自己申告（週単位） |
| 管理職 | DR資料を待つ時間、内容の確認にかかる時間 | 管理職の自己申告 |
| チーム | 量産移管前に、根拠となる検討・資料を集める時間 | 移管準備の作業で計測 |
| チーム（第2期） | 要求の変更に気づくまでの時間、古い値のまま進んだ手戻りの件数 | 通知の記録と手戻りの記録 |
| 利用状況 | 参加者ごとのノート作成数、継続して使っている人の割合 | 自動集計 |

#### 7.4.6 拡大の判断基準

第1期・第2期の終了時に、次を満たせば対象を広げる。

- 参加者の大半が、試験後も使い続けたいと回答している
- 個人の作成・検索時間、管理職の確認時間のいずれかで、明確な削減が数字で示せている
- 品質保証部門が、記録・証跡の扱いに問題がないと確認している

#### 7.4.7 想定されるリスクと対策

| リスク | 対策 |
|---|---|
| 慣れるまでPowerPointの方が速い | Excalidrawのテンプレートと、よく使う図形のライブラリを用意。最初の2週間は推進役が隣で支援 |
| 公開されるのを嫌がり、ノートを書かない | デイリー・メモは本人のみ。案件ノートの公開範囲を本人が選べることを周知。下書きは評価の対象にしないことを明文化 |
| 計算がExcelに残り、根拠が追えない | Excelファイルはノートに添付し、IDで結ぶ。よく使う計算を試験中に洗い出し、置き換えの候補にする |
| 既存システムとの二重入力 | DR・承認は既存システムのまま。本システムからはPDFを添付するだけにし、二重入力をしない |
| 管理職が見に来ない | 今週の更新一覧を週1回、管理職にリンクで通知する |

### 7.5 段階的な拡大

| 段階 | 対象 | 狙い |
|---|---|---|
| 第1段階 | 研究・開発（要求、設計判断、DR、試験、設計変更） | 思考過程と確定事項の資産化、要求トレーサビリティ |
| 第2段階 | 品目・BOMマスタ、設計変更と製造の連携 | 開発から製造への正確な引き渡し |
| 第3段階 | 製造・検査・出荷のロット・シリアル管理 | 製品の一生の「一本の糸」を製造まで延ばす |
| 第4段階 | 販売・サービス・市場不具合 | 顧客と市場からのフィードバックを設計へ戻す |

- 第1段階の中でも、試験導入の第1期（1人でも便利＋管理職も便利）→ 第2期（チームでつながる）→ チームの追加、の順で広げる
- 各段階で、既存システムとはIDで連携し、置き換えは効果が確認できたものから行う（原則8）
