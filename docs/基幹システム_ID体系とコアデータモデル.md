# 基幹システム ID体系とコアデータモデル

- 上位文書：「基幹システム 基本方針」「基幹システム 非機能要件」
- 対象：試験運用（数十人、研究・開発）。将来の拡張先も併記する
- 前提（非機能要件 9章）：30年以上一意・再利用しない／意味を埋め込まない／英数字のみ／既存システムのIDと共存し既存側を正本とする／試験運用の規模で動き、部品の差し替えで将来に対応

---

## 1. 基本の考え方

### 1.1 本システムが採番するのは「思考の単位」と案件だけ

| 区分 | 例 | 採番する所（正本） |
|---|---|---|
| **思考の単位** | ノート、フレーム | **本システム** |
| 版 | ノートの版 | Git（コミット） |
| モノ | 品番、（将来）ロット、シリアル | 既存システム |
| 人 | 社員 | 既存の社員情報 |
| 仕事の単位 | 案件 | **本システム**（案件台帳、2.4。既存システムに案件コードがないため） |
| 取引・顧客 | （将来）顧客、受注、発注 | 既存システム |
| 既存の文書 | 承認システム・設計判断・DR記録の文書番号 | 既存システム |
| 権限 | 機密タグ | 本システム（アクセス管理台帳） |

本システムが採番するのは、思考の単位（ノート・フレーム）と、既存システムにない案件だけ。**モノ・人・取引の番号は自分で作らない**。既存システムの番号をそのまま使い、本システムはそれを参照するだけにする（基本方針 原則2）。

### 1.2 すべての参照を「型付きID」で統一する

本システム外の番号は、**種別を前に付けた型付きID**で表す。種別が分かるので、同じ形の番号が別の意味で使われても混ざらない。

```
種別:値
```

| 種別 | 意味 | 例 | 試験運用 |
|---|---|---|---|
| `part` | 品番 | `part:123456-AB12` | ○ |
| `proj` | 案件 | `proj:P00042` | ○ |
| `user` | 社員 | `user:yu` | ○ |
| `doc` | 既存システムの文書（承認・設計判断・DR等）。既存の文書番号をそのまま使う（コロンを含まないため衝突なし） | `doc:DR-2026-0123` | ○ |
| `tag` | 機密タグ | `tag:A社-X100-GrA` | ○ |
| `data` | データ保管庫の大容量データ（100MB超） | `data:…` | ○ |
| `calc` | 共通の計算ツールと版（vault設計 9.5） | `calc:bracket-stiffness@v1.2.0` | ○ |
| `env` | 計算環境の版（vault設計 9.5） | `env:rd-calc-env@2026.10` | ○ |
| `export` | 持ち出しパッケージ（vault設計 9.6） | `export:261005-x200-359dy` | ○ |
| `lot` | 製造ロット | `lot:…` | 将来 |
| `sn` | 製品シリアル | `sn:…` | 将来 |
| `cust` | 顧客 | `cust:…` | 将来 |
| `order` | 受注・発注 | `order:…` | 将来 |

- 種別は台帳で管理し、追加できる（将来の拡張は種別の追加で対応）
- 将来グループ会社で番号体系が異なる場合は、発行元を付けて区別する（例：`part@grpA:…`）。試験運用では使わない

## 2. ID体系

### 2.1 ノートID（本システムが採番）

| 項目 | 内容 |
|---|---|
| 形式 | `YYMMDD-xxxxx`（作成日＋5文字のhash） |
| ファイル名 | `YYMMDD_タイトル_xxxxx.md` |
| hashの文字 | 英小文字＋数字から `0` `o` `1` `l` を除いた32種 |
| 採番 | オンライン時はサーバから未使用のhashを受け取る。オフライン時は手元で生成し、プッシュ時にサーバが確認 |
| 一意性 | 全社で一意。再利用しない。将来グループ会社に広げる場合も、採番サーバを1つにして一意を保つ |
| 正本 | プロパティ `id`（詳細は vault設計 3章） |

### 2.2 フレームID（本システムが採番）

| 項目 | 内容 |
|---|---|
| 形式 | `ノートID#Fnn`（例：`260915-7k2m9#F03`） |
| 採番 | 図の中で連番。フレームの要素に保存し、フレーム名を変えても番号は変わらない |
| 再利用 | フレームを削除しても番号は再利用しない（引用・開示グラントが番号を指すため） |

### 2.3 版の指定

| 項目 | 内容 |
|---|---|
| 版 | Gitのコミット（短縮形、7文字以上） |
| 形式 | `ノートID@コミット`、`ノートID#Fnn@コミット` |
| 使いどころ | 版を固定した引用、開示グラントの承認版、PDFの余白記載 |

### 2.4 案件（本システムの案件台帳で採番）

既存システムに案件コードがないため、本システムの案件台帳で採番する。

| 項目 | 内容 |
|---|---|
| 形式 | `P` ＋ 5桁の連番（例：`P00042`）。参照は `proj:P00042` |
| 意味 | 持たせない（部署・製品・年度を埋め込まない）。連番は登録順を表すだけ |
| 再利用 | しない。終了・中止した案件の番号も欠番として残す |
| 容量 | 5桁で約10万件。30年で足りない見込みになれば桁を増やす（既存番号はそのまま有効） |
| 表示名・略称 | 案件名と略称（例：「X100」）は別の項目で持つ。略称は変更可能で、検索とリンクの候補表示に使う |
| 台帳の項目 | 案件ID、案件名、略称、状態（進行中／終了／中止）、既定の機密タグ、責任者、開始日、終了日 |

**略称をIDにしない理由**：略称は製品名や計画の変更で変わり得る。IDに使うと、変わった時に全ノートのリンクを直すことになる。

### 2.5 品番・品名（既存システムが正本）

**品番**

| 項目 | 内容 |
|---|---|
| 正本 | 既存の品番体系・採番システム |
| 形式 | 数字6桁 ＋ ハイフン ＋ 英大文字・数字4桁（例：`123456-AB12`） |
| 形式チェック | 正規表現 `^[0-9]{6}-[A-Z0-9]{4}$`。形式外は警告。英小文字で入力された場合は大文字に自動変換 |
| 本システムでの扱い | ノートのプロパティ `parts` に手入力、本文中は `[[part:123456-AB12]]` |
| 実在確認 | 試験運用では行わない。将来、既存システムとの連携で行う |

**品名**

| 項目 | 内容 |
|---|---|
| 正本 | 既存システム |
| 本システムでの扱い | **IDとしては使わない**（品番で参照する）。将来の連携では、品番から既存システムの品名を取得して表示する |
| カンマを含む品名 | 品名にはカンマが使われるため、プロパティに書く場合は必ず引用符で囲む（例：`part_name: "ブラケット, L型"`）。表・CSVへの出力時も引用符で囲む |

### 2.6 社員

| 項目 | 内容 |
|---|---|
| 正本 | 既存の社員情報（社内認証） |
| 本システムでの扱い | 社内アカウントのIDを `user:` で参照（`owner`、承認者、開示先など） |
| 退職・異動 | IDは残す（過去の記録の作成者として必要）。権限だけを外す |

## 3. 本文中での参照の書き方

| 参照先 | 書き方 | 表示 |
|---|---|---|
| ノート | `[[260915_X100仮目標値_7k2m9]]` | 閲覧者の権限に応じてタイトルまたは「🔒」 |
| フレーム（埋め込み） | `![[260915_X100仮目標値_7k2m9#F01]]` | フレームの描画 |
| 版を固定した引用 | `![[260915_X100仮目標値_7k2m9#F01@a1b2c3d]]` | 固定版の描画。更新があれば通知表示 |
| 本システム外のID | `[[part:123456-AB12]]` | プラグインが種別に応じた表示にする（品番なら、その品番を参照している全ノートの一覧へ） |

**本システム外のIDもリンクとして書く理由**
- `:` はファイル名に使えない文字なので、ノートのリンクと衝突しない
- Obsidianのグラフ表示で、品番や案件が**複数のノートをつなぐ中心（ハブ）**として現れる。「この部品に関わる検討」が図として見える
- 索引DBが本文中のリンクも拾うので、プロパティに書き忘れても品番で検索できる

## 4. コアデータモデル（試験運用）

### 4.1 全体像

```
                ┌────────────┐
                │ 社員 user   │（既存の社員情報）
                └─────┬──────┘
                      │ owner / 権限保持
   ┌──────────────────┼───────────────────────┐
   │                  │                       │
┌──▼───────┐   ┌──────▼──────┐   含む   ┌───────────┐
│ 機密タグ   │◄──┤ ノート note  ├────────►│ フレーム   │
│ tag       │付与│（Git）      │         │ frame     │
└──────────┘   └──┬───┬───┬──┘         └─────┬─────┘
                  │   │   │                  │
        関係・引用  │   │   │ 外部参照          │ 開示対象
   ┌──────────────┘   │   └──────────┐       │
   │                  │              │   ┌───▼────────┐
┌──▼──────┐    ┌──────▼─────┐   ┌────▼───┴┐ 開示グラント │
│ 関係     │    │ 版 version  │   │ 外部ID   │（ノートの一種）│
│ relation │    │（Gitコミット）│   │ part/proj│└────────────┘
└─────────┘    └────────────┘   │ doc/…    │
                                └──────────┘
```

### 4.2 エンティティと正本

| エンティティ | 主な項目 | 正本 | 索引DBに写すか |
|---|---|---|---|
| **ノート** | id、type、title、owner、project、status、access、summary、parts、ext_refs、created、updated | Git（ノートのプロパティ） | ○ |
| **フレーム** | フレームID、所属ノート、フレーム名、フレーム内の文字 | Git（図のJSON） | ○ |
| **添付** | 添付ID（＝付属ノートのID）、ファイル名、機密タグ、由来、ハッシュ値 | 中身はGit LFS、属性は付属ノート（Git） | ○（属性のみ） |
| **版** | コミット、日時、作成者 | Git | ○（必要な範囲） |
| **関係** | 元ID、先ID、関係の種類、固定した版（引用の場合） | Git（プロパティと本文のリンク） | ○（解析して生成） |
| **外部参照** | ノートID、型付きID | Git（プロパティと本文のリンク） | ○（解析して生成） |
| **開示グラント（開示申請）** | 申請対象（フレーム・添付）、開示先、目的、申請者、承認者、判断（未処理／承認／却下）、承認した対象、理由（必須）、承認版、期限、更新時の扱い | Git（`type: grant` のノート） | ○ |
| **機密タグ** | タグID、名称、管理責任者（必須）、代理（必須）、有効期限、存在の秘匿、AI利用可否、PDF出力可否 | アクセス管理台帳 | — |
| **権限保持** | 社員 × 機密タグ | アクセス管理台帳 | — |
| **案件** | 案件ID、案件名、略称、状態、既定の機密タグ、責任者 | 本システムの案件台帳 | ○ |
| **保管レベル** | 社員 × ノート：ホット／コールド／アーカイブ、最終閲覧日時 | 本人の端末（プラグイン）＋索引DB | ○ |
| **監査ログ** | 閲覧、PDF出力、開示、正式化、AI問い合わせ | ログDB | — |

**索引DBに写すものは全て派生物**であり、Gitと台帳から再構築できる（基本方針 原則2）。

### 4.3 関係の種類（管理された語彙）

| 関係 | 意味 | 書く場所 |
|---|---|---|
| `link` | 本文中の通常のリンク | 本文 |
| `cites` | 版を固定した引用（埋め込み） | 本文 |
| `derived_from` | 元になった要求・情報 | プロパティ |
| `based_on` | 根拠にした検討・計算・試験 | プロパティ |
| `verifies` | 検証対象の要求 | プロパティ |
| `affects` | 影響する品目・図面 | プロパティ |
| `supersedes` | 置き換えた旧ノート | プロパティ |
| `promoted_to` | 正式化した先 | プロパティ |

- 関係の種類は台帳で管理し、自由に増やさない（増やす時は台帳に登録）
- 既存システムの文書（設計判断、DR記録、承認文書）への参照は `ext_refs: [doc:…]` で持つ

### 4.4 ノートの種類（試験運用）

設計判断・DR記録・承認は既存システムを使うため、試験運用では次の種類を中心にする。

| 種類 | type | 試験運用 |
|---|---|---|
| デイリー | `daily` | ○ |
| メモ | `memo` | ○ |
| 議事録 | `meeting` | ○ |
| 検討 | `study` | ○ |
| 計算 | `calc` | ○ |
| 要求 | `req` | ○ |
| 報告 | `report` | ○ |
| 図 | `drawing` | ○ |
| 添付の付属ノート | `attachment` | ○（自動作成） |
| 開示グラント | `grant` | ○ |
| 設計判断・DR記録・試験・課題・変更要求 | `decision` 等 | 既存システムを使用。本システムでは `ext_refs` で参照（将来、移行を検討） |

## 5. 検査ルール（プッシュ時にサーバが確認）

| # | 検査 | 不合格時 |
|---|---|---|
| 1 | プロパティ `id` が `YYMMDD-xxxxx` の形式で、全社で一意 | 受け付けない |
| 2 | ファイル名のID部分とプロパティ `id` が一致 | 受け付けない（プラグインが事前に自動修正） |
| 3 | ファイル名・本文がUTF-8・NFC | 自動で正規化 |
| 4 | `access` のタグが台帳に登録済み | 受け付けない |
| 5 | 引用元のタグが、引用先に付いている | 警告 |
| 6 | `parts` が品番の形式に合う（英小文字は大文字に自動変換） | 警告 |
| 7 | 型付きIDの種別が台帳に登録済み | 警告 |
| 8 | 関係プロパティの種類が語彙に含まれる | 警告 |
| 9 | フレームIDの重複・再利用がない | 受け付けない |
| 10 | プロパティ `id` がある（テンプレートを使わずに作ったノートの検出） | 受け付けない |
| 11 | プロパティ名が予約名・台帳登録済み・`my_` 始まりのいずれか（vault設計 5.4） | 警告 |
| 12 | 予約名・台帳登録済みのプロパティの型・取りうる値・書き方（日付は `YYYY-MM-DD`） | 予約名は受け付けない、他は警告 |
| 13 | プロパティ値に、台帳の顧客名リストの語が含まれない | 警告（本文に書くよう促す） |

## 6. 試験運用の構成

| 部品 | 試験運用 | 将来の差し替え先 |
|---|---|---|
| Gitサーバ | 社内設置の軽量なGitサーバ（Gitea等） | 同左または大規模向け |
| 索引DB | 小規模なDBの全文検索機能（PostgreSQL＋日本語全文検索の拡張等） | 大規模向け検索エンジン（OpenSearch等） |
| アクセス管理台帳・案件台帳・ログ | 索引DBと同じDBに同居 | 分離 |
| 採番 | 索引DBと同じサーバ上の小さな処理 | 同左（全社で1つ） |

- 索引DBは、検索の窓口となる層の背後に置き、差し替え可能にする（非機能要件 8章）
- 試験運用では、台帳・索引・ログを1つのDBにまとめて運用を軽くする

## 7. 将来の拡張（第2段階以降）

| 段階 | 追加するエンティティ | 正本 | 本システムとのつなぎ方 |
|---|---|---|---|
| 第2段階 | 品目マスタ、BOM（E-BOM／M-BOM）、設計変更 | 既存システム（PLM／PDM） | `part:` の実在確認・品目情報の取得、`affects` からBOMの使用先展開 |
| 第3段階 | 製造ロット、製品シリアル、検査記録、出荷 | 既存の生産管理 | `lot:` `sn:` の参照。シリアル単位の構成（どの部品のどの版か） |
| 第4段階 | 顧客、受注、設置先、保守履歴、市場不具合 | 既存の販売・サービスシステム | `cust:` `order:` の参照。市場不具合から要求・ノートへの逆引き |

型付きIDの種別を追加し、正本側のシステムと連携するだけで拡張できる。本システムのノートIDとデータモデルは変えない。

## 8. 決定事項と未決事項

### 8.1 決定事項

| 項目 | 決定 |
|---|---|
| 案件コード | 既存システムにないため、本システムの案件台帳で採番（`P` ＋ 5桁の連番） |
| 品番の形式 | 数字6桁 ＋ ハイフン ＋ 英大文字・数字4桁 |
| 品名 | IDとしては使わない。カンマを含むため、プロパティ・CSVでは引用符で囲む |
| 既存の文書番号 | コロンを含まないため、`doc:` ＋ 既存番号でそのまま参照 |

### 8.2 未決事項

| 項目 | 必要になる時期 |
|---|---|
| 品番の後ろ英数4桁の意味、版を品番に含めるか | 第2段階 |
| 製品の管理単位（シリアル／ロット） | 第3段階 |
